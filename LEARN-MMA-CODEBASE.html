MMA — Mass Message Automation

Learning path

The developer guide is the reference — twelve chapters, every file, every trap. This page is the schedule: what to read in what order, what to type while you read it, and how to know a thing has actually landed before you move on. Five sessions, roughly a working week at two hours a day.

How to use this page

Each session has four parts, always in the same order: read a chapter and the files it is about, do something at the keyboard, prove it with a command, and answer one self-check question out loud. If you cannot answer the question, the session did not land — re-read the one file named in it rather than pushing on. The sessions build; session 3 assumes session 2.

One rule that saves the most time. In this repo the box comment at the top of a file is not a summary — it is the record of the failure that produced the code. Read it before the code, every time. Most of what you need to know was written down by the person who got it wrong first.

Before session 1 — twenty minutes of orientation

MMA is not one program. It is up to a dozen small processes that never call each other's functions. They cooperate two ways only: shared files in userdata\ say what the data is, and window messages declared in src\core\messages.ahk say go and re-read it.

Separate processes cannot throw an exception into each other. They can only fall silent, and almost every bug this codebase has had is that silence. Hold on to that sentence — it is the reason for the logging, the registries, and half the comments you are about to read.

Do this now

Launch MMA, then look at what is actually running. Every AHK script titles its main window with its own full path; that is how these processes find and close each other.

Get-Process AutoHotkey64 | Select-Object Id, MainWindowTitle
Get-Process python*, pythonw* | Select-Object Id, Path

Match every line to a file in the tree. The Python ones have no AHK window at all — each signs its presence with a named event instead, which is exactly why they cannot ride on the same start/stop machinery as the rest.

The five sessions

01

The language, and the shape

~2 hrs

You cannot read this codebase without reading AutoHotkey v2, and v2 is not v1 with tidier syntax — it is a different language with the same file extension. Start there, then get the process picture straight before any product code.

Read

  • Chapter 1 — The AutoHotkey primer, in full. It is the longest chapter and the only one you should not skim.
  • Chapter 2 — The shape of MMA.
  • Then ARCHITECTURE.md §1–§3, which will now read as confirmation rather than information.

Do

Open src/chat/nav.ahk — about 75 lines, and the cleanest example of the bind pattern in the repo. Read every line. You should be able to say what each one does before you finish the session.

Prove

Parse an entry point without running it. /validate exists and is the right tool; validate entry points only, because AHK resolves calls at load and a library checked on its own reports errors that are not bugs.

$psi = New-Object System.Diagnostics.ProcessStartInfo
$psi.FileName  = "C:\Program Files\AutoHotkey\v2\AutoHotkey64.exe"
$psi.Arguments = '/ErrorStdOut /validate "D:\Software\Dev\Chatting\MMA\MMA.ahk"'
$psi.UseShellExecute = $false; $psi.RedirectStandardOutput = $true
$p = [System.Diagnostics.Process]::Start($psi)
$out = $p.StandardOutput.ReadToEnd(); $p.WaitForExit()
$p.ExitCode        # 0 = parses · 2 = error, text is in $out

Now break it on purpose — put if (1 { in a scratch copy and run the same command. Always prove a check can fail before you trust it passing. Every trap in this area produces a uniform "everything passes", which a pass-only test cannot tell from a real result.

Self-check Why does () => inside a for loop fail to see the loop's variable, and what do you do instead? (Chapter 1, closures.)
02

The spine and the registries

~2 hrs

Six files establish everything else. Read them bottom-up so you are never holding an unknown: nothing in a layer depends on anything above it.

Read

  • Chapter 3 — The spine with src/core/paths.ahk and src/core/log.ahk open beside it.
  • Chapter 4 — The registries with modes.ahk, hotkeys.ahk, messages.ahk, processes.ahk.
The idea to take away

Everything declarative lives in exactly one file. Features in modes.ahk, keys in hotkeys.ahk, messages in messages.ahk, services in processes.ahk, paths in paths.ahk. If you are about to hand-write a list of anything, you are about to grow a sixth registry — and the last time four hand-kept lists decided when services ran, they had drifted apart silently: three services started five seconds late, and two kept running after you unticked them.

Do

Add a feature, watch it appear, then delete it. One line in core/modes.ahk:

; delete this again in five minutes
FEAT_Def("scratch", "ScratchFeature", "Scratch (delete me)", "1", "Tools")

Restart MMA, open Settings ▸ Features, and watch the checkbox draw itself. You wrote no UI. Untick it, find the feat.set line in debuglogs\mma.log, then remove the line again. That round trip is the whole architecture in ninety seconds.

Prove

Run tools/test/services_test.ahk. It exists specifically to stop a fifth hand-kept list growing back.

Self-check A key is bound, its feature is on, and pressing it does nothing. Name three places that could have swallowed it, and the log line each one leaves behind.
03

One keypress, traced twice

~2.5 hrs · the centrepiece

This is the session that teaches the codebase. Follow one follow-up from the key to the paste — first on a numbered key, then on a shared one. Same destination; the difference between the two lanes is most of MMA's design.

Read

  • Chapter 5 — What a mass IS and Chapter 6 — The parser, quickly. You need the record shape, not the details.
  • Chapter 7 — The send path, slowly, with src/mass/runtime.ahk open.

F1 — the numbered key

Model 1's follow-up 1. Nothing is read off the screen.

1
MassBindModel(1)binds mass.1.fu1 — but only if FEAT_HotkeyAllowed says the owning feature is on. Off means never registered at all.
2
_ModelFire(1, fn)the wrapper that makes this key mean model 1. The key you press IS the model selector.
3
_SetCurModel(1)one global, set for the length of the send.
4
DoFu1() → _DoFuGroup(1, …)branch chooser, then editable paste, then the plain send — in that order.
5
CurMassSlot(slot)reads MASS_DOC, the library loaded from masses.json.
6
Snd / Sendtclipboard paste and Enter, from core/utils.ahk.

shared — the [mass.active] key

One key for every model. Something has to decide which.

1
MassBindActive()binds mass.active.fu1 — same gate.
2
_ActiveFire → _RunOnActiveModelevery shared key funnels through here. No answer means the key does nothing — the correct choice, and the most confusing thing MMA does.
3
SharedKeysOn()off in Settings ▸ Models means LOG_Bail, and the numbered keys carry on working from the same keypress.
4
LockedModelNo()a lock wins over everything — no mode check, no pixels. The badge on screen is the condition on which this branch is allowed to exist.
5
ModelMatchMode()manual opens the picker window; name/position call ActiveModelStatus(), which reads an ini written by a different process entirely.
6
_SetCurModel(n) → fn()and from here it is the left-hand lane, step 4 onward.

Do

Turn logging up in userdata\mass_gui.cfg under [Debug], press one follow-up key, and read the timeline back in debuglogs\mma.log. Find the LOG_Bail lines — each is a gate that closed. "The feature is off" is the correct answer to a startling number of why did nothing happen reports, and this is where it is written down.

Then read the reasoning

docs/decisions.md §5 and §5.1. Three model scripts used to exist; all three bound the same keys, and five separate mechanisms existed purely to decide who answered. The data moved into masses.json, the behaviour was already shared, and what was left was three processes fighting each other. None of those five mechanisms survive. The left-hand lane above is what replaced them.

Self-check Why does the shared key refuse to send when it cannot resolve a model, rather than falling back to the last one it knew? Answer in terms of what the failure would look like to a fan.
04

Pixels, and the discipline they need

~2 hrs

Everything that reads the screen lives in src/screen/, split deliberately in two: pure scanners with no side effects (pill_scan, rail_scan, reply_scan) and services built on them (model_detector, fansly_detector, reply_box, stats_overlay). The split exists so a service and its Settings calibrator cannot disagree about geometry.

Read

  • Chapter 8 — Detection, with core/active_model.ahk open.
  • src/core/dpi.ahk — short, and the file that stops you losing a day.
The rule

Never calibrate a coordinate off a screenshot. This desk is mixed-DPI — primary at 125%, second monitor at 150% — and AutoHotkey ships a system-DPI-aware manifest. On the second monitor three processes report three different rects for the same window, and none converts to another by one clean factor. Worse, the wrong numbers stay self-consistent inside the process: the mouse, the overlay and the capture rect all agree with each other and disagree only with the screen. Take every measurement from inside a throwaway AHK script and write those numbers into the config.

Do

Run a probe, not a test. tools/*_probe.ahk binds a key, stays resident, and exists so you can look at your own screen through it — detector_probe.ahk first. Note the difference from tools/test/, where every file asserts, prints N passed, M failed, exits, binds no keys and leaves no window. That contract is what lets Settings ▸ Debug ▸ Run all run the lot mid-shift.

Self-check When would you call DPI_ScriptWide(), and in what kind of process must you never call it?
05

Changing it without breaking three other things

~2.5 hrs

Read

  • Chapter 9 — The GUI and Chapter 10 — Auto import, skimming.
  • Chapter 11 — Recipes and debugging, closely.
  • Chapter 12 — The trap museum. Read it once now; come back to it every time something makes no sense.

Do — your first five changes, in this order

  1. Change a log line's wording in mass/runtime.ahk, press the key, find it in mma.log. You have now proved your edit reaches the running app.
  2. Add a feature and delete it — session 2's exercise, from memory this time.
  3. Add a hotkey end to end: HK_Def in hotkeys.ahk, HK_Bind(id, fn) in the process that owns it, a default in hotkeys.default.ini. Not a bare F-key — those are reserved. Use a Ctrl+Alt variant.
  4. Add a field to a mass via MASS_Fields() in store.ahk, and watch the loader, the writer, the blank-record builder and the migration all follow it. Run tools/test/store_test.ahk.
  5. Add a background service: a FEAT_Def, an SVC_Def, and the file. Boot, the Features tab, the Tools window, its count and the watchdog all walk SVC_ORDER and pick it up for free.

Prove

Your loop from here on is validate → test → look. For a GUI change, run the entry point and photograph the window with PrintWindow(h, dc, 2) — it does not steal focus, and you are usually live in Infloww. Call SetProcessDPIAware() in the capturing process first, or the capture is offset by a few hundred pixels and you photograph half the desktop.

Self-check You add a test file to tools/test/ and it never runs from Settings ▸ Debug ▸ Run all. Why not?

When you get stuck

Look the symptom up rather than reasoning from first principles — nearly every one of these has already cost somebody a day here, and the answer is written down.

What you seeWhere to look first
The key does nothing at alldebuglogs\mma.log for a LOG_Bail line. A closed feature gate, a shared key with no resolved model, or a mass slot nobody filled in.
The script exits 0 and nothing happenedChapter 12. A reserved name such as base, or a name collision — AHK is case-insensitive, so a variable and a function sharing a name fail to load.
Two Continue/Abort dialogs for one mistakeThat is one bug, not two. Read the pair in the crash log as a single event.
A window opens in the wrong placeCoordinates. Gui.Show scales w and h by the display scaling but passes x and y straight through, and a CoordMode set at the top of any included file becomes the default for every thread in that process.
A scan reads the pixels next to the thing it was calibrated oncore/dpi.ahk, and session 4's rule.
A setting is on in the config and dead on the keyboardA hand-kept list somewhere that the registry should own. That is the failure mode the five registries exist to remove.

What not to read yet

About 35,000 lines can wait, and knowing which is part of learning the tree. src/ui/ is a third of the codebase and almost nothing includes it — windows are the outermost layer, not the centre, which is why a UI bug is almost never a UI bug. src/vendor/ is thqby's WebView2 wrapper, the OCR library and a JSON parser: not yours, and not to be read. The optional services in src/services/ are each self-contained with their own README.
