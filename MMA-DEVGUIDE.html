MMA — Mass Message Automation

Developer guide

A twelve-chapter walkthrough of the AutoHotkey core: what every file does, why it is shaped that way, which AHK concepts you need in order to read it, and how to change any of it without breaking three things you did not know were connected.

What this is for

The docs already in this repo tell you what the tree is (ARCHITECTURE.md) and why it is shaped that way (docs/decisions.md). This guide teaches you how to read and write the code — the language, the patterns, the traps, and the actual control flow from a key being pressed to a message landing in a chat.

It assumes you know no AutoHotkey and no more than the surface of this codebase.

The one thing to understand first

MMA is not one program. It is up to a dozen small processes that never call each other's functions. They cooperate two ways only: shared files in userdata\ say what the data is, and window messages declared in src\core\messages.ahk say go and re-read it.

Separate processes cannot throw an exception into each other. They can only fall silent — and almost every bug this codebase has ever had is that silence. Learning MMA is largely learning where the silence can come from.

The CORE selection

19 files, about 7,600 lines — the mass / send / detect / parse / organise spine. Everything else in the repo (another ~35,000 lines) is windows, tools, tests, optional services and vendored third-party code.

Tier 1 — the spine

src/core/paths.ahk276Every path from one anchor. Included by 47 files.
src/core/log.ahk728One log for eight processes, and the level that makes silence audible.
src/core/modes.ahk335The feature registry. FEAT("id") is the only question the rest of the code asks.
src/core/hotkeys.ahk1003Every key in MMA, declared once, bound by id, stored in an ini. Contains no keys.
src/core/messages.ahk~110The ten window messages processes send each other.
src/core/processes.ahk758The service registry, the launcher, the watchdog.

Tier 2 — the product

src/mass/store.ahk413What a mass is, as data. The record shape and masses.json.
src/mass/parser.ahk764What a mass is as text. Three parse modes and the ::branch marker.
src/mass/runtime.ahk979What a mass does. Every follow-up, PPV, branch and __mm handler.
src/mass/engine.ahk~110The process. Loads the library, binds the keys, listens for reloads.
src/core/utils.ahk1417Snd/sndFu — the code that actually sends — plus the TAB-staging picker.
src/mass/next_fu.ahk310The one key that reads the chat and sends whichever follow-up comes next.
src/mass/model_picker.ahk659The "which model?" window, for the modes where nothing on screen answers it.

Tier 3 — knowing which model is on screen

src/screen/pill_scan.ahk296Pure pixel functions. One BitBlt, then memory reads. No side effects at all.
src/core/active_model.ahk783Three resolution strategies, lock mode, and every refusal to guess.
src/screen/model_detector.ahk254The background service: scan, OCR on change, write an ini.

Tier 4 — the window, and getting masses into it

src/ui/main_core.ahk1800The app behind the main window, with no window in it. Load, Save, Parse, import routing.
src/sequences/sequences.ahk424The Discord Ctrl+click import — how masses get into MMA at all.
src/chat/nav.ahk~75The navigation keys. Tiny, and a clean example of the bind pattern.
