AHK v2 GUI — the advanced bits

The parts of Gui that do something other than put a button on a form: windows that refuse focus, geometry that survives DPI scaling, live restyling, scoped hotkeys, and how to check any of it without a pair of eyes on the screen.

Two kinds of claim appear below and they are marked, because they are not worth the same: measured here means it was demonstrated against AutoHotkey 2.0.26 in this repo — usually because it cost an afternoon first. capability means it is a documented feature this codebase either uses or could; trust it, but check the numbers on your own machine.

1 · Window styles that change behaviour, not looks

Options passed to Gui() are not decoration. Four of them change what the window is as far as Windows is concerned.

+E0x08000000 — WS_EX_NOACTIVATE measured here

The window can never become the active window. Click it, and focus stays where it was. This is the single most useful style for an automation overlay: the app you are driving stays focused, so Send keeps going to the right place and any HotIf scoped to that app keeps matching. 

ov := Gui("+AlwaysOnTop -Caption +ToolWindow +E0x08000000", "overlay")
ov.Show("x100 y100 w200 h60 NoActivate")   ; NoActivate on Show too

The style and the NoActivate show-option are both needed. The style stops clicks activating it; the option stops the first Show() stealing focus. Miss the second and the window steals focus exactly once — which is enough to break a picker whose keys are scoped elsewhere.

-Caption, +ToolWindow, +AlwaysOnTop capability

-Caption removes the title bar and border — which also means the client area is the window, so Show("w… h…") and control coordinates finally agree with each other. +ToolWindow keeps it out of the taskbar and out of Alt+Tab. +AlwaysOnTop is topmost.

A -Caption window has no close button. If its only way out is a key and that key is scoped to a different window, a user who switches away is stranded with a window that ignores them. See §8 — this is a real bug that shipped.

+Owner and +Owner<HWND> capability

+Owner alone makes a window modal-ish: the owner is disabled while it is up. +Owner followed by a handle makes it owned by that window — it stays above the owner, minimises with it, and dies with it, without being topmost over everything else on the machine. Good for dialogs belonging to your own main window; risky against a foreign window (a browser), because you inherit its z-order behaviour.

Transparency and click-through capability

WinSetTransparent(200, "ahk_id " g.Hwnd)      ; 0-255 whole-window alpha
WinSetTransColor("FF00FF", "ahk_id " g.Hwnd)  ; that colour becomes holes
g.Opt("+E0x20")                                ; WS_EX_TRANSPARENT: clicks pass through

TransColor plus WS_EX_TRANSPARENT is how you get a shaped, non-interactive HUD — an outline drawn over another app that the mouse never notices.

2 · Geometry and DPI — where the time goes

The one that will get you. With DPI scaling on (the default), AHK reports control geometry through GetPos in logical units, but creates the window in physical pixels. On a 125% display the rows render 1.25× further down than the numbers say — so a window sized from its own measurements, or from AutoSize, comes out a quarter too short and clips its last control clean off.

Measured in this repo while building the follow-up picker: rows 67 px apart according to GetPos, 86 px apart on screen. 86 ÷ 67 ≈ 1.28. measured here

The fix is one option, and then everything agrees:

g := Gui("+AlwaysOnTop -Caption +ToolWindow -DPIScale +E0x08000000", "picker")

With -DPIScale, GetPos, Show's w/ h/x/y, WinGetPos on other windows and MonitorGetWorkArea are all in the same physical pixels. Fonts still scale with the display, so scale any fixed width yourself or the window shrinks relative to its own text: 

w := w * A_ScreenDPI // 96   ; the ini value now means "at 100%"

Measuring before showing measured here

Controls have real positions as soon as they are added — you do not have to show the window to measure it. So the tidiest way to size a window around variable content is to add everything, ask the last control where it ended up, and show once: 

hint := g.Add("Text", "xm y+10 w" tw, "TAB next   ENTER send   ESC cancel")
hint.GetPos(, &hy, , &hh)
g.Show("NoActivate x" x " y" y " w" w " h" (hy + hh + g.MarginY))

Do not reach for the Show("Hide") + WinGetPos pattern. WinGetPos obeys DetectHiddenWindows, which is off by default, so on a hidden window it neither finds anything nor assigns its output variables. The script then dies on the next line with "This local variable has not been assigned a value", pointing at your arithmetic instead of at the real cause.

Gui.GetPos() and GuiCtrl.GetPos() go at the handle directly and do not care whether the window is visible.

Auto-height text measured here

Give a Text control a w and no h and AHK sizes it to fit its content, including explicit newlines. That is what makes a variable-height list of messages possible without measuring strings yourself.

Staying on the monitor capability

Loop MonitorGetCount() {
    MonitorGetWorkArea(A_Index, &l, &t, &r, &b)
    if (cx >= l && cx < r && cy >= t && cy < b)
        break                       ; the monitor the window landed on
}

Work area, not monitor bounds — it excludes the taskbar. Clamp after positioning, or a tall window anchored to the bottom of a maximised app runs off the top of the screen.

3 · Layout, without a layout engine

There is no flexbox. There are four positioning shorthands, and between them they do most of what you need:

OptionMeans
xm / ym Back to the left / top margin (g.MarginX, g.MarginY).
y+8 8 px below the previous control's bottom. y+0 flush against it — which is how you build a contiguous coloured band out of several controls.
x+12 12 px right of the previous control — same row.
xs / ys Relative to the last Section (a control added with the Section option), for column layouts.

Everything flows off the most recently added control, so the order you add in is the layout. For resizing, register controls and move them in the Size event — there is no anchoring built in: 

g.OnEvent("Size", (gui, minMax, w, h) => Relayout(w, h))

4 · Restyling a control after it exists

You do not have to rebuild a window to change how it looks — and you should not, if it is on screen, because destroy-and-recreate flickers. Controls take new options and repaint: 

for i, row in rows {
    sel := (i = staged)
    for _, c in row.ctrls
        c.Opt("+Background" (sel ? "F2CFDF" : "F8E7EF"))
    row.head.SetFont("c" (sel ? "8A2B57" : "A3778A"))
    row.head.Text := (sel ? Chr(0x25B8) : " ") "  " i ".  " row.label
    for _, c in row.ctrls
        c.Redraw()
}

Opt("+Background<hex>"), SetFont("c<hex>") and assigning .Text all work post-creation; Redraw() is what makes the background change actually appear. measured here

The band trick. A selectable "row" of wrapped text is four controls, not one: a padding Text with h5, the label, the body, another pad. All four carry the row's background, all four are stacked with y+0, and the gap between rows is the window background. That gives you a highlight bar around content of any height, with no owner-draw.

5 · Colour and theming

g.BackColor := "FDF3F7" repaints the window and the static controls on it. Measured on 2.0.26: measured here

ControlFollows BackColor?
Text, Checkbox, Radio, GroupBox Yes — no white box behind them, nothing to do.
Edit, ListView, Button No — they keep their system colours.

That split is usually what you want: tinting the window while leaving the typing surfaces white is exactly the cue that separates "panel" from "somewhere you type". When you do need a dark Edit or ListView, set them individually with +Background<hex> and a c<hex> font colour.

A dark title bar is not a Gui option — it is a DWM attribute: capability 

DllCall("dwmapi\DwmSetWindowAttribute", "ptr", g.Hwnd,
        "int", 20, "int*", 1, "int", 4)   ; 20 = USE_IMMERSIVE_DARK_MODE

6 · Controls worth knowing about

ControlWhy you would reach for it
ListView Rows with columns, checkboxes (Checked), sorting, icons via ImageList, and ItemEdit/DoubleClick events. The workhorse for anything list-shaped.
TreeView Hierarchies. Add(name, parent, options) returns an item ID you keep.
Tab3 Tabbed pages. Controls added after tab.UseTab(2) belong to page 2; UseTab() with no argument escapes the tab control — forget it and your buttons end up buried on the last page.
Link Inline clickable text with <a href="…"> markup inside a label.
Progress Also fine as a plain coloured bar — Background<hex> and a value — when you want a meter, not a spinner.
Hotkey Lets the user press a combination and hands you the string. The correct way to build a key-rebinding screen.
StatusBar Bottom strip with parts; SetText(text, part).
Custom Custom Class<WinClass> embeds any registered window class — the escape hatch when nothing built in fits.
ActiveX Embeds a browser control. Heavyweight; a self-contained HTML file opened in the real browser (what this page is) is usually the better answer.

7 · Events, and the messages underneath them

g.OnEvent("Close",       (*) => ExitApp())
g.OnEvent("Escape",      (*) => g.Hide())
g.OnEvent("Size",        (gui, mm, w, h) => Relayout(w, h))
g.OnEvent("ContextMenu", ShowMenu)
g.OnEvent("DropFiles",   (gui, ctrl, files, *) => Import(files))
btn.OnEvent("Click",     (*) => DoThing())
lv.OnEvent("DoubleClick",(lv, row) => Open(row))

Below that there is OnMessage, which is how you get behaviour the event model does not expose. Two this repo uses: capability 

OnMessage(0x201, WM_LBUTTONDOWN)   ; drag a -Caption window from anywhere in it
OnMessage(0x232, WM_EXITSIZEMOVE)  ; persist position the moment a drag ends

The drag trick is PostMessage(0xA1, 2) — tell Windows the click was on the title bar it does not have. Saving position on WM_EXITSIZEMOVE rather than on every Size means one write per drag instead of hundreds.

PostMessage's fourth parameter is Control, not a message value. Passing 0 there throws "Target window not found" — omit it instead.

8 · Hotkeys that belong to one window

A GUI that hijacks Tab, Enter and Esc must hijack them somewhere, not everywhere. HotIf takes a criterion function: 

HotIf StagingActive
Hotkey "*Tab",    Next,   "On"
Hotkey "*+Tab",   Prev,   "On"
Hotkey "*Enter",  Commit, "On"
Hotkey "*Escape", Cancel, "On"
HotIf                                ; back to unscoped

StagingActive(*) {                   ; the (*) is REQUIRED
    return staged && WinActive("ahk_id " chatHwnd)
}

The (*) is not style. HotIf calls its criterion with the hotkey name, and a zero-parameter function is rejected outright with "Invalid callback function."

Wildcard vs exact modifiers measured here

*Tab fires on Shift+Tab as well — the * ignores extra modifiers. So walking backwards needs its own *+Tab binding, and it does win: with both registered, plain Tab reaches the wildcard handler and Shift+Tab reaches the exact one. Verified by registering both under a HotIf scoped to the probe's own window, SendLevel 1, sending {Tab} then +{Tab}, and recording which handler ran.

The stranding bug. Scoping the keys to the chat window is correct — and it means that when the user switches away, Esc no longer reaches your window. With -Caption there is no close button either. They are stuck looking at a topmost window that ignores them.

Fix it with a watchdog, not with a wider hotkey scope: 

AltStageWatch() {                      ; SetTimer(…, 250) while staged
    if !WinExist("ahk_id " chatHwnd)   ; the anchor is gone …
        return EndStaging()            ;   … so the picker has no subject
    want := WinActive("ahk_id " chatHwnd) ? true : false
    if (want != shown)                 ; hide while they are elsewhere,
        shown := want,                 ;   restore when they come back
        (want ? g.Show("NoActivate") : g.Hide())
}

Pair it with an absolute timeout that releases the keys no matter what. A key that is claimed forever because a thread forgot to clean up is the worst failure this design has.

9 · Staying alive

A hidden Gui and an OnMessage handler do not keep a v2 script running. The script needs a hotkey, a timer, a visible window, or an explicit Persistent. A tool whose whole job is to sit waiting for a message exits instantly and silently without one.

10 · Testing a GUI without looking at it

Does it build?

Parsing clean and building are different questions. A control placed on the wrong tab, a class constructed with the wrong arity, a Map indexed with a missing key — none are syntax errors, and all of them throw the first time the window opens, in front of a user. Include the real layout file, stub what it depends on, build it headless and assert on the control census: 

#Warn All, StdOut     ; a #Warn DIALOG is modal and looks exactly like a hang

What does it look like?

PrintWindow reads a window's pixels directly, without raising it and without stealing focus — so it works on a window that is behind others, and on one that must not be activated. measured here 

PrintWindow(hwnd, hdc, 2)   ; 2 = PW_RENDERFULLCONTENT

Call SetProcessDPIAware() in the capturing process first. Without it GetWindowRect hands back virtualised coordinates (divided by the scale factor), your bitmap is created too small, and the capture clips — which looks exactly like the window itself being clipped. That misdiagnosis cost an hour.

If the window is hidden when you capture it, you get a black rectangle. ShowWindow(hwnd, 8) — SW_SHOWNA — makes it visible without changing focus, which is enough to grab it and leaves the user's foreground window alone.

Drive it without synthetic keys

Sending {Tab} at a test window means sending it at whatever is actually focused. Call the handler directly instead — AltStageNext() rather than Send "{Tab}" — and you exercise the same repaint path with nothing escaping into the rest of the machine.

11 · Trap sheet

SymptomCause
Window is a quarter too short; bottom control clipped DPI scaling. GetPos is logical, the window is physical. Add -DPIScale.
"This local variable has not been assigned a value" on an arithmetic line A WinGetPos above it silently assigned nothing — the window was hidden and DetectHiddenWindows is off. Use Gui.GetPos.
"Invalid callback function." when setting HotIf The criterion takes no parameters. It must accept (*).
Shift+Tab moves forwards *Tab matches it. Register *+Tab separately.
A window with no title bar that ignores Esc Its keys are scoped to another window that is no longer active. Watchdog timer.
Dark window, but every label sits on a pale box — or a black one Statics on a tab page cannot be recoloured after creation. SetFont on one makes it lose the inherited background and repaint with the system colour; adding +Background then renders it #000000. Measured: the identical label outside the tab takes the colour correctly. Set the colour on the window font before the controls are added (g.SetFont("s9 cFFFFFF")) and give the tab control its own Background; never touch the labels afterwards.
Dark window with a white title bar DWM owns the title bar. DwmSetWindowAttribute(hwnd, 20, &1, 4) — DWMWA_USE_IMMERSIVE_DARK_MODE, attribute 19 on pre-2004 builds.
Every radio button can be checked at once They are not one group. Windows ends a radio group at the first control that is not a radio, so a description Text between them makes each a group of one — and a group of one never unchecks anything. Add the radios consecutively and place the labels afterwards.
Overlay steals focus once, then behaves +E0x08000000 is set but the first Show() lacks NoActivate.
Script with a hidden GUI exits immediately A hidden Gui does not keep v2 alive. Add Persistent.
Script exits 0 with no error and no window Look for {base: …} — base is reserved and sets the prototype.
Whole script fails to load, no useful message A variable and a function sharing a name (matching is case-insensitive).
No output, no exit, nothing on stderr A modal dialog you cannot see — often #Warn. Use #Warn All, StdOut.
