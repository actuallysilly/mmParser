How MMA is built, in one picture

MMA is really two programs that grew together. The AutoHotkey half is the hands (keys, typing, clicking, windows). The Python half is the eyes and the brain (reading the screen, recording chats, AI). A small runner connects them.

1. You
Hotkeys, typed triggers (__lore), hotstrings, the main window and Settings.
2. AHK app (MMA.ahk)
One AutoHotkey process: the hotkey registry, mass sending, hotstrings, windows, model selection. Starts and watches everything else. src/core, src/mass, src/ui, src/hotstrings, src/chat
3. AHK helpers
Small separate AHK scripts for overlays and detectors (model detector, stats overlay, reply timers, timer, activity). src/screen, src/timer, src/activity
4. Runner
Starts every Python program the same way and restarts it if it crashes. AHK talks to it over a named pipe. src/services/runner/runner.pyw
5. Python services
Always-on eyes: chat reader, Screen Map, automation, typelog, autoword, pinger. src/services/*
6. Python tools
Windows you open: TestFlow, Arena, Live Trainer, Fan Viewer, Chat View, Video import, __lore, Ghost OCR. tools/*, src/services/llm, src/services/ocr
7. Local AI
Ollama on your PC running Artemis-31B (or nemo 12B). Nothing goes to the cloud. src/services/llm/client.py, userdata/llm.ini
8. Your data
userdata/ (settings, masses, typelog, shift log, corpus), D:\FanData (406 fan files), D:\ShiftRecordings (206 videos, 23 GB).

Debt ranked by real usage (0–10)

Is there a usage log? Not a real one. MMA never counts "action X was used". The main log (debuglogs/mma.log) could have shown it, but it fills 10 MB in about 3 hours, mostly with 58,000 repeats of the same feature-switch lines, so today's 10:13–16:28 is all it remembers. The ranking below pieces usage together from other traces:

  • mma.log (today): what each background service did. No key presses were logged, because you were testing with me, not chatting.

  • hotstring_usage.ini: per-trigger counts.
  • typelog: about 1,000 typed and 70–350 pasted messages per day.
  • TestFlow and Live Trainer ratings, and when each tool's data file was last changed.

Score = how urgently it should be fixed or cut: 10 = it hurts you right now, 0 = healthy. Being unused only scores high when keeping the feature costs something.

What to ponder

Three directions, from cheapest to biggest. They aren't exclusive; my recommendation is 1, then 2.

1. Prune (days)

Cut what's broken, dead or duplicated: numbered key sets, Fansly detection, pinger, draft.py, test helpers on real keys, probes moved out of tools/, root clutter. Fix the F24 collision. Commit the November work.

Risk: low. Gain: less to break, a clearer Settings.

2. One eye, one memory (weeks)

Every tool asks Screen Map where things are and one chat reader what's on screen; everything is stored in FanData. Retire the ~15 separate readers and the shiftlog store. This is your #1 priority (lore_gatherer, "one merged scroll+capture core") taken to its end.

Risk: medium. Gain: geometry stops tripping us, and the data gets clean enough to train the agent on.

3. Pick one UI (weeks)

Keep either WebView or Classic, not both. Or go further: AHK keeps only keys and sending, and every window becomes a web page served by Python, like TestFlow and Fan Viewer already are.

Risk: higher. Gain: halves the biggest area of code.
