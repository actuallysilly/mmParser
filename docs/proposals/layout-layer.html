One Screen Map for every tool

Why MMA keeps clicking and reading in the wrong place when the window size, the monitor or the window changes, and a plan to fix it once for all tools. No programming knowledge needed to read this.

01The short version

Every MMA tool that looks at or clicks in Infloww currently carries its own map of where things are on screen. Most of those maps were drawn once, by hand, on a 1920×1032 window. Your windows are 3441×1381, 3842×2090, 4130×1658, on two monitors with different zoom levels, and often with 2–3 models in one window. The maps no longer match the window, so tools miss.

The fix is one small background service, the Screen Map, that:

  1. finds every open Infloww window and works out what each one is (main window or fan window, which model, which fan),
  2. measures where everything is in each window, from what is actually on screen right now,
  3. writes that down in one place, and
  4. every tool reads it from there before doing anything. If the map isn't sure, the tool doesn't act.

What you get: tools that work in any window size, on any monitor, in main windows and fan windows, and that no longer break every time you move or resize a window.

02What goes wrong today

Think of each tool as a delivery driver with its own paper map, printed years ago. When the town gets rebuilt, every driver gets lost, and fixing one driver's map doesn't help the others.

Three separate problems that look like one

Window size

The map was drawn at 1920×1032. Infloww doesn't just get bigger when the window grows; the chat list stays the same width and the chat gets wider, so you can't just scale the old numbers.

Monitor zoom (DPI)

Your monitors are at 125% and 150%. Different parts of Windows report different positions for the same window. Already mostly fixed (dpi.ahk).

Which window

All Infloww windows are titled Infloww Messages - 333 (333 is the agency tag), so tools can't tell them apart by name and sometimes grab the wrong one.

Why this keeps coming back: the good fix (measuring the window live) was built inside the chat reader to solve the chat reader's problem, and never moved out where the other tools could use it. An older plan (snapping.md, part A) suggested storing positions as percentages of the window. That would still break, because Infloww's layout doesn't stretch evenly. This proposal replaces part A.

03The idea: one Screen Map

One surveyor, many drivers. A single background service walks around, measures the town as it is right now, and pins an up-to-date map on the wall. Every tool reads that map. When the town changes, the surveyor redraws it, and every tool is right again at the same time.

It works in three steps, explained in the next three sections:

STEP 1Which window is which: main or fan window, which model tab is active, which fan.
↓
STEP 2Measure each window: where the list, the chat, the header, the message box and the model tabs are, and how big the text is.
↓
STEP 3Every time a tool is about to act: a quick check that the map is still true. If it isn't, re-measure; if that fails too, don't act.

04Step 1 · Which window is which

Every window Windows opens gets a hidden ID number (a "handle") that stays the same until that window closes. Two windows can look identical, but their IDs never match. That's how the Screen Map keeps them apart; it never relies on the title.

Two kinds of Infloww window

Main window

Model tabs at the top left (often 2–3), the chat list on the left, the chat on the right. Model = the name on the active tab.

Fan window

One fan's chat plus the Fan insights panel. No chat list, no @handle shown. Model = the name on its own top-left tab. Fan = see below.

The two kinds are easy to tell apart from the screen: a main window has the chat-list column (with its thin divider lines), a fan window doesn't. A third, look-alike window (the "Inbox" one with no model tabs) is recognised and ignored.

Which model: by name only

The model is read from the name on the active tab (and the big name above the chat list, as a second opinion), never from the profile picture. MMA already knows which name goes with which mass file (your [ActiveMap] setting), so there's nothing new to set up.

Why re-read it every time: with 2–3 models in one window, switching tabs doesn't tell Windows anything. The window is the same and only the inside changed. So "which model" is read fresh whenever a tool is about to act, which takes a few milliseconds.

Which fan, in a fan window

The fan window only shows the fan's header name (which chatters can edit, e.g. $171 Dan(dan). The Screen Map looks that name up in the same model's chat list, where the unchangeable @handle sits next to it. If exactly one fan matches, done. If it's unclear, the fan stays unknown instead of guessed. Mixing two fans' histories is worse than keeping one fan in two pieces.

The one rule for all of them: a tool acts on the window you're in. Whatever model and fan that window shows is who the tool works for. Fan windows included: __mm in Hail's fan window sends Hail's masses. Every tool works in both window kinds unless it says otherwise.

05Step 2 · Measuring a window

Infloww draws thin grey lines (1 pixel, colour #444444) between its panels. Those lines are the landmarks: find them and you know where the list ends, where the chat starts, where the header and message box are, at any window size. The height of the header tells how big everything is drawn (the "scale"). This is exactly what the chat reader already does successfully; the Screen Map takes that code and makes it everyone's.

For each window it records, in plain terms:

One way of counting pixels. Positions are stored relative to the window's own top-left corner, in real screen pixels. Converting to "where on the monitor" happens in exactly one place. The DPI mess came from different tools counting pixels differently; with one way of counting, it can't come back.

The map is a small file on disk (userdata/layout/infloww.json) that both halves of MMA (the AutoHotkey side and the Python side) can read.

06Step 3 · Checking before acting

A map can go stale: you drag a window, resize it, switch model tab, open a fan window. The Screen Map redraws when Windows reports a window moved, resized, opened or closed. But some changes (like switching model tabs) don't trigger any of that, so every tool does a spot check first: "is the divider line still where the map says?", "is the active tab still CIN?". That's a handful of pixels, about one millisecond.

07No map, no action

This is the "mandatory" part. No tool may click or read inside Infloww without a map marked ok for that window. No tool may keep its own coordinates either. Once a tool is moved over, its old hand-measured numbers are deleted, and a check stops anyone (me included) from sneaking new ones back in.

Today: a tool with a wrong map clicks somewhere, or reads the wrong text and confidently uses it. You find out later, if at all.

After: a tool that can't be sure does nothing, and says so. Annoying for a second, but never wrong.

How it tells you is decision 1 below.

08What changes for you

  • Nothing to set up. No calibrating, no clicking windows to label them, no profile pictures. Model names already map to your mass files.
  • Arrange windows however you like: any size, either monitor, 1 window with 3 models or 3 windows, fan windows on the side. Tools follow.
  • Fan windows work for every tool unless that tool says otherwise.
  • Tools stop silently misfiring. When something can't work, you'll be told instead.
  • Fixes stop being one-tool-at-a-time. When Infloww changes its look, one place gets fixed and every tool recovers.

09Which tools move, in order

The Screen Map is built first, then tools move onto it one at a time. Each move is tested live with you before the next starts, and each one deletes that tool's old coordinates.

10What this does NOT fix

  • Reading names badly. The map tells tools where the name is; it doesn't make the text reader (OCR) better at weird names like xX_Dbcooper77. That's a separate project: testing newer OCR engines on real name crops. The live readers still use a 2022 model while newer ones sit unused.
  • Chatters editing the header name. Still true; fans are still identified by @handle, never the header name.
  • Infloww redesigning itself. If the divider lines disappear, the map stops saying "ok". But then everything fails loudly in one place, and one fix repairs everything.

11Costs and risks

  • Up-front work before anything feels better. Step 0 has no visible payoff until tools move onto it.
  • Two systems for a while. During the move, some tools use the map and some still have old numbers. The table above tracks which.
  • "It refuses" will feel worse at first than "it guesses", even though guessing was causing the silent mistakes.
  • One more background service. It's small and only looks at the screen when something changes. It joins the same service list as the others.
  • Possible overlap with the chat reader: both would screenshot Infloww. See decision 2.

12Decisions for you

Answered 2026-11-27: 1 → (c), a tooltip for hotkeys, log only for background tools. 2 → later, after the map works. 3 → the order in section 9. 4 → every tool works in fan windows unless it says otherwise. 5 → the window you used last wins (not the main window).

  1. When a tool refuses, how should it tell you?
    (a) a small tooltip near the mouse for 2 seconds, e.g. "Can't see Infloww's layout"; (b) only written in the log; (c) a tooltip for hotkeys you pressed, log only for background tools. My pick: (c).
  2. Should the Screen Map also take over taking screenshots?
    Today the chat reader screenshots Infloww every 5 seconds on its own. If the Screen Map takes the screenshots and shares them, there's one camera instead of two (less duplication, one less thing to break), but it's a bigger first step. My pick: yes, but as a later step, after the map works.
  3. Is the order in section 9 right? Or is something else hurting more right now?
  4. Are there tools that should NOT work in fan windows? (e.g. mass-related tools that only make sense in the chat list.)
  5. When there are two windows for the same model (e.g. main window on Hail + Hail's fan window), and you're in neither, do background tools (unread ping, stats) read the main window? My pick: yes, main window wins.

13Words used here

Screen Map
The proposed service: knows which Infloww window is which and where everything is inside each one.
Window ID (handle)
A hidden number Windows gives each open window; unique, and fixed until the window closes.
Main window / fan window
Infloww's normal window (tabs + list + chat) vs a single fan's chat popped out on its own.
DPI / zoom
Windows' "Scale" setting (125%, 150%). Different per monitor on your desk, which used to confuse positions.
Divider lines
Thin grey lines Infloww draws between panels; the landmarks the map measures from.
Scale
How big Infloww is drawing things compared to the old reference window.
OCR
Turning a picture of text into text. Separate from this project.
@handle
The fan's OnlyFans username in the chat list; chatters can't change it, so it's the reliable fan ID.
Spot check
Looking at a few pixels to confirm the map is still right before acting.
