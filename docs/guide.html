MMA

You know the job. This is where everything lives, and the handful of things that will waste your afternoon if nobody tells you.

The one architectural fact that matters. The window is just an editor. A separate background script — the mass engine — owns every hotkey and does all the sending. They share files, not memory, so a save takes effect on the next keypress with no restart. It also means if the engine is not running, no key works, no matter how good the fields look. MMA starts it and a watchdog restarts it every 5 s if it dies.

The window

Left is one mass in 14 fields, one tab per model — the selected model's name is violet and bold in the tab strip, so the tab you are typing into is the one that is coloured. Right is the workflow. Bottom is every other window: Settings, Hotstrings, Tools, Variants.

Tools is the background tools — unread pinger, stats overlay, both model detectors, the automation listener, the activity tracker and the typelog recorder — each with its live state and an On/Off. It was Pinger: ON/OFF, which was one of those getting a button because it was the one people asked about; the rest were a tab and a Save away in Settings. The button's own label counts what is running, so Tools (2) means two are up.

The strip used to also carry Open with Code, How to Use, Add Hotkey, New Script and one ◻ toggle per message script. They have moved to where you are already standing when you want them:

  • Open with Code and How to Use — Settings → Scripts, next to Wipe TEMP and Check update.
  • Add Hotkey — the top of the Hotstrings window, beside the title, and named Add hotstring… there, because that is what it makes. What it writes is a hotstring in one of the message files, and that window is where those are listed, searched, overloaded and deleted. (It needs MMA's main window running: the dialog belongs to it.)
  • New Script — the bottom of the Add Hotkey window. The new file drops straight into that window's File dropdown and is selected, so there is nothing to reload.
  • The ◻ script toggles — Hotstrings → Startup scripts. It reads each script's live state on a timer, rather than a label that only changed when you clicked it, and gives each one a Restart instead of an off-then-on.
ControlWhat it actually does
ParseFills the tab you are looking at, clearing that tab's fields first.
ClearWipes the paste box and every field in all three tabs. Disk untouched — reload to recover.
Export !mmaReverse of Parse: rebuilds paste text from the current tab. For handing a mass to someone.
Archive…Opens the archive: search past masses, preview, load one back into the fields. Every Parse appends the raw text to mass_archive.txt unless you have turned that off under Settings ▸ GUI ▸ Mass archive; a mass already archived today is skipped silently, so re-parsing a fix does not store it twice.
Load <model>Disk → the model tab in front of you, at that model's live mass slot. Discards what is on screen. The button carries the name of whichever tab you are on.
Save <model>The tab in front of you → disk, into the mass # picked on that tab, then nudges the engine. Read this first.
Set massNoWhich of the three masses that model sends. Applies instantly. Read this too.

Both buttons relabel the moment you switch tab, so the button you are about to press always names the model whose fields are on screen — the same model the tab strip is showing in violet.

It used to be one load and one save button per model. That grid is still available under Settings → GUI → Use legacy Load/Save UI, for the one thing the pair cannot do: load or save a model you are not looking at. Ticking it reloads MMA, and it changes nothing about what a save writes.

Add hotstring… (at the top of the Hotstrings window; the dialog itself is still titled Add Hotkey, and the grab hotkey opens the same one) appends a hotstring to a message file without opening an editor — trigger, target file, send mode (snd() sends, SendText() types only, Sendt() sends with a custom wait), :: vs :*:, one message per line. The script restarts itself so the trigger is live immediately. The OCR variant (Ctrl+Shift+O) lets you drag a box round text anywhere on screen and opens the same form prefilled.

…or make it a follow-up — Replace follow-up…

A hotstring is a trigger you type. But the text you grab off the screen is usually a message you have just sent by hand, and the reason you grabbed it is that it worked better than the follow-up MMA has. That belongs in the mass, not behind a trigger.

Replace follow-up…, on the same button row, hands the Lines box to the capture window instead:

drag a box (^+o)  →  Replace follow-up…  →  model · mass · follow-up  →  Replace

The three dropdowns open on the follow-up you last sent, which is nearly always the one you are rewriting — so the usual answer is to press Replace f2 and be done. It shows what that follow-up says right now, and asks before overwriting it.

  • Replace overwrites the trunk — what the plain key sends. One message per line, up to three (f2, f2.5, f2.7); a fourth line has nowhere to go and it says so rather than dropping it. Sub-slots the new text does not fill are cleared, so a replace can never leave an old third message trailing a new first one.
  • Add as alt puts the same text in as an alternative instead — a branch, offered on the follow-up key with Tab. Same window, same three dropdowns; see Add alt-FU for what the branch name box does.

Reached this way, both buttons save straight to masses.json — the engine has the new wording on the next keypress. That is the opposite of the same window opened from Variants ▸ Add alt-FU…, which writes into the grid and waits for Save to file: there you are in the editor and can see what happened, here you are in Infloww and the main window is behind it. The line under the buttons always says which of the two you are in.

The Lines box is left as it was, so cancelling over there costs you nothing — a grab is expensive to make twice.

All of them live in userdata\hotkeys.ini, editable in Settings ▸ Hotkeys. Changes apply live. ^ Ctrl · ! Alt · + Shift · # Win · blank = deliberately off. F13–F24 are Scimitar side buttons 1–12.

Anti-fumble. A second send within 200 ms of the first is dropped, and any key pressed while a send is still in flight is dropped — so a clumsy F1-then-F2 cannot put two masses in one chat. Navigation keys are exempt. Tune with DoubleFireWindowMs under [meta] in hotkeys.ini; 0 disables it.

If you open hotkeys.ini, ignore brPick, brFu2, brFu3 and brPpv. Branches used to have four keys and their own picker window; they ride the ordinary follow-up key now, so nothing claims those entries and setting them does nothing.

Paste format

Three modes, picked automatically from what is in the paste. You never choose.

ModeTriggered by
keyworda line starting with an exact field name (f2.5 …, ppvfu1 …)
prefixedany line starting with f/fu + number
positionalneither — blank lines separate the groups

Positional — what a Discord mass usually is

!mma opening message here            ← optional; without it, line 1 is the mass

first follow-up                      ← f1
second part of it                    ← f1.5

second follow-up                     ← f2

third follow-up                      ← f3

ppv the caption                      ← group starting "ppv" → ppv

did you like it?                     ← ppvfu1  (group straight after the ppv)
want more?                           ← ppvfu2

Within a group: line 1 → fN, line 2 → fN.5, line 3 → fN.7. A fourth line is ignored. !mm !mma mm mma are interchangeable, colon optional.

A mass that spans lines — !mma alone on top

Put the marker on a line by itself and everything under it is the mass — blank lines and all, as one message. Nothing in the block becomes a follow-up.

!mma:

If you were my artist, how would you picture me? 🎨

Would my curves take over the entire canvas...
Or would you only sketch the parts you couldn't stop thinking about? :3

Would your artwork be bold enough to leave people speechless? ♡

The block stops at a --- fence (eaten with it), at any labelled line (f2, ppv, ::branch…), or at the end of the paste. If follow-ups come after a multi-line mass, close it with a fence — positional follow-ups have no label of their own to stop the block with:

!mma

paragraph one

paragraph two
---

late night opener                    ← f1
still up?                            ← f1.5

Export !mma writes this form for you whenever the mass spans lines, so it round-trips.

Prefixed — blank lines stop mattering

!mma opening message
f1 first follow-up
f1.5 second part
f2 second follow-up
ppv the caption

f1 fu1 f1: fu 1 all identical.

Only .5 and .7 work today. f1.1 / f1.2 / f1.3 match nothing and are silently dropped — no error, no log line, the part is just not there. If a follow-up part vanishes after parsing, this is why. known bug

Both spellings are supposed to work; it is written up in development.md. Until it is fixed, use .5 and .7.

Comments, fences, branches

-- this line is a comment           "--" alone or "-- " + space
---                                 3+ dashes = multiline-ppv fence

follow up 1                         unmarked = the trunk, f1 then f1.5 then f1.7
::alt another wording of f1         ":: + name" = that BRANCH's answer to f1
::mexican mehico                    any name you like; it identifies the branch
::german germaniaaaaa               the same name twice in one group =
::german gernabiaaa22222              one branch, two messages (f1 and f1.5)

A fence keeps a multi-paragraph PPV caption in one field instead of spilling into ppvfu1: everything from the ppv marker up to the --- becomes the caption, blank lines and all.

A branch is a named alternative: its own f1/f2/f3/ppv, any of which may be empty. Pick it at f1 and f2/f3/ppv open on it. It keeps its identity by name, so the ::mexican under follow-up 2 is the same branch as the one under follow-up 1 — you write it where it belongs instead of in a block of its own. Max 6 branches per mass, 3 messages per branch per follow-up.

The wording can go on its own line under the marker — write it the way it reads. These two are the same thing, and several lines under one marker are several messages of that branch's answer (f3, then f3.5):

::tits Would you mind if I smothered you with them?
::tits
Would you mind if I smothered you with them?

A marker with text on its line doesn't own the line after it — that one is the trunk's next sub-slot. A marker with nothing under it says nothing at all; it never sends a blank line.

A group that opens with a marker is the next follow-up, and consecutive branch-led groups are choices at that same step rather than successive follow-ups. So this is an f2 that asks a question and two f3s that answer it, with no trunk f3 at all:

!mma Are you needy for nakedness?

late night opener                       f1

which curve entices you the most?       f2
and be honest about it                  f2.5

::tits                                  f3, if she says tits
smother you with them

::ass                                   f3, if she says ass
my personal throne

An empty trunk f3 is correct there: what goes out depends on her answer. Sparse is normal.

alt: and --Name are gone. They were two spellings of this one thing: an alt was a branch nobody had named, a --Name block was a branch written somewhere else. ::alt some wording is what an old alt: line is now — alt is just a branch name. Masses already saved keep working; masses already written in the old syntax need those markers changed before they parse as alternatives again.

A leading word: is stripped from message text (so pasted transcripts don't carry their labels). URL schemes are exempt: http https ftp ftps mailto tel file.

Footgun 1 — massNo

Each model holds three masses and sends one. The Set massNo radios pick which. Applies instantly, no save.

This is the number one cause of "my hotkeys stopped working." The keys are fine. massNo points at a slot you never filled, so the key sends an empty field, which sends nothing — silently, with nothing on screen to say so.

MMA now warns the moment you switch to an empty slot and logs it. If keys go quiet, check massNo before anything else.

Footgun 2 — load / save cover all three tabs

They are labelled per model, but each one moves all three tabs at once.

The way this bites: load Aliw → edit Mass 2 → click save Rama. You have just written Aliw's three masses into Rama, because the tabs still held Aliw's data.

Habit that avoids it: load a model, edit it, save that same model. One model start to finish.

Save while the engine is down and MMA says so explicitly rather than reporting success — the write worked, but nothing on the machine can send it.

single & edit

Two boxes in the gutter beside f1, f2, f3.

offonscope
single parts go out as separate messages, wait time between parts joined into one message with line breaks per model and per group
edit pasted and sent pasted only, no Enter — change it before it goes per group, all models

edit applies immediately without a save. Wallet check before FU3 in Settings is the same mechanism aimed at f3.

Use a single hotkey for all masses

One key per action instead of one per action per model — that's the shared key set, and the whole of Settings ▸ Models below the model rows is about it. The numbered per-model keys ignore every control here and keep working whatever you set.

Enabled is the outer switch. Off, the shared keys go quiet and say so in the log — a real answer, not a broken one, for a machine where nothing on screen identifies the model. Then pick a Strategy:

StrategyHowCosts you
Manual — pick with the GUIThe shared follow-up and PPV keys open a window; you pick, and the send happens on your answer. Reads no pixels. A window in front of every shared send. Nothing is ever assumed — this is the mode to be in when detection isn't trustworthy.
AutomaticReads the screen. Set separately per site, because the two sites fail in different ways — see below. Everything below.

Automatic is configured per site, and a mixed setup is the normal case:

Siteby name (OCR)by position
OnlyFans (Infloww) OCRs the model name off the tab. Survives reordering. Depends on names matching across Infloww/Discord/MMA, which they often don't — map them in [ActiveMap] / [ModelAliases]. Default here. Uses where the lit tab sits, through the Tab order row. No names, no OCR. Trusts the order — reorder and you re-teach.
Fansly The rail truncates its labels ("Luxdo Fa…"), so there's often no full name to read at any OCR quality, and two models sharing a prefix are indistinguishable. Uses which card on the rail is selected, through the Rail order row. Default here — for the reason in the column to the left.

Each order row only offers the models that are on that site — the Platform column decides it, live, so switching a model to Fansly takes it out of the tab order as you watch. One model on Infloww means one tab-order dropdown, not four; a site with none says so instead of showing a row. Positions a site doesn't have are saved as "no answer", so a lit tab that isn't yours sends nothing rather than something stale.

Teach either order by pointing: click a model's tab in Infloww — or its card on the Fansly rail — and press that model's ^!N. The key knows which window is in front and teaches that one. High beep = set, low = refused, tooltip says why.

Why Manual exists. Screen detection doesn't fail by going quiet — it fails by reporting the wrong tab confidently, and then a shared key sends one model's message to another model's fan. With no answer at all the shared keys deliberately do nothing rather than guess. If detection isn't solid on your screen, switch to Manual, or switch the section off and use the numbered keys.

Read Detector sees: top to bottom when it's wrong — no lit tab is a colour/region problem; a wrong tab number is geometry (TabOrigin/ TabPitch); a right number pointing at the wrong model is your tab order.

Platform per model: set manual for a model MMA can't see (Fansly), and "detector saw nothing" resolves to that model instead of nothing.

Lock — one model, no more asking

Manual's window is the right answer to "which model am I on?" and the wrong answer to the way a shift is actually worked: every message for one model, then the next model. Twenty minutes of pressing the same side button means twenty windows asking a question whose answer hasn't changed — and a window you dismiss by reflex isn't protecting you from anything.

Locking answers once. While a lock is on, every shared key — the side mouse buttons included — sends that model. No window, and nothing on screen is read. The working sequence:

DoWhat happens
1Press a side button, pick the model in the window as usual That follow-up goes out, and the shared keys are now aimed at that model.
2^!lLocked. The badge appears, naming the model.
3Clear that model's messagesThe side buttons send straight out — no window, ever.
4^!lUnlocked. The picker is back, unchanged.
5Change model — next side button, or ^!N Step 1 again, for the next one.

The same lock is a toggle in the "Send follow-up" window itself — the checkbox on its bottom row. It names the key beside it, and it flips the lock the moment you click it, reading Locked to name while on. Clicking a different model button with it ticked moves the lock to that model. The main window has a Lock to name button too, which locks to the model tab in front — that is why it names it.

A small LOCKED badge sits in the corner of the screen for as long as the lock does, naming the model. It never takes focus, and clicking it unlocks. So does ^!l again, the checkbox, or the main window's button, which reads Unlock (name) while a lock is live.

You do not have to unlock to move on: another model's ^!N pressed under a lock moves the lock, and the badge follows. Step 4 is in the list because unlocking is what puts the "which model?" safety net back for the model you have not chosen yet.

If MMA has no answer for which model is on screen, ^!l refuses and beeps low rather than locking to a guess — pick a model first.

The badge is the safety mechanism, so don't park it off-screen. A lock is a mode in which a key you press sends to a model nothing on screen identifies — exactly the shape of mistake that puts one model's message in another model's chat. The badge is what makes that visible from the chat you're sending into. Move it if it's in the way ([Lock] BadgeX / BadgeY in mass_gui.cfg, screen pixels) but keep it somewhere you'll see it.

It's a lock, not a fourth strategy: it applies whatever this tab says. Under Automatic it overrides the detector, which is occasionally what you want on a tab the scan keeps misreading — and the badge is the reason that's safe to offer. The numbered per-model keys are untouched by it, as by everything else here.

Tab bars — dividers on your own tab strip

Eight near-identical tabs are hard to read at a glance, and detection doesn't help with that: the problem isn't that MMA can't tell them apart, it's that you can't, quickly, forty times an hour. So split the strip up with dividers.

One hotkey. ^!, puts a bar where the pointer is. Everything else is the bar itself:

Do thisGet
^!,Place a bar at the pointer (and un-hide the layer if it was hidden).
Left-drag a barMove it. Windows' own drag, so it's exactly as smooth as moving any other window.
Right-click a barIts menu: Remove · Colour (eight presets, the system colour picker under Custom…, or apply one to all bars) · Size (taller / shorter / wider / narrower, applies to every bar) · Add another bar here · Hide all bars.

A bar is a real little window, five pixels wide, so it drags and right-clicks like anything else on your desktop. It never takes focus — click one mid-sentence and your cursor stays in the chat box.

The cost is that those five pixels are no longer click-through: a click that lands exactly on a bar hits the bar, not the tab behind it. A divider goes in the gap between tabs, so in practice you're never aiming there — but if it does bite, [Marks] ClickThrough=1 puts the old behaviour back. Bars then can't be dragged or right-clicked, and ^!, is all you have.

A bar means whatever you meant by it. It is decoration: MMA never moves one, never reads one, and never works out which model is which from one. Which model is live is the lock badge's job, and it looks nothing like a bar.

Reply timers — how long has that fan been waiting?

The conversation list gives you a clock time and nothing else. Turning 7:45 am into "four minutes" is a subtraction you do in your head, against a clock you have to go and look at, once per row, forty times an hour — and the row you get wrong is always the one you were about to scroll past.

So MMA does the subtraction and paints the answer. Any conversation that is unread and has been sitting past a threshold gets a thick border in that threshold's colour:

WaitingBox
under 3 minnothing
3–4 minyellow
4–6 minred
6–10 minpink
10 min+bright white

Those are the defaults. Every time and every colour is yours, under Settings ▸ General ▸ Reply timers — a colour picker per tier, and clearing a row's minutes deletes that tier. The quiet band at the bottom isn't a separate setting: it's just everything below your first tier, so lowering that one shrinks it.

Calibrate it before it does anything — two drags, and you draw both.

  1. Calibrate the list… — drag a box around the whole list of conversations. This is where MMA looks.
  2. Calibrate a row… — drag a box around one conversation, picking one that is unread (it needs to see the orange dot). This is how big a box gets drawn, and it's what makes the frame cover the whole row instead of part of it.

Both rectangles are on your screen at your window size, so there's no sensible default to ship — until you draw the first one, the line next to the button says so in red and nothing is painted.

The region is stored relative to the Infloww window, so moving or maximising Infloww takes it along. The window has to be in front for boxes to show: they're frames drawn at fixed offsets inside one window, and left up over something else they'd just be coloured rectangles floating over your desktop.

Why a row needs its own drag. The unread dot isn't in the middle of its row — it sits on the same line as the timestamp, below the fan's name. So a box centred on the dot comes out noticeably high. The row calibration finds the dot inside the box you drew and measures the difference, which is the one thing MMA can't work out from the list alone.

You can also type the two numbers directly (Row height and Above dot) if you'd rather. Leaving Above dot blank means "assume halfway", which is the old behaviour and draws slightly high.

You never dismiss a box. MMA finds the rows by the little coral unread dot at the right-hand end, so replying is what clears it — open the conversation, the dot goes, and the box goes with it. Conversations you've already answered never get one, which is the whole reason it isn't every row: the list is sorted by recency and runs off the bottom of the screen, so boxing everything would fill the screen with frames that need nothing.

The frames are click-through — clicking one opens the conversation underneath exactly as if it weren't there — and they never take focus from the message you're typing.

If the boxes look wrong, press Calibrate a row… again — it sets both numbers at once and is quicker than guessing. By hand:

  • Row height — a frame covering two conversations, or only part of one.
  • Above dot — frames sitting consistently high or low.
  • Border — how thick the frame is drawn.

If they're sideways or off the list entirely, re-do Calibrate the list…. Saving applies within a few seconds; nothing restarts.

The boxes don't show up in screenshots, and that's deliberate: MMA scans those same pixels for the unread dots, and a frame it could see would be a decoration quietly changing what the scan reads.

When you need a picture of them, untick Keep the boxes out of screenshots. While it's off, avoid tier colours close to the orange of the unread dot — with the colours MMA ships, there's plenty of room.

A row stamped Yesterday or with a date is counted as if it arrived at midnight, so its wait comes out as however long today has been. That's a floor, not a guess — it can only ever understate how long someone has waited, never overstate it.

Bars are stored against the window, not the screen — move or resize it and they stay on their tabs — and nothing has to be calibrated first, so this works on a strip MMA can't read at all.

In mass_gui.cfg under [Marks], one line per bar — Bar1 = 412,44, or Bar2 = 338,44,4AC9FF where the third field is that one bar's colour. Delete the Bar lines to clear the lot. The menu writes all of this for you; the section is just where it lands. Also there: SepColor (what a bar with no colour of its own uses), SepWidth / SepHeight, ClickThrough, and WinMatch for which window bars belong to (the detector's window by default). Switched off in Features ▸ Tools.

If the tab detector starts miscounting, take the bars off the strip first. MMA reads the tab strip by grabbing those exact pixels, so anything drawn over them is a candidate for being counted. Each bar asks Windows to leave it out of screen capture, which handles it — but that is a request to the compositor, not a guarantee, so it's the first thing to rule out.

Stars are gone (v2.1), along with the flicker and the misplacement they brought with them. A star needed a glyph, a font and a magenta transparency key to punch its background out; a bar needs none of that, because the whole little window is the bar. Any old Mark1 = sep,412,44 lines are converted to Bar lines the first time MMA starts; star lines are dropped.

Tab-staging — the branches of a follow-up

One key, one list. Press the follow-up key as normal:

  • No alternatives → it sends. Nothing appears.
  • Alternatives → all of them are pasted into the chat box with ▸ marking one. Tab moves the marker · Enter sends the marked one · Esc cancels and clears the box.

You read the options in the real chat box, at the real width, with nothing stealing focus. Picking a branch variant is remembered for that conversation, so f2/f3 open on it; picking main at f2 returns you to the trunk.

If Enter "stops working" in a chat, a choice is still staged. Tab/Enter/Esc are captured while it is — scoped to that window only. Press Esc, or wait 45 s for it to release on its own.

Adding one — Variants ▸ Add alt-FU…

The Variants grid is the whole mass at once, which is what you want for reading it and not for adding one line to it — nothing on it says that a row is a branch, that the row needs a name before the picker can offer it, or that a second wording goes on a second line of one cell rather than in the next column. Add alt-FU… asks in order instead: which model, which mass, which follow-up, and what it says. It shows you what that follow-up says right now, and which branch names are already taken.

You pasteWhat happens
Plain text, one message per line One branch. Named from the Branch name box — or alt, then alt1, alt2… if the mass already has one. Type a name that already exists and it adds to that branch, which is the point of a branch keeping its identity across follow-ups.
Lines with ::name markers Parsed exactly as a real paste is — markers kept, nothing auto-added, several branches in one go. So working alt code copied out of Discord goes straight in. A bare line under a marker continues that branch; a line above the first marker is the trunk being copied along for context and is dropped.

Opened from the grid, Add writes into the grid, not to disk. You see what it did before committing to it, and Save to file is still the only thing that writes your library — so a mistake is undone by closing the window. The status line says so after every Add.

The same window reached from Replace follow-up… saves straight away instead, because there you are not in the editor. The line under the buttons says which.

Three messages per branch per follow-up is the ceiling (f1, f1.5, f1.7), and six branches per mass. Both are refused out loud rather than silently dropped.

Edit variants in Variants…, or write them in the paste. Separators are configurable in mass_gui.cfg [Settings] — with \n, \t, \s escapes (\s is needed because ini reads strip edge spaces):

AltStageVariantSepbetween variants\n\n (blank line)
AltStagePartSepbetween parts of one variant\s\s|\s\s →   |  
AltStageMarkermarks the staged variant▸

Don't put a / in AltStagePartSep. The staged preview is pasted into the Infloww composer, and / is Infloww's command trigger — it opens the slash-command menu over the box, which then swallows the Tab and Enter the picker runs on. The picker looks frozen, and the wrong variant goes out once you escape it.

It used to default to / for exactly this reason-shaped bug. If your config still has the old value, MMA rewrites it to | once, automatically — but it leaves a separator you chose alone, so if you set one containing a slash, that's on you.

Same rule for anything else you put here: it has to be inert in a chat composer.

Next follow-up

Ctrl+XButton2. OCRs the conversation, finds the last follow-up already in it, sends the one after. Right per chat and per model with nothing to remember, and it skips gaps — on a mass with no f2, "last seen f1" sends f3 and says so.

It refuses in two cases, both deliberate:

  • No follow-up found and the mass isn't on screen. Ambiguous — you're scrolled up, or this fan never got the mass. Sending f1 would repeat a message or open with "did you see what I sent?" to someone who got nothing.
  • The last follow-up the mass has is already there. Wrapping to f1 would re-send.

Both beep low and tooltip which it was.

Region is set in Settings ▸ Sending. A wrong region can't announce itself — it just never finds a follow-up and always sends f1. Tune it there, or run the Next follow-up probe in Settings ▸ Debug to see exactly what it reads.

Clicking the next chat too early

A follow-up is not one message. f1, f1.5 and f1.7 go out as three, with a pause between each, so one keypress owns the chat box for a good second. Click the next conversation inside that second and the parts still in flight land in the chat you just moved to — one fan gets half a follow-up and a stranger gets the other half.

So while a send is running there's a wall over the conversation list. The click isn't lost — it's held. MMA remembers where you clicked, and the moment the send finishes it plays the click back at the same spot. You click once, nothing seems to happen for a beat, and then the chat opens. A tooltip says so while you're waiting.

Nothing to calibrate. The wall covers the conversation list you already drew for reply timers; if you never drew one, it covers everything to the left of the Next follow-up pane, which is the same column. Set [ClickWall] Region in mass_gui.cfg only to overrule that — in the window's coordinates, like the reply-timer one, not the screen's.

It checks the list hasn't moved before clicking. Infloww sorts conversations by most recent message, and the send holding your click is what makes one most recent — so a point that meant "row 4" when you pressed it can be a different fan a second later. MMA keeps a strip of pixels from under the pointer and re-reads it before playing back. If the rows moved it beeps, says so, and leaves the click to you rather than opening the wrong chat.

Only the list, and only while sending. Clicks anywhere else are never touched — outside those two seconds and that rectangle there's no hotkey registered at all, so drags and double-clicks behave exactly as they always did. Switched off in Features ▸ Sending, and read fresh on every send, so unticking it takes hold on the next follow-up rather than the next restart.

Easy / Advanced

Easy is MMA as of v1.4.0 — paste, parse, tabs, script toggles, basic settings. Advanced is everything, each switchable alone.

Easy doesn't hide the extras, it switches them off — hotkeys never register, services never start. A hidden feature that still runs can still surprise you. Your individual choices are remembered; flip back and every box is where you left it.

Hotstrings

Canned messages live in plain files: content\general.ahk (shared, always running) and one per account in content\accounts\.

:*:_gns1::{
    snd("your message here")
}

A key for one you send constantly

Some messages go out often enough that typing the trigger is the slow part. Any hotstring can optionally have a hotkey as well, in two places:

  • For one you already have — select it in the Hotstrings window and press Hotkey…. The Key column shows what is bound.
  • While writing a new one — Add hotstring… has a Record… button. Press it, press your chord, and the key is bound when you press Append. Nothing is written until then, and Clear drops it.

Esc cancels a recording, Backspace means "no key". Any trigger can have one, dots and all — ..intro is as bindable as _gns1.

The trigger keeps working exactly as before — the key is a second way to fire the same thing, not a replacement. An overloaded hotstring bound to a key still offers its variants, because the key runs the same code the trigger does.

Stored inhotkeys.ini, under [hotstring], as trigger = key — the same file and format as every other key in MMA, so it is hand-editable and it appears in Settings ▸ Hotkeys like anything else.
ConflictsChecked when you bind. If the key is already used, you are told what by and asked whether to go ahead — the conflict report in Settings ▸ Hotkeys covers these too.
Takes effectA new binding restarts the message script that owns the hotstring, and says so — the script reads its keys when it loads. Changing a key applies live with nothing interrupted.

The key is global, like the hotstring it stands in for. A hotstring fires wherever you type, so its key fires wherever you press it — including Discord, your browser and everything else. Pick chords you would not otherwise hit. This is also why bare, easy keys are a bad choice here even though nothing stops you.

Duplicates are refused. Record a key that something else already uses and you are told what owns it and asked to pick another — no "bind it anyway". A hotstring key is global, so sharing one means both fire and whichever script loaded last wins, which is not a state worth offering.

This replaces something that was already happening the wrong way: bare !9:: blocks written straight into a message file, each sending one message. Those work, but they are invisible to the Hotkeys tab and to the conflict report, and they are lost the moment that file is tidied.

With ~117 of them the problem is recall, so the Hotstrings manager searches the message text as well as the trigger — find one by half-remembering a phrase. From there: jump to source, delete, or make it an overload.

Overloads give one trigger several variants without rewriting your message files — the trigger is re-pointed at a picker when the script loads. Per trigger: ask (chooser, click a row or press 1–9, Esc cancels) or random.

Actions menu

^!m. Searchable list of every action and its key. Type to filter, Enter to run. Two things make it worth the muscle memory:

  • It runs actions with no key bound — otherwise unreachable without editing the ini.
  • It's generated from the registry, so it can't go stale.

Other scripts are suspended while it's open (so typing can't fire a hotstring), and focus returns to your chat before the action runs.

Discord import

Ctrl+click a message in Discord. MMA copies it, reads the channel name to decide which model it's for, and hands it to the window, which parses it into that model's tab.

#aliw-staff-chat → aliw → the Aliw model. Unrecognised channel → a prompt asks which model and remembers, so the next one is automatic. Aliases live in mass_gui.cfg [ModelAliases] as name=slot — the same table name-based detection uses.

Logs

Settings ▸ Debug. MMA is up to eight cooperating processes; this is how you find out which one went quiet.

SwitchDefaultDoes
Write a log fileonEvery process appends to debuglogs\mma.log — what it did, and every point where it deliberately did nothing.
Report errors with a pop-upoffA failure also raises a dialog carrying the last 20 log lines. The "debug someone else's machine" switch — they can screenshot it.
Max loggingoffThe full firehose: every feature gate, every setting read, every branch.

They apply everywhere within a second or two — no save, no restart.

21:42:26  BOOT  engine.ahk   11244  lifecycle  start ahk=2.0.26 …
21:42:31  DEVL  engine.ahk   11244  mass.fu2   devlog: DoFu2 entered
21:42:31  BAIL  engine.ahk   11244  send.fu    model 2 follow-up 2 is EMPTY …

How to read it. "Nothing happened" has exactly two causes and one grep separates them:

  • DEVL line present, no send → the code ran and chose to stop. The BAIL right after says why.
  • No DEVL line at all → it never ran. Key unbound, feature off, engine down, or the press was debounced. The hk.* lines say which.

Levels: BOOT/EXIT (process start/stop, with reason) · DEVL (it fired) · INFO · BAIL (deliberately did nothing, and why) · WARN · FAIL/CRSH (with stack).

Buttons: open mma.log · Error log (failures only, short) · Mark log (press before and after a repro — only the lines between matter) · Diagnostic report (the file to send: environment, both config files, last 400 log lines; masses and message text excluded) · Clear logs · probes · self-tests.

For a machine you can't open Settings on: set MMA_DEBUG=max (or popups / off) in the environment and launch. It overrides all three, and the checkboxes grey out and say so.

Back up userdata\ and content\. That's everything you've written. Updates skip them deliberately, but nothing protects them from a mistake.
