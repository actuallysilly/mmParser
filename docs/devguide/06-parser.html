Chapter 6

The parser

src/mass/parser.ahk, 764 lines. It turns text somebody wrote in Discord into 45 fields, and it has to do that without ever being told which format the text is in. This is the least defensive code in the core and the place where a wrong guess sends a message no one wrote.

The problem it solves

Someone in a Discord channel posts a mass. It might look like any of these:

--- positional ---          --- prefixed ---        --- keyword ---
!mma hey babe                 !mma hey babe             mma hey babe
                              f1 did you see it?        f1 did you see it?
did you see it?               f1.5 still up?            f1.5 still up?
still up?                     f2 hellooo?               f2 hellooo?
                              ppv unlock this           ppv unlock this
hellooo?                                                ppvfu1 like it?

ppv unlock this

All three mean the same thing. Nobody is going to be told which mode to use, and if the parser picks wrong the text lands in the wrong fields and gets sent to real people. MMA picks the mode automatically by looking at the text.

Read docs/mass-format.md alongside this chapter. That file is the user-facing spec — what the format is. This chapter is how the code implements it and why it is shaped the way it is.

The unusual thing about this file

CONCEPT-ENCOUNTERED

A parser that writes into GUI controls

Every other file in the core takes data in and returns data out. This one does not. It writes its results directly into the edit boxes on screen:

ck := "m" mNo "_" slot                  ; e.g. "m2_fu1_5"
if edCtrls.Has(ck)
    edCtrls[ck].Value := StripPrefix(t)

edCtrls is a global Map owned by the GUI: control key → control object. FillTab is declared global in bulk so it can reach it.

That is a real coupling and it is worth understanding why it is tolerable here. The parse result is "the boxes are now filled in" — parsing is an editing operation, and the boxes are the editing surface. Returning a record would mean the GUI immediately copying it into the boxes anyway, and the intermediate object would be a shape that exists nowhere else.

The cost is that the parser cannot be unit-tested without a GUI and cannot be reused by anything headless. If you ever need that, the refactor is: make edCtrls[ck].Value := v into a call to a _Put(ck, v) function, and let the caller supply it. Note the shape of the seam — a minimal duck type — because chapter 9 shows the same trick being used deliberately.

FillTab(lines, mNo) — the entry point

Everything happens in one function, in five stages.

Stage 1 — strip comments

cleaned := []
for _, rawLn in lines {
    if RegExMatch(Trim(rawLn), "^--(\s|$)")
        continue
    cleaned.Push(rawLn)
}
lines := cleaned

A line that is -- alone, or begins with -- followed by whitespace, is a comment.

Two subtleties in that one regex:

  • --- (a multiline fence) is not a comment — its third character is not whitespace, so ^--(\s|$) does not match.
  • --word is not a comment either. It used to be a branch marker; it is not any more (::word is), but it is still left alone rather than swallowed, because "masses in the wild contain lines like '--sale ends tonight', and eating those would delete message text on a rule the person pasting never agreed to."

Stage 2 — the bare !mma header block

This runs first, before the mode is chosen, and the reason is a good lesson in parser design.

!mma:

If you were my artist, how would you picture me? 🎨

Would my curves take over the entire canvas...
Or would you only sketch the parts you couldn't stop thinking about? :3

Would your artwork be bold enough to leave people speechless? ♡

That is one message — paragraph breaks and all. Every other form puts the mass on the marker line, so a marker with nothing after it set the mass to "" and left the paragraphs to positional mode, which read them as f1, f2 and f3 and dropped the fourth. The mass went out in pieces, as follow-ups, or not at all.

MassHeaderBlock(lines) finds a line matching i)^!?mm[a]?\s*:?\s*$ — a marker with nothing after it — and takes everything below it until the first of:

a --- fenceeaten with the block. Write one when follow-ups come after, since positional follow-ups have no label to stop the block themselves.
a labelled linea field name, an f-prefix, ppv, or a ::branch. That line names its own field and is left for the rest of the parse.
the end of the paste

It returns {text, rest} — the block, and the paste with the header and block removed, for the ordinary modes to carry on with.

CONCEPT-ENCOUNTERED

Take prose out of the way before you classify

The comment explains the ordering:

"Done FIRST, before the mode is chosen, because the mass body is prose: a paragraph of it that happens to open with a word the keyword mode knows would otherwise pick the mode for the whole paste."

A mass that opened "f2 or f3 of these outfits, which would you pick?" would trip the keyword detector and change how the entire rest of the paste was read. Removing the free-text region first means the mode detectors only see text that is structural.

This is a general parsing principle: lex the unambiguous regions out first, then classify what remains.

Stage 3 — reset the branch registry

NewBranchReg(mNo) {
    Loop MASS_BRANCH_MAX
        for _, f in MASS_BranchFields(A_Index)
            if edCtrls.Has("m" mNo "_" f)
                edCtrls["m" mNo "_" f].Value := ""
    return {order: [], idx: Map()}
}
The clear is not optional

Parsing writes into boxes that are already on screen. A mass with no ::mexican in it must not inherit the last mass's mexican branch — "which is precisely how a wording gets sent for a model it was never written for."

The registry is {order: [name, …], idx: Map(lowername → slot)}. It assigns branch names to slots 1–6 on first sight, and matches case-insensitively — because ::Mexican and ::mexican in one mass are a typo, not two branches, and two branches is the answer that costs a slot and splits one wording across two rows of the picker.

Stage 4 — choose the mode

        hasKw := true
        break
    }
}
if hasKw { … keyword mode …; return }

hasFPrefix := false

; …otherwise, positional mode…

Note the !RegExMatch(m[1], "i)^!?mm[a]?$"): the mass markers are in keyMap, so without that exclusion every paste starting !mma something would be classified as keyword mode.

Stage 5 — parse in that mode

Keyword mode

Simplest. Each line's first word is looked up in keyMap; the rest of the line is the value.

isLab := RegExMatch(t, "^(\S+)\s*(.*)", &m) && keyMap.Has(StrLower(m[1]))
if BranchLine(brReg, t, curGrp, mNo, &curBr, isLab)
    continue
if isLab {
    kw  := StrLower(m[1])
    ck  := "m" mNo "_" keyMap[kw]
    if edCtrls.Has(ck)
        edCtrls[ck].Value := Trim(m[2])
    curGrp := BranchGroupOf(keyMap[kw])
}

Prefix mode

Each line's f/fu + number routes it to an exact slot. FPrefixToSlot does the mapping and is worth reading for what it rejects:

FPrefixToSlot(s) {
    if !RegExMatch(s, "i)^[Ff][Uu]?\s?(\d+)(?:\.(\d+))?[:\s]", &m)
        return ""
    n := m[1], d := m[2]
    if d = ""                       return "fu" n
    if SubStr(d, 1, 1) = "5"        return "fu" n "_5"
    if SubStr(d, 1, 1) = "7"        return "fu" n "_7"
    return ""                       ; f1.2 → nothing. Silently dropped.
}

Blank-group boundaries are irrelevant in this mode, which is why it is the format to reach for when a mass is complicated.

Positional mode

The default, and the most work. Blank lines separate groups; groups are taken in order.

PositionalGroups — splitting on blank lines, with fences

Returns {groups, fenced}: an array of line-arrays, plus a Map marking which groups came from a --- fence.

The fence logic is the fiddly part. When a --- is found, the code walks backwards to the most recent line starting with ppv (or to the start of the positional content), pops any groups it had already emitted from that point, and re-emits the whole span as one group with its internal blank lines preserved. That group is routed to ppv_base and never spills a line into a ppv follow-up — a multiline PPV, not a PPV plus a follow-up.

The ::name marker — one syntax for every alternative

follow up 1
::alt folow up 1 alternative
::mexican mehico
::german germaniaaaaa
::german gernabiaaa22222

Four rules, and each one has a story:

1. A branch keeps its identity by NAME across the whole mass

The ::mexican under follow-up 2 is the same branch as the one under follow-up 1. That is what makes picking it at f1 commit you to it at f2 and f3.

2. Repeating a name inside one group adds the next PART, not another choice

::german twice is one branch answering f1 with two messages (f1 then f1.5), exactly as two unmarked lines are the trunk's f1 and f1.5. Capped at MASS_FU_PARTS, since there are only three sub-slots to send them into.

3. A marker ALONE on its line owns the lines under it

::tits Would you mind if I smothered you with them?

; …means the same as…

::tits
Would you mind if I smothered you with them?
The bug this fixed

The second form did not parse. ::tits with nothing after it was read as "this branch has nothing to say here" — a no-op — and the sentence under it fell through to the trunk. So the branch was empty and the trunk's follow-up silently became one branch's wording.

Sent to a real fan, that is the wrong message with no error anywhere.

And it matters because the second form is how a person actually writes a mass: the wording is a sentence, not a label's argument.

4. A group that OPENS with a marker is not a new follow-up

And tell me.. which curve entices you the most      <- f2

::tits                                             <- f3, if tits
would you mind if I smothered you with them?

::ass                                              <- f3, if ass
I want to make you my personal throne

Counted as ordinary groups, those are follow-ups 3 and 4 — and there is no fourth, so the whole ::ass block was dropped with only a line in the log to show for it.

isBrLed := BranchMarker(firstLine) ? true : false
if !(isBrLed && prevBrLed)
    fIdx++
prevBrLed := isBrLed

Consecutive branch-led groups share one index: they are choices at the same step, not successive messages. The first one still advances the index, because it is the next follow-up — one the trunk has no wording for, which is normal and already supported.

BranchLine — the one rule, shared by all three modes

BranchLine(reg, t, grp, mNo, &curBr, labelled := false) {
    mk := BranchMarker(t)
    if mk {
        if (grp = "") {
            LOGW("gui.parse", "model " mNo ": '::" mk.name "' appears before any"
                            . " follow-up or ppv line, so there is nothing for it to"
                            . " be an alternative TO — dropped")
            curBr := ""
            return true
        }
        if (mk.body != "") {
            AddBranchPart(reg, mk.name, grp, mk.body, mNo)
            curBr := ""              ; wording was on the line; owns nothing below
        } else {
            curBr := mk.name         ; the lines under it are its answer
        }
        return true
    }
    if labelled {
        curBr := ""                  ; a labelled line ENDS a capture
        return false
    }
    if (curBr != "" && grp != "") {
        AddBranchPart(reg, curBr, grp, t, mNo)
        return true
    }
    return false                     ; the trunk's — caller places it
}

Three things to take from this function:

curBr is passed by reference so all three parse modes share one rule instead of three copies of it. This is the shape to reach for when several call sites need to advance the same piece of state.

The return value is "did I consume this line?" — true means the caller skips it, false means it is the trunk's and the caller should place it in the next sub-slot. Clean separation: this function knows about branches, the callers know about slots.

labelled ends a capture. Without it, one ::tits above an f2 line ate the rest of the paste — every following line, labels and all, went into the branch and every field below it came out empty. So a line carrying its own f2 or ppv label belongs to that label, never to a capture.

Limits are reported, never silently truncated

Four places in this file hit a ceiling, and all four log a LOGW that names what was dropped and why:

LimitMessage
7th branch name"…names more than 6 branches — 'x' was DROPPED. Everything it said is missing from this mass."
4th part in a branch group"…already has 3 parts for fu2 — 'text' was dropped, there is no fourth sub-slot to send it in"
4th follow-up group"…more than three follow-up groups — group 4 was dropped, MMA sends f1, f2 and f3 only"
4th line in a group"…follow-up 2 has more than 3 lines — 'text' was dropped. There are three sub-slots (f2, f2.5, f2.7) and no fourth."

Every message names the limit, the thing dropped (truncated to 30 characters so the line stays readable) and the reason the limit exists. That is the standard to hold new code to: a limit that silently truncates is a limit that produces a mass nobody wrote.

StripPrefix, and the URL exception

StripPrefix(s) {
    if RegExMatch(s, "i)^[Ff][Uu]?\s?\d+(?:\.\d+)?[:\s]+", &m)
        return SubStr(s, m.Len + 1)
    if RegExMatch(s, "^\S+:(?![)(])\s*", &m) {
        scheme := SubStr(s, 1, InStr(s, ":") - 1)
        if PREFIX_EXCEPTIONS.Has(StrLower(scheme))
            return s                        ; leave the URL intact
        return SubStr(s, m.Len + 1)
    }
    return s
}

The second branch removes any word: prefix — people write Opener:, Follow up: and so on. Two guards keep it from eating real text:

  • PREFIX_EXCEPTIONS — https://… would otherwise become //….
  • (?![)(]) — a negative lookahead so that an emoticon like :3 or :) at the start of a line is not read as a prefix terminator.

The serialiser half

EscQ(s) {
    for _, ch in AHK_CHARS          ; ["``", Chr(34), ";"] — backtick FIRST
        s := StrReplace(s, ch, "``" ch)
    return s
}

Backtick must be first in that list, or escaping a quote would then have its own escape backtick escaped again. Classic escaping-order bug.

These are vestigial: they exist because masses used to be AHK source (chapter 5). Nothing on the save path needs them any more — MASS_Save writes JSON — but the export button still produces text a human pastes back, so they stay.

What was deleted, and why the note remains

At the bottom of the file:

SplitAltLines() stood here: it pulled alt: / alt0: lines out of a follow-up group and returned {baseParts, alts}, with an insertion sort to compact a stray alt5: down to a dense list. All of it existed to reconcile a second syntax for a thing that is now spelled one way. The group loop reads marked and unmarked lines in a single pass, so there is nothing to split.

CONCEPT-ENCOUNTERED

Tombstone comments

MMA leaves a note where a deleted thing used to be, several times over — here, in hotkeys.ahk where HK_ModelSendIds was, in active_model.ahk where UniversalSendActive was, in utils.ahk where AltChooseGui was.

The value is specific: when you are reading code and something you expected is absent, the question "where did this go, and was it deleted on purpose?" costs real time to answer from git history — and git history does not tell you why. A three-line note at the site is cheaper than the archaeology.

The discipline is to delete them once nobody would look. In practice, keep one where the removed thing was documented elsewhere or named in a test.

Working on this file

Before you change anything here

This is the one file in the core where a bug produces a plausible wrong result rather than nothing at all. A parse that puts f2's text into f3 does not look broken — it looks like a mass. It goes out.

Test with tools/test/branch_parse_test.ahk (512 lines of assertions) before and after. If you change a mode-detection heuristic, hand-check at least one real mass in each of the three modes, plus one with a bare !mma header, plus one with branches.
