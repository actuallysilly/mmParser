Chapter 2

The shape of MMA

Eight to a dozen processes that never call each other. What each one is, how they find each other, how they cooperate, and exactly what happens between double-clicking MMA.ahk and having a working keyboard.

Why it is not one program

The obvious design is one AHK script: the window, the hotkeys, the detector, all in one process. MMA is not that, for reasons that are worth understanding before you read a line of the code, because almost every unusual thing in this codebase follows from it.

Reason one: a GUI blocks

An AHK script runs one pseudo-thread at a time. While the GUI is showing a modal MsgBox, that process is not answering hotkeys. Put the mass hotkeys in the GUI's process and every dialog freezes your ability to send. Worse, the WebView shell carries a full Edge runtime; CreateControllerAsync was measured at 60.8 seconds from launch to ready on a cold start. A minute of MMA visibly running with every key dead.

Reason two: a crash should be survivable

If the detector throws, you want the detector to die — not the mass engine. Separate processes give you that for free. It is also what makes the watchdog possible: something has to be alive to notice something else died.

Reason three: some parts must be reloadable and some must not

You edit masses constantly. You do not want to restart the thing holding your hotkeys every time. Because they are separate processes sharing a file, the GUI can rewrite the whole mass library and the engine picks it up on the next keypress.

CONCEPT-ENCOUNTERED

Shared-nothing processes, coordinated by files and nudges

The architecture in one sentence: a file says what the data is; a window message says go and re-read it.

The message is never the data. It cannot be — a Windows message carries two integers and no string. So the design that constraint forces turns out to be the right one anyway: there is one authoritative copy of every piece of state, on disk, and no process ever has to reconcile its in-memory copy with anyone else's.

The alternative — one process holding everything in globals — is faster and would have made half this codebase unnecessary. It would also mean that "the GUI is busy" and "the hotkeys are dead" are the same sentence.

Opened on a key, then gone

The Hotstrings window, the Hotkeys editor, Settings (WebView), the branch builder, the activity chart, the recorder, the updater. Each is its own process. The three WebView windows each carry an Edge runtime, which is exactly why they must be separate — the main window must never block waiting for one to open.

That last point creates two of the ten window messages. A separate process cannot call into the main window's globals, so MMA_MSG_OPEN_SETTINGS and MMA_MSG_ADD_HOTKEY exist for a window to ask the window that owns those globals to open a dialog on its behalf.

How processes find each other

CONCEPT-ENCOUNTERED

Identity by window title

Every AHK script has a hidden main window titled with its full file path. MMA uses that as process identity throughout:

_EngineTitle() {
    return MMA_SRC "\mass\engine.ahk ahk_class AutoHotkey"
}
EngineRunning() {
    prev := A_DetectHiddenWindows
    DetectHiddenWindows true
    up := WinExist(_EngineTitle()) ? true : false
    DetectHiddenWindows prev
    return up
}

"Is the engine running?" is one WinExist. "Stop it" is ProcessClose(WinGetPID(title)). "Which windows are ours?" is: enumerate every window of class AutoHotkey and keep the ones whose title starts with the repo root.

That last one is HK_Broadcast, and it replaced a hard-coded list of filenames that had gone stale in both directions — it still named a deleted script and had never gained sequences.ahk, so rebinding the Discord import key did not apply live.

Why MMA.ahk uses Run and not #Include

The launcher at the repo root could simply #Include the GUI. It does not, and its header explains why: including would run the GUI under the title MMA.ahk, and three mechanisms that address the GUI by its real path would quietly stop matching — HK_Broadcast, processes.ahk, and the auto-parse post from sequences.ahk. Run keeps one canonical identity.

CONCEPT-ENCOUNTERED

Named events — identity for a process with no window

The Python services have no AutoHotkey window, so the title trick cannot find them. Each signs its presence with a named kernel event:

SVC_OpenEvent(id) {
    static EVENT_MODIFY_STATE := 0x0002
    return DllCall("OpenEventW", "UInt", EVENT_MODIFY_STATE, "Int", false,
                   "Str", SVC_META[id].event, "Ptr")
}

Opening the event answers "is it up?" in one call. Setting it means "please exit". The alternative — shelling out to python service.py --status — would spawn a whole Python interpreter every watchdog tick, every five seconds.

This is also why the Python children cannot ride on the startup-scripts list and are not closed by KillAllScripts: neither mechanism can see them.

The HK_MSG_FIRE trick is worth understanding

A message carries only numbers. So how does the Actions menu, running in the GUI's process, fire an action owned by the engine?

It sends an index into HK_ORDER — the array of declared hotkey ids, built by HK_Def calls at load time. Every process loads the same hotkeys.ahk, so index 47 means the same action everywhere. The message goes to every MMA script; only the one that actually bound that id answers, and the rest ignore it.

That works only if every process agrees on the numbering, which is why the dynamically declared hotstring ids are appended after every static one, and sorted. A process started before you bound a hotstring has a shorter HK_ORDER, but indices 1..static still mean the same thing in both, and a stale process handed an index in the dynamic tail finds it out of range and ignores it.

CONCEPT-ENCOUNTERED

Broadcast with a delivery receipt

HK_Broadcast counts how many windows it actually reached, and logs a warning when the answer is zero:

if sent
    LOGI("hk.broadcast", "msg " Format("0x{:X}", msg) " → " sent " of " seen ...)
else
    LOGW("hk.broadcast", "... reached NOBODY ... Whatever this was meant to apply"
                       . " live has not applied.")

This is a small thing that pays for itself constantly. "A save that does not apply live", "a rebind that does not take", "an Actions-menu entry that fires nothing" all look identical from the outside and look identical to a message that was never sent. The recipient count is the fastest way to tell them apart.

Why debuglogs\ is not inside userdata\. Diagnostics are throwaway — you read one, fix the thing, delete it. Mixing them into userdata\ put them next to masses.json and hotkeys.ini, the two files you must never delete by mistake. That separation is load-bearing.

Gitignore subtlety worth knowing

.gitignore contains userdata/*, not userdata/. Git never descends into an excluded directory, so excluding the directory and then negating one file inside it does nothing — the negation is dead, and hotkeys.default.ini would silently stop being tracked. Nobody would notice until a fresh clone had no keys to seed from.

The boot sequence, in order

This is worth tracing once, because "MMA is running but X does not work" is nearly always a boot-order question.

1. MMA.ahk — the launcher, ~20 lines of real work

  • Includes src\core\paths.ahk, which is the whole of its knowledge.
  • Checks the Win32 shell file exists; if not, a message box and exit. (That file's absence means a broken install; a missing WebView shell only means the preference falls back.)
  • Runs a one-time migration that lifts installs from the old legacy default onto the WebView shell, guarded by a marker key so it never runs twice.
  • Runs MMA_ShellPath() and exits. The launcher does not stay alive.

2. The shell starts and immediately calls CORE_BootEarly()

CORE_BootEarly() {
    LaunchEngine()
    LaunchSequences()
}

Before it builds anything. The comment above it is one of the more instructive in the repo: everything a shell does between here and showing its window is construction — tabs, the archive, the settings pages, or, for the WebView, standing up Edge. That is hundreds of milliseconds (or a minute) during which MMA is on screen with every hotkey it owns dead. Ctrl+clicking a Discord message in that gap does nothing, which is indistinguishable from the import being broken — and it is exactly when you would do it.

3. The shell reads its settings, then calls CORE_BootServices()

CORE_BootServices() {
    LaunchStartupScripts()   ; general.ahk, the account files
    SVC_LaunchEnabled()      ; every declared service whose FEAT is on
}

Still before drawing. Same rule: nothing a user reaches for waits on a window.

4. The shell builds and shows its window

5. CORE_BootWindowTasks() — the parts that genuinely need a window

  • SetTimer(RefreshToolsLabel, -800) — after Python has had time to claim its events.
  • SetTimer(WatchdogTick, 5000) if auto-restart is on.
  • SetTimer(CheckUnmappedModel, 4000) if the detector is on — this opens a dialog, so it must live in a process that has a window. Note it cannot live in ActiveModelStatus, which is read from a hotkey context on every keystroke; a dialog there would be one popup per character.

6. Meanwhile, in the engine's own process

#Include "runtime.ahk"          ; loads MASS_DOC, reads 8 settings, registers __1mm…
OnMessage(MMA_MSG_MASSES_CHANGED, ReloadMasses)
Loop MASS_MODELS
    MassBindModel(A_Index)      ; [mass.1] [mass.2] …
MassBindActive()                ; [mass.active]
MassBindSelect()                ; [mass.select]
NavBind()                       ; [nav] [chat] [util]
LOCKBADGE_Sync()
SetTimer(LOCKBADGE_Sync, 700)
MARKS_Start()
HK_OnSend(CW_Arm, CW_Release)   ; the click wall
HK_Summary("mass engine")       ; ← the line that answers "are the keys alive at all?"

Read that last line's purpose. Every individual bind logs itself, but a hundred per-key lines never answer the question a user is actually asking. HK_Summary prints "N key(s) live, M bound but unassigned". If N is 0, the cause is upstream of anything in the engine — Easy mode, the Features tab, or a hotkeys.ini that never arrived.

The watchdog

WatchdogTick() {
    if !FEAT("startupScripts")
        return                       ; Easy mode runs no children

    down := ""
    if !EngineRunning()    down .= "engine "
    if !SequencesRunning() down .= "sequences "
    if (down != "")
        LOGW("proc.watchdog", "found down, restarting: " Trim(down))
    else
        LOG_Heartbeat("proc.watchdog", "alive; engine and sequences both up")

    LaunchEngine()
    LaunchSequences()
    LaunchStartupScripts()
    SVC_LaunchEnabled()
    RefreshToolsLabel()
}

Every five seconds. The down sampling before the launches exists for one reason: LaunchEngine already logs "starting the mass engine", but on the first tick that is normal and on the twentieth it means the engine is crash-looping and every mass key is dying with it every five seconds. Sampling first is what makes those two distinguishable in the log.

CONCEPT-ENCOUNTERED

Idempotence — the property that makes a watchdog cheap

Every Launch* function checks "is it already running?" and returns if so. That makes calling them harmless, which in turn means the watchdog does not need to know what changed — it just re-asserts the desired state every five seconds and lets the checks sort it out.

An operation you can safely repeat is called idempotent. It is worth noticing how much of MMA is built this way: DirCreate on the debuglogs folder, HK_MergeDefaults (present keys are never touched), MASS_Normalise (run on the way in and the way out), SVC_Sync. Idempotent operations turn "did this already happen?" from a question you must track into a question you never have to ask.

The two children that are not services

The mass engine and sequences.ahk are launched by hand-written code, not by the service registry, and they have no feature switch at all. That is deliberate, and both were learned the hard way.

The engine was a startup script. SaveCfg rebuilds the startup list from checkboxes, so one visit to Settings while engine.ahk was missing from that list wrote it straight out of the config, and every mass hotkey went dead with no error.

sequences.ahk had it worse: it was reachable only through the startup list, so every fresh install had the Discord import dead on arrival (a new cfg has no StartupScripts key), and one untick killed it. It also had a FEAT_Def, which made Easy mode a silent killer — Easy switches off everything in the registry, so the import died there with no box to find.

The rule that came out of it: a script that owns hotkeys should not be a checkbox.

Notice what is not in that picture: any arrow that is a function call between boxes. There are none. Every connection is a file or a numbered message.

What this means when you make a change

  • Changing a setting's effect usually means changing the code that reads it, not the code that writes it — because it is read per use.
  • Adding cross-process state means adding a file or an ini key, not a global. There is no global that two processes can share.
  • "It works when I restart" is a symptom, not a fix. It means something is cached that should be re-read, or a message that should be broadcast is not being.
  • A message with no listener is silent. Check the hk.broadcast log line before assuming the receiving code is wrong.
  • If you move a file, three things break silently: the recorder writes code into sequences.ahk and hotkeys.ahk by path, the main window scrapes utils.ahk as text, and sequences.ahk builds a WinTitle from the main window's path. All three path constants sit together at the bottom of paths.ahk for exactly that reason.
