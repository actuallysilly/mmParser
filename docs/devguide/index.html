MMA developer guide

Learn this repo well enough to change it

This guide exists so you can open a file in src\, read it, know why every line is there, and change it without breaking three things you did not know were connected. It assumes you know no AutoHotkey and no more than the surface of this codebase. It does not assume you are stupid — it assumes you were never told.

How this is different from the docs already in the repo. ARCHITECTURE.md tells you what the tree is. docs/decisions.md tells you why it is shaped that way. This guide teaches you how to read and write the code — the language, the patterns, the traps, and the actual control flow from a key being pressed to a message landing in a chat. Read all three eventually. Read this one first.

The one thing to understand before anything else

MMA is not one program. It is up to a dozen small independent processes that never call each other's functions. They cooperate through two things only:

  • Shared files in userdata\ say what the data is.
  • Window messages declared in src\core\messages.ahk say go and re-read it.

That single fact explains most of what looks strange in this repo. It is why settings are read from an ini on every keypress instead of held in a variable; why saving in the GUI applies instantly in the engine with no restart; why a "list of running scripts" is really a list of window titles; and why so many comments in the source are about failures that produce nothing at all rather than an error. Separate processes cannot throw an exception into each other. They can only fall silent.

Almost every bug this codebase has ever had is that silence. Learning MMA is largely learning where the silence can come from, and the code is written — sometimes at extraordinary length in comments — to make each source of silence audible in a log file.

The CORE selection

You asked for a selection of files that count as core — the mass/send/detect/parse/organise spine, no add-ons, no Python. This is it. 19 files, about 7,600 lines. Everything else in the repo (another ~35,000 lines) is windows, tools, tests, optional services and vendored third-party code, and none of it is load-bearing for the thing MMA actually does.

If you have one hour

  1. Read chapter 1 to the end of "Closures and the loop-variable trap". Skim the rest.
  2. Read chapter 2 in full. It is short and it is the mental model.
  3. Open src\mass\runtime.ahk and read _DoFuGroup with chapter 7 open beside it.
  4. Set MMA_DEBUG=max in your environment, launch MMA, press a follow-up key, and read debuglogs\mma.log. Everything in this guide is visible in that file.

How to actually learn a codebase (the meta-point)

You said the goal is to stop band-aiding and start developing. The difference is not knowledge of syntax — it is having a model of the system that lets you predict what a change will do before you make it. Three habits get you there faster than reading more code:

1. Follow one thing end to end, repeatedly. Do not read files. Read paths. Pick "I press F1" and follow it through every function until a message is in a chat box. Then pick "I click Save". Then "the detector notices a tab change". Each trace takes an hour and teaches you more than a day of browsing, because you learn the joints — where one subsystem hands off to another — and joints are where bugs live.

2. Read the comments as bug reports. This repo's comments are unusual: most of them describe a failure that already happened. When a comment says "this used to X, which meant Y", that is not history — it is a constraint. If you change that line back, you get Y back. Chapter 12 collects the worst of them.

3. Change one thing and watch the log. The logging in this codebase is good enough to be a teaching tool. Turn on max logging, do something, read the timeline. You will see hk.fire, then mass.fu, then send.fu, then send.snd — the exact call chain, with the decisions it made, in order.
