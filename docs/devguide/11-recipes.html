Chapter 11

Recipes and debugging

How to make each kind of change, what it touches, and — the part that turns you into someone who can maintain this alone — how to find out why nothing happened.

Part one — recipes

Add a field to a mass

MASS_Fields() {
    out := ["mass", "fu1", …, "ppv_f3", "my_new_field"]   ; ← here
    …
}

That is the whole storage change. The loader, the writer, the blank-record builder, the migration, ApplyFile's save loop and FillTabFromSlot's load loop all read that one list.

Then, if you want to see and send it:

  1. An edit box in each shell — edCtrls["m" n "_my_new_field"].
  2. A parser route — a keyMap entry (both shells) for keyword mode; positional/prefix modes need explicit handling.
  3. A send path — a handler in runtime.ahk, an entry in MassSlotHandlers(), an HK_Def, a default key.
  4. If it holds several messages, MASS_FieldIsMultiline and read it back with MASS_SplitParts.

Add a hotkey

; 1. core/hotkeys.ahk — declare it
HK_Def("nav.myThing", "Do my thing", , "engine.ahk")

; 2. userdata/hotkeys.default.ini — give it a default
[nav]
myThing = ^!k

; 3. the owning script — bind behaviour
HK_Bind("nav.myThing", MyThing)
Four things to get right
  • The id must match the ini exactly. nav.myThing → [nav] myThing. Split at the last dot.
  • Bind it in the process that owns it. HK_Bind in the wrong process registers a key that runs the wrong thing, or nothing.
  • If it needs a context, register the context first. HK_Context("name", (*) => …) before HK_Bind, or the bind refuses.
  • Existing installs need HK_MergeDefaults to pick it up — which runs automatically at HK_Init, so adding it to hotkeys.default.ini is enough.

No bare F-keys. F1–F12 and Escape are already spoken for by the mass sections, and any key you pick fires globally while Infloww is focused. Prefer a ^! chord.

Add an optional feature

; 1. core/modes.ahk
FEAT_Def("myThing", "MyThing", "My thing (does the thing)", "1", "Tools")

; 2. guard its entry points
if !FEAT("myThing") {
    LOG_Bail("mything", "feature 'myThing' is off — nothing done")
    return
}

; 3. if it has keys, one line in FEAT_HOTKEY_MAP
"myThing.",  "myThing",

The Features tab draws itself from the registry, so there is no checkbox to add.

Choosing the default: the pattern in this repo is that anything which watches you, types on your behalf, or needs calibration to be useful ships off. Everything else ships on. Read the FEAT_Def comments in modes.ahk — several of them argue the case explicitly, and they are a good model for writing your own.

Add a background service

; 1. core/modes.ahk
FEAT_Def("myService", "MyService", "My service", "0", "Background")

; 2. core/processes.ahk
SVC_Def("myService", "ahk", MMA_SRC "\screen\my_service.ahk",
        "proc.myservice", "my service")

; 3. write src/screen/my_service.ahk

That is the whole change. Boot, the Features tab, the Tools window, the Tools button's count and the watchdog all walk SVC_ORDER.

The service file itself needs:

#Requires AutoHotkey v2.0
#Include "../core/paths.ahk"
#SingleInstance Force

; …read config with LOG_IniInt, never Integer(IniRead(…))…
; …initialise EVERY global BEFORE the first tick…

LOG_Kv("myservice.boot", Map(...))    ; what it resolved, since it has no window
Tick()
SetTimer(Tick, PollMs)                ; ← the timer is also what keeps it alive

Remember: OnMessage alone does not keep a v2 script alive. It needs a hotkey, a timer, a visible GUI, or Persistent.

Add a window message

; core/messages.ahk — in the right block, with a comment saying who sends it
global MMA_MSG_MY_THING := 0x8014

; receiver
OnMessage(MMA_MSG_MY_THING, MyHandler)

; sender
HK_Broadcast(MMA_MSG_MY_THING)                    ; to every MMA script
PostMessage(MMA_MSG_MY_THING, 0, 0, , MMA_GuiWin())  ; to one window

Use the name at both ends. Never a literal, and never arithmetic on one unless you also write the pair of helper functions like MMA_MSG_EditableFu does.

Remember the payload limit: two integers, no strings. If you need to send data, write it to a file and let the message be the nudge.

Add a self-test

Every file in tools/test/ asserts and exits: it prints N passed, M failed to stdout, returns 0 or 1, binds no keys and leaves no window. That is the entire entry requirement, and it is why they can run from Settings ▸ Debug ▸ Run all in the middle of a shift.

; then add it to the list, or it will only ever run by hand:
; src/ui/debug_panel.ahk
static TESTS := [
    {label: "logging",       file: "tools\test\log_test.ahk"},
    …
    {label: "my thing",      file: "tools\test\my_thing_test.ahk"},
]
The #Warn trap, which looks exactly like a slow pass

#Warn VarUnset is on by default in v2, fires at LOAD, and a warning is a modal dialog even under /ErrorStdOut.

So a test that includes a library expecting globals from its includer — processes.ahk reads SCRIPT_DIR and startupScripts, which only the main window assigns — hangs forever with no output, which reads as the test passing slowly rather than as a failure.

services_test.ahk sets #Warn VarUnset, StdOut and then assigns both globals itself, so the contract is stated rather than muted. Prefer VarUnset over All: All also prints the tree's ~80 "local has the same name as a global" lines and buries the real output.

Running one by hand

$ahk = "C:\Program Files\AutoHotkey\v2\AutoHotkey64.exe"
$psi = New-Object System.Diagnostics.ProcessStartInfo
$psi.FileName = $ahk; $psi.UseShellExecute = $false; $psi.RedirectStandardOutput = $true
$psi.Arguments = '/ErrorStdOut "' + (Resolve-Path .\log_test.ahk) + '"'
$p = [System.Diagnostics.Process]::Start($psi)
$p.StandardOutput.ReadToEnd(); $p.WaitForExit(); $p.ExitCode

Start-Process -RedirectStandardOutput does not capture /ErrorStdOut — the text lands on the parent console and the log file comes back empty, which reads as every test passing.

Some tests write real settings. mass_bind_test, position_test, active_model_test and hotstring_key_test each snapshot and restore what they touch — but a crash mid-run leaves your detector configured however the test left it. tools/test/README.md lists which.

Move a file

  1. Update its #Include lines (relative to the file, not the script).
  2. Update every #Include that names it.
  3. Check the source-as-path block at the bottom of paths.ahk — three things reference source as paths rather than including it, and all three break silently.
  4. If it can be a startup script, check MMA_ScriptPath's folder list.
  5. If it is a service, update its SVC_Def path.
  6. Search for its bare filename in the whole repo, including .md and .ps1.

Syntax-check without running

MSYS_NO_PATHCONV=1 "/c/Program Files/AutoHotkey/v2/AutoHotkey64.exe" /validate "path\file.ahk"

Two traps: AHK is a GUI-subsystem executable so it detaches immediately — from PowerShell use Start-Process -Wait to get the exit code. And under Git Bash, MSYS rewrites /validate into a path unless you set MSYS_NO_PATHCONV=1.

/validate is a parser, not a linter. It will not catch a closure reading a loop variable, a string compared with <, a missing Map key, or a variable and a function whose names differ only by case.

Part two — the debugging playbook

Step 0, always: turn on the log

set MMA_DEBUG=max

…then launch MMA from that shell, reproduce, and open debuglogs\mma.log. Or Settings ▸ Debug and tick Logging + Max logging + Popups.

Use "Mark log" before and after a reproduction to bracket it. That writes a MARK line you can search for.

The one question that splits the search in half

Did the code run at all?

  • There is a DEVL … entered line → the handler ran, and the cause is below it. Read on to the first BAIL.
  • There is no line at all → the handler never ran, and the cause is upstream: the key never bound, a guard dropped the press, the feature is off, or the process is not running.

Everything else follows from that split.

When the log says nothing at all

That is itself a diagnosis. In order of likelihood:

  1. The process is not running. Check the Tools button count, or WinGetList("ahk_class AutoHotkey") with hidden windows on.
  2. The script failed to load. AHK exits with code 0 and no message for several classes of error — a name collision differing only by case, a base property, a top-level Integer() on a bad ini value. Bisect with FileAppend at the top of the file, or run it directly and watch.
  3. A #Warn dialog is up behind something. A warning is modal, and from the outside a modal you cannot see is indistinguishable from a hang.
  4. Logging is off and the failure is not a LOGE (which writes regardless).
CONCEPT-ENCOUNTERED

Bisecting a silent load failure

When a script exits 0 with no output, you cannot ask it what happened — you have to find where it stopped. Put an unconditional write near the top and move it down:

FileAppend("reached line 40`n", "D:\bisect.txt")

FileAppend, not MsgBox — a message box in a load-time failure can itself be part of the problem, and it blocks. Not LOGI either, because the logger may be the thing that failed to load.

Halve the interval each time. Five or six moves finds any line in a thousand.

The probes

tools/*_probe.ahk — the opposite of a test. A probe binds a key, stays resident, and exists so you can look at your own screen through it.

Never drive a real key capture from a probe

Probes run while Infloww is focused, and hotkeys fire globally. A probe that simulates a keypress to test something can send a real message. Read; do not act.

Part three — the house style

These are the rules the codebase already follows. Following them is what makes your changes look like they belong, and — more usefully — what stops you reintroducing bugs that were already fixed.

Naming

  • A folder's name is the global prefix its functions use. HK_, MASS_, FEAT_, PILL_, SVC_, MMA_, NFU_, CW_. So HSI_Build → src/hotstrings/index.ahk, with no search.
  • Drop the prefix from the filename once the folder carries it: mass/store.ahk, not mass/mass_store.ahk.
  • Name a file for what it does, never for what it contains.
  • A leading underscore means private to this file: _HK_Fire, _MassApplyMouseControl, _PickOpen.

Configuration

  • Read per use, not cached, unless it is on the typing hot path — and then cache with an explicit TTL and say why.
  • LOG_IniInt, never Integer(IniRead(…)).
  • Seed defaults into the file on first read so they are discoverable by opening it. AltStageSetting and LOG_Seed both do this.
  • Never hard-code a path. Everything comes from paths.ahk.

Logging

  • Every early return gets a LOG_Bail naming the condition and the cfg key you would change.
  • Every handler opens with a LOGD.
  • Dump resolved state at boot with LOG_Kv, especially in anything without a window.
  • Log the change, not the value, for anything that runs on a timer — see WriteActive and FEAT_SetRaw.
  • Say the consequence, not just the fact. Compare "detector off" with "Every [mass.active] shared key will do nothing; the numbered keys still work."

Failure

  • Refuse rather than guess, wherever a wrong answer sends a message.
  • Make the refusal audible when the user's eyes are elsewhere — 880 Hz for success, 300 Hz long for a refusal.
  • Show your working in a failure message. Per-tab pixel counts, the string OCR actually read, which field differs.
  • Report limits, never truncate silently.
  • Guard the action, not the check — external state is stale by the time you act on it.

Structure

  • One declaration, walked by everything. If you are writing a list that must match another list, stop.
  • A file that names a function includes the file that defines it.
  • Pure scanners, then services on top.
  • Convert at the boundary rather than compromising both sides.
  • Publish an edge, do not name the listener, when a low-level file is included everywhere and the listener is not.

Comments

The house style is unusual and worth matching: a header block explaining why the file exists, and inline comments that describe the failure a line prevents rather than what the line does. When you fix a bug here, the fix is not complete until the comment says what it was.

Part four — a suggested learning path

If you want to be able to maintain this alone, do these in order. Each is a real, small, shippable change.

#ExerciseTeaches
1Turn on max logging, press every mass key once, and annotate the log by hand — write down which function produced each line.The whole send path, and the tag vocabulary.
2Add a LOGD to a handler that has none, and watch it appear.Which process a file runs in; the edit-restart loop.
3Add a new navigation hotkey that clicks a coordinate.The hotkey registry end to end: declare, default, bind.
4Add a feature flag around an existing behaviour and toggle it in Settings.The feature registry, and FEAT_HOTKEY_MAP.
5Add a 15th trunk field to a mass, end to end: storage, box, parser keyword, send.Every layer at once. This is the real graduation exercise.
6Write a self-test for something in store.ahk and add it to DebugPanel.TESTS.The test harness and the #Warn trap.
7Recalibrate the detector for your actual window size using the probe.Pixel geometry, DPI, and why the probe shares the scanner.
8Add a background service that writes a heartbeat and nothing else.The service registry, process lifetime, and the watchdog.

And one habit above all: before changing a line that has a comment on it, read the comment to the end. In this codebase a comment on a line is usually the record of what happened last time someone changed it.
