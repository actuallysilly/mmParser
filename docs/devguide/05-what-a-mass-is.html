Chapter 5

What a mass is

Before you can follow the send path you need to know what is being sent. src/mass/store.ahk — 413 lines — is the only file in MMA that reads or writes the mass library, and it owns the record shape that eleven other files depend on.

The vocabulary

Four words, and confusing any two of them will make the rest of the codebase unreadable.

WordMeans
ModelOne of your accounts. 3 to 12 of them (MASS_MODELS). Each is a tab in the GUI and a section of hotkeys.
MassOne campaign: an opening message plus its follow-ups and PPV. Each model holds three (MASS_SLOTS) and one of them is live at a time.
SlotWhich of a model's three masses. massNo says which slot is live — that is what every hotkey sends.
BranchA named alternative wording within a mass. Up to six (MASS_BRANCH_MAX). "alt" is just the commonest branch name.

The file

{
  "schema": 1,
  "models": [                      // exactly MASS_MODELS entries, in order
    { "massNo": 1,                 // which of this model's masses is live
      "masses": [ {…}, {…}, {…} ]  // exactly MASS_SLOTS entries
    },
    …
  ]
}

One mass is a flat record of string fields. Flat is not an accident: every field is one editable box in the GUI, and keeping the storage shape equal to the editing shape is what stops a mapping layer from existing at all.

Why JSON, and not AHK source

Masses used to be AHK source code. The GUI generated m1 := { mass: "…", fu1: "…" } blocks by string-splicing, and a pair of functions called EscQ/UnescQ existed purely to make message text survive a round trip through a programming language's grammar.

The failure mode that killed it

A save that produces subtly wrong source produces a file that will not load, exits 0, and says nothing. Your entire message library, gone, with no error — the same silent death as the base-is-reserved bug.

Data files do not have syntax errors that kill a process.

CONCEPT-ENCOUNTERED

Data as data, not as code

This is one of the load-bearing design decisions in MMA and it generalises. If you find yourself generating source code to hold user data, you have coupled the integrity of your program to the shape of your data — and user data contains quotes, semicolons, backticks, emoji and newlines.

The JSON version also has a property the code version could never have: something other than AHK can read it. That is why MASS_Save writes "UTF-8-RAW" and not "UTF-8":

f := FileOpen(tmp, "w", "UTF-8-RAW")

"UTF-8" writes a byte-order mark, and a BOM is illegal at the start of JSON. Python's json.load rejects it outright and so does a browser's JSON.parse. AHK never noticed it was writing one, because FileRead(…, "UTF-8") strips a BOM on the way back in.

The record shape — MASS_Fields()

MASS_Fields() {
    out := ["mass", "fu1", "fu1_5", "fu1_7", "fu2", "fu2_5", "fu2_7",
            "fu3", "fu3_5", "fu3_7", "ppv_base", "ppv_f1", "ppv_f2", "ppv_f3"]
    Loop MASS_BRANCH_MAX
        for f in MASS_BranchFields(A_Index)
            out.Push(f)
    out.Push("altGui")
    return out
}

MASS_BranchFields(n) {
    return ["br" n "_name", "br" n "_fu1", "br" n "_fu2", "br" n "_fu3",
            "br" n "_ppv"]
}

14 trunk fields + 6 branches × 5 fields + 1 legacy = 45 fields per mass.

FieldMeaning
massThe opening message. Pasted, never sent — you review it first.
fu1 fu1_5 fu1_7Follow-up 1, in up to three parts. Three separate messages by default.
fu2 …, fu3 …The same for follow-ups 2 and 3.
ppv_baseThe PPV caption. May span lines.
ppv_f1..3Follow-ups sent after the PPV.
br<n>_nameWhat this branch is called. Displayed in the picker.
br<n>_fu1..3This branch's answer for each follow-up group. Multiline — newline-joined parts.
br<n>_ppvThis branch's PPV. Multiline.
altGuiDead. Kept because dropping a field rewrites every mass on next save.

The decimals are .5 and .7. Nothing else. f1.1, f1.2, f1.9 match no field and are silently dropped by the parser. They are only labels for "second part" and "third part"; the odd numbers are historical.

Why the field list lives here

It used to be MassBlockProps() inside the GUI, with ALT_MAX_RT and BRANCH_MAX_RT copied into utils.ahk under a comment reading "must match ALT_MAX in main_window.ahk".

Two files agreeing by hand about a record shape is a bug waiting for someone to add a field. The GUI edits the record and the engine sends it; neither owns it, so it is defined once, here.

The payoff: adding a field to a mass is one line in MASS_Fields(). The loader, the writer, the blank-record builder, the migration, the GUI's save loop and the GUI's load loop all read that one list.

The four constants

global MASS_SCHEMA     := 1
global MASS_MODELS_MAX := 12
global MASS_MODELS     := _MASS_SlotCount()   ; from [Settings] ModelCount
global MASS_SLOTS      := 3
global MASS_BRANCH_MAX := 6
global MASS_FU_PARTS   := 3

MASS_MODELS — the number that used to be 3

_MASS_SlotCount() {
    n := 3
    try n := Integer(Trim(IniRead(MMA_CFG, "Settings", "ModelCount", 3)))
    catch
        n := 3
    if (n < 3)  n := 3
    if (n > MASS_MODELS_MAX)  n := MASS_MODELS_MAX
    return n
}

This was literally := 3, and it was the one number pinning MMA to three models — everything downstream already looped over it. Two guards, both meaningful:

  • Never below 3. Every existing library on disk has three model entries and three sets of numbered hotkeys declared against them. Dropping below would orphan both.
  • Never above 12. Not timidity: each model is a row in Settings, a tab in the panel and an entry in every masses.json. A config typo of 400 should not produce a 400-tab window and a megabyte of blank records. The cap is where the GUI stops being usable, not where the data stops working.
Two readers, one setting

MMA_ModelNames() in paths.ahk reads ModelCount with the same clamp, written out again — because store.ahk includes paths.ahk, so MASS_MODELS does not exist yet when that function is defined, and paths.ahk must stand alone.

The duplication is deliberate and flagged in a comment: two readers of one setting must agree, and the failure if they drift is a model whose load/save button has no slot behind it. If you change the clamp, change both.

Alts and branches were never two things

This is the most important piece of history in the file, because half the comments in utils.ahk and parser.ahk refer to it.

A mass used to carry both:

  • fu1_alt0..2 — three other wordings of this follow-up.
  • br1..3 — a whole named alternate sequence.

Two syntaxes to write, two shapes to store, two halves of one window to edit — for one question: "which wording goes out for f<N>?"

The send path had already merged them: AltVariants() staged the trunk, then the alts, then the branches, as one list that TAB walked. What was left was storage and syntax, and both are gone now:

EVERYTHING IS A BRANCH, and "alt" is simply the default branch name.

::alt some wording is a branch called "alt". ::mexican mehico is a branch called "mexican". A branch that only answers f1 is the ordinary case, not a special one.

What a branch carries that a loose wording did not is the implication: pick a branch variant at f1 and f2/f3/ppv start on that same branch. An "alt" that answered f1 and then left you back on the trunk at f2 was never a different thing — only a branch nobody had named.

The fu<grp>_alt<n> fields are simply no longer in MASS_Fields(). They are left on disk in any existing masses.json rather than deleted — nothing reads them, and nothing destroys them, so a downgrade finds its data intact.

Multiline fields

MASS_FieldIsMultiline(field) {
    if (field = "ppv_base")
        return true
    return RegExMatch(field, "^br\d+_(fu\d|ppv)$") > 0
}

MASS_SplitParts(stored) {
    parts := []
    for _, p in StrSplit(StrReplace(StrReplace(stored, "`r`n", "`n"), "``n", "`n"), "`n")
        if Trim(p) != ""
            parts.Push(Trim(p))
    return parts
}

A branch's _fu2 field holds all of that branch's parts for follow-up 2, joined by newlines. MASS_SplitParts reads them back.

Note it handles three line separators: `r`n (Windows CRLF from a GUI edit box), `n (a real newline), and the literal two-character sequence ``n — a backtick followed by "n". That last one is the escape an ini file needs, because an ini has no other way to hold a line break. The DefaultFu3 setting uses it, which is why DefaultFu3Parts() can call MASS_SplitParts on an ini value directly.

De-duplication worth noticing

This function existed twice — AltParts() in main_window.ahk and AltPartsRT() in utils.ahk, identical character for character — because the GUI deliberately does not include utils.ahk and so had no way to reach it. The "RT" suffix existed only to stop the two names colliding.

Both files already reach store.ahk, so one copy is enough. If you ever find yourself adding a suffix to a function name to avoid a collision with an identical function, that is the signal to move it somewhere both callers can see.

MASS_Blank() — guaranteeing shape

MASS_Blank() {
    m := Map()
    for f in MASS_Fields()
        m[f] := ""
    return m
}

Four lines, and they remove .Has() guards from the entire rest of the codebase. A Map throws on a missing key (chapter 1), so without this every reader would need a guard at every use. Guarantee the shape at the boundary; assume it everywhere else.

Loading

MASS_Load() {
    if !FileExist(MMA_MASSES) {
        LOGW("mass.load", "masses.json does not exist — starting with an EMPTY"
                        . " library. Normal on a first run; on an existing install"
                        . " it means every mass is missing. Looked for " MMA_MASSES)
        return MASS_Default()
    }
    try {
        raw := FileRead(MMA_MASSES, "UTF-8")
        if (SubStr(raw, 1, 1) = Chr(0xFEFF))     ; a stray mid-stream BOM
            raw := SubStr(raw, 2)
        doc := JSON.Parse(raw)
    } catch as e {
        bak := MMA_MASSES ".broken-" FormatTime(, "yyyyMMdd-HHmmss")
        try FileCopy(MMA_MASSES, bak, true)
        LOGE("mass.load", "masses.json is not valid JSON — started with an EMPTY"
                        . " library and kept a copy of the broken file", ...)
        MsgBox "…A copy was kept at:`n" bak
             . "`n`nMMA has started with an empty library. Fix that file and "
             . "restart rather than saving over it.", "MMA", 0x10
        return MASS_Default()
    }
    doc := MASS_Normalise(doc)
    ...
}

It never throws. A missing file is a first run; a corrupt one must not take the GUI down with it. But note what it does not do: it does not silently start empty. It backs up the broken file with a timestamp and tells you, in a modal, not to save over it — because silently replacing a damaged message library with an empty one would destroy work a text editor could still have recovered.

The summary line

if LOG_On() {
    summary := ""
    Loop MASS_MODELS {
        mi := A_Index
        filled := ""
        Loop MASS_SLOTS
            if (Trim(MASS_Get(doc, mi, A_Index)["mass"]) != "")
                filled .= A_Index
        summary .= "m" mi ": live=" MASS_MassNo(doc, mi)
                 . " withText=" (filled = "" ? "none" : filled)
    }
    LOGI("mass.load", "loaded " MMA_MASSES " — " summary)
}

Producing a line like:

mass.load  loaded …\masses.json — m1: live=1 withText=1   m2: live=3 withText=12   m3: live=1 withText=none

This one line settles "the hotkeys do nothing" more often than anything else in the codebase. Read m2 above: its live slot is 3, and slots 1 and 2 have text. Every key for model 2 will correctly send slot 3, which is empty, and do nothing. That state is completely invisible from the keyboard.

Note the if LOG_On() wrapper — the summary costs a loop over every model and slot, and AHK evaluates arguments before the call, so without the guard you would pay for it even with logging off.

Saving

MASS_Save(doc) {
    doc := MASS_Normalise(doc)
    tmp := MMA_MASSES ".tmp"
    try {
        f := FileOpen(tmp, "w", "UTF-8-RAW")
        if !f
            throw Error("could not open " tmp " for writing")
        body := JSON.Stringify(doc, "  ")
        f.Write(body)
        f.Close()
        FileMove(tmp, MMA_MASSES, true)
        LOGI("mass.save", "wrote " MMA_MASSES " (" StrLen(body) " chars) via "
                        . "temp file + move")
    } catch as e {
        try FileDelete(tmp)
        LOGE("mass.save", "could not save masses.json — YOUR EDITS ARE NOT ON DISK."
                        . " The previous library is intact.", LOG_Err(e))
        MsgBox "Could not save masses.json:`n`n" e.Message, "MMA", 0x10
        return false
    }
    return true
}
CONCEPT-ENCOUNTERED

Atomic write — temp file plus move

Writing directly to masses.json means a crash, a full disk, or antivirus interference mid-write leaves you with a half-written file — which is worse than no file, because it looks like a file. And this single file is every mass the user has.

Writing to masses.json.tmp and then FileMove-ing it into place makes the swap atomic at the filesystem level. Either the new file is there complete, or the old one is still there untouched.

Note the failure path: FileDelete(tmp) to clean up, a LOGE at FAIL level (so it can raise a dialog), and a MsgBox — plus the crucial reassurance "The previous library is intact." Losing a save is the worst outcome in the app, and the user needs to know which of "your edits are gone" and "everything is gone" just happened.

MASS_Normalise — the shape guarantee

MASS_Normalise(doc) {
    if !(doc is Map)
        doc := Map()
    out := Map("schema", MASS_SCHEMA, "models", [])
    src := (doc.Has("models") && doc["models"] is Array) ? doc["models"] : []
    keep := Max(MASS_MODELS, src.Length)
    Loop keep {
        ...
        Loop MASS_SLOTS {
            rec := MASS_Blank()
            if (A_Index <= sMs.Length && sMs[A_Index] is Map) {
                for f, v in sMs[A_Index]
                    if rec.Has(f)                  ; drop keys we no longer know
                        rec[f] := String(v)
            }
            masses.Push(rec)
        }
        no := sm.Has("massNo") ? Integer(sm["massNo"]) : 1
        if (no < 1 || no > MASS_SLOTS)
            no := 1
        ...
    }
    return out
}

Run on the way in and on the way out. A hand-edited file that omits a field, a release that adds one, a truncated array — all become "present and empty" rather than a crash somewhere far away in the send path, where the first sign of trouble would be a fan receiving nothing.

Max, not MASS_MODELS 
keep := Max(MASS_MODELS, src.Length)

Now that the slot count follows a setting, a plain Loop MASS_MODELS would make "set Active models back to 3" a data-destroying action: models 4–8 would be dropped on the next normalise and written out on the next save, with no warning and no undo, taking every mass in them.

Keeping whatever the file already holds means lowering the count hides models rather than deleting them, and raising it again brings the text back.

Generalise this. Any normaliser that rebuilds a structure is a potential data shredder. Ask: what does this do to data outside the shape I am enforcing?

Note also String(v) on the way in. JSON has numbers and booleans; the record is all strings. Coercing at the boundary means no reader downstream has to think about it.

MASS_MassNo deserves a note. This was massNo := 1 written into the model's source file and rewritten by the GUI on every change — state stored as code. It is now a field in a data file, which is what it always was.

The Map/object boundary

MASS_AsObject(rec) {
    o := {}
    for k, v in rec
        o.%k% := v
    return o
}
CONCEPT-ENCOUNTERED

Converting at the boundary instead of compromising on both sides

Storage wants a Map. That is what a JSON object is, and it is what lets MASS_Normalise iterate keys generically (for f, v in sMs[i]).

The send path wants properties. Every follow-up, alt and branch helper in utils.ahk and runtime.ahk was written against m.fu1, m.%key% and m.HasOwnProp(key) — and that code is correct and working.

Rather than force one shape on both, there is a five-line converter at the seam. One shape for storage, one for sending, without either side compromising — and without touching a single line of the send logic, which is the part it would hurt most to get wrong.

Every call in the runtime goes through it:

CurMass() {
    return MASS_AsObject(MASS_Active(MASS_DOC, MASS_CUR_MODEL))
}

The "last sent" note

MASS_RememberSent(modelNo, slot, group) {
    try {
        IniWrite(modelNo, MMA_CFG, "LastSent", "Model")
        IniWrite(slot,    MMA_CFG, "LastSent", "Slot")
        IniWrite(group,   MMA_CFG, "LastSent", "Group")
        IniWrite(A_Now,   MMA_CFG, "LastSent", "When")
    } catch as e {
        LOGV("mass.sent", "could not note the last send in the cfg — the capture"
                        . " window will open on its own defaults. " LOG_Err(e))
    }
}

Three design points in nine lines, all worth copying:

  1. It lives in the cfg, not in masses.json. That file is your messages; this is a note about which one you last aimed at. It sits beside CurrentModel and LockedModel, which are the same kind of state.
  2. group is a field prefix, not a number — "fu1", "fu2", "fu3", "ppv". The same string MASS_Fields() uses, so nothing between the engine and the capture window has to map one vocabulary onto another.
  3. The whole thing is inside a try that logs at VERB. This runs on the send path, so it must never be the reason a message does not go out. A cfg that cannot be written costs a default in one dropdown, and nothing else.

MASS_LastSent() reads it back and validates every field against the shape the library actually has — a hand-edited cfg, or a model count that has come back down since, must not hand a window an index that throws when it goes to read the mass behind it.
