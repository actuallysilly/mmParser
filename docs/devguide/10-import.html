Chapter 10

Auto import

Ctrl+click a message in Discord and it becomes a parsed, saved mass on the right model's tab. Six steps, two processes, two OCR reads and a window message. This is the feature that has been reported broken most often, and never once because of its own logic.

The flow

you Ctrl+click a Discord message
   │
   ▼  the DISCORD process is in front; the key belongs to SEQUENCES.AHK
copyDiscordMessageSeq()                          sequences/sequences.ahk
   │
   ├─ 1.  Click "Right"                          open Discord's context menu
   ├─ 2.  poll for the "Copy Text" row           bitmap match, then OCR
   ├─ 3.  Click it, ClipWait                     the mass is now on the clipboard
   ├─ 4.  DiscordChannelName()                   window title, then OCR the header
   ├─ 5.  ModelFromChannel(chan)                 "aliw-staff-chat" → "aliw"
   ├─ 6.  prepend "@model: aliw" to the clipboard
   └─ 7.  PostMessage MMA_MSG_AUTOPARSE → the GUI's window
                                     │
                                     ▼  a DIFFERENT PROCESS
                       AutoParseFromClipboard()  ui/main_core.ahk
                                     │
                       ExtractModelName(&raw)    strips the @model line
                       MatchModelName(detected)  → a slot number, or 0
                                     │
                    ┌────────────────┴────────────────┐
                    ▼ known                            ▼ unknown
          tabs.Value := slot                   PromptSaveTarget(detected)
          ParseCurrent()                       (the routing dialog, which can
          ApplyFile(_mFiles[slot], true)        remember the name for next time)

Why sequences.ahk has no off switch

Read this before the code, because it is the reason the feature "broke again" repeatedly.

It was reached only through the startup-scripts list, which is a list of checkboxes. So:

  • Every fresh install had the import dead on arrival. A new mass_gui.cfg has no StartupScripts key at all, and the default when the key is absent is general.ahk alone.
  • One untick killed it — or one Save from a Settings window that happened to load before the box was ticked. Silently, with the key still listed in the Hotkeys tab.
  • It also had a FEAT_Def, which made Easy mode a fourth killer: Easy switches off everything in the registry, so the import died there with no box to find and nothing to untick.

So it now starts unconditionally, exactly like the mass engine, from CORE_BootEarly(). A script that owns hotkeys should not be a checkbox.

And the first line of the handler is a breadcrumb, for exactly this reason:

LOGD("seq.discord", "Ctrl+click import fired — right-clicking to open the menu")

"'The Discord import broke again' starts here. If this line is absent the key never reached the handler — script not running, key unbound, wrong window — which has been the cause every time so far."

Step 1–3: getting the text

Finding "Copy Text" in a menu that is not a window

Discord renders its context menu inside its own window — there is no popup window of its own — so a normal window search finds nothing. Two strategies, tried in order.

Fast path: bitmap match

CoordMode "Pixel", "Screen"
try {
    if ImageSearch(&fx, &fy, mx - b.left, my - b.up, mx + b.right, my + b.down,
                   "*20 " COPY_TEXT_IMG)
        return {sx: fx + 10, sy: fy + 10}
}

ImageSearch against assets\copy_text.png, ~10 ms, exact when it hits. *20 is a per-channel tolerance.

It is kept, and nothing depends on it: it stops hitting the moment Discord restyles or rescales its menus — which is what happened here: it missed at *20, *50 AND *100.

Robust path: read the menu

FindCopyTextRow(nearX, nearY, box := 0) {
    opts := box ? {x: box.x, y: box.y, w: box.w, h: box.h, scale: 2, mode: 4}
                : {scale: 2, mode: 4}
    try res := OCR.FromWindow("ahk_exe Discord.exe", opts)
    if !res
        return 0
    best := 0, bestDist := 0
    for w in res.Words {
        if (StrLower(w.Text) != "copy")
            continue
        a := w.BoundingRect
        for w2 in res.Words {
            if (StrLower(w2.Text) != "text")
                continue
            b := w2.BoundingRect
            if !(Abs(b.y - a.y) <= a.h && b.x > a.x && b.x - (a.x + a.w) < 40)
                continue
            row  := {x: (a.x + b.x + b.w) // 2, y: a.y + a.h // 2}
            dist := Abs(row.x - nearX) + Abs(row.y - nearY)
            if (!best || dist < bestDist)
                best := row, bestDist := dist
        }
    }
    return best
}
CONCEPT-ENCOUNTERED

OCR with word geometry, not just text

Windows' OCR engine (driven through src/vendor/OCR.ahk, no install required) returns not just a string but a list of words with bounding rectangles. That is what makes this possible: you can ask "is there a word 'text' on the same line, immediately to the right of this 'copy'?"

mode: 4 is PrintWindow with PW_RENDERFULLCONTENT — the only capture mode that returns anything but black for a hardware-accelerated Electron window, and it reads Discord even when another window covers it.

Three traps this has to avoid, and all three are in the comments:

  1. The same menu carries "Copy Message Link". Matching a lone "Copy" clicks that about half the time, depending on which one OCR reports first. So a "Text" word is required on the same row, immediately to its right.
  2. A message in the channel can itself contain the words "copy text". Ties are broken by distance to the click, and the menu opens at the click.
  3. The whole window is a lot of pixels for a menu that is always at the cursor. OCR cost tracks area — the whole window at scale 2 measured ~157 ms — so the read is boxed to a rectangle around the click.

The clamp that is not defensive padding

bx := Max(0, cx - b.left)
by := Max(0, cy - b.up)
bw := Min(b.left + b.right, (ccw ? ccw : bx + 1) - bx)
bh := Min(b.up + b.down,    (cch ? cch : by + 1) - by)
if (bw < 40 || bh < 40)
    return 0

"A right-click near the top of the message list puts cy - up well below zero, and a capture region starting off the bitmap is not a smaller read — it is a throw, inside a try, which would look exactly like 'the menu was not found.'"

Polling instead of sleeping

global SEQ_MENU_FIRST_MS := 60     ; before the first look
global SEQ_MENU_STEP_MS  := 55     ; between looks
global SEQ_MENU_MAX_MS   := 600    ; give up, measured from the click

Sleep SEQ_MENU_FIRST_MS
Loop {
    tries++
    hit := _SeqFindMenu(mx, my)
    if (hit || A_TickCount - t0 > SEQ_MENU_MAX_MS)
        break
    Sleep SEQ_MENU_STEP_MS
}
CONCEPT-ENCOUNTERED

Poll to a deadline, do not sleep to a guess

"This was one flat Sleep 250 and a single attempt. 250 ms is a guess at the slowest frame Discord might need, paid in full on every import even when the menu was up in 60 — and if it was not up yet, the one attempt was spent on a blank patch of chat and the whole import failed."

Polling fixes both ends: the common case is fast and the slow case still works. Any time you see a fixed Sleep before checking for something asynchronous, that is the shape to replace.

And there is a last-resort whole-window read after the loop, which logs a LOGW when it succeeds: "If this line is common, SEQ_MENU_BOX is too small." That is instrumentation telling you how to tune it.

Failure is specific

if !hit {
    Send "{Escape}"          ; don't leave the menu hanging open over the chat
    LOGE("seq.discord", "neither the bitmap match nor the OCR read found a"
                      . " 'Copy Text' row in Discord's context menu — nothing"
                      . " imported",
                      "clicked at " mx "," my
                    . "; bitmap needle " COPY_TEXT_IMG
                    . " (goes stale when Discord restyles its menus)")
    ToolTip("Import: no 'Copy Text' in the menu")
    SetTimer(ClearImportTip, -2000)
    return
}

Naming which of the two routes failed matters, because the fixes are completely different — one goes stale when Discord restyles, the other depends on the window being readable.

Step 4–5: which model is this for?

The channel name is the routing key: #-aliw-staff-chat → aliw → the Aliw model.

Two readers, title first

DiscordChannelName() {
    DetectHiddenWindows false
    CoordMode "Pixel", "Client"
    chan := DiscordChannelFromTitle()
    if (chan = "")
        chan := DiscordChannelFromHeader()
    ; …restore both…
    return chan
}

Neither covers everything: the title is exact and instant but only names a text channel, while the header is on screen whatever the title says.

DiscordChannelFromTitle() {
    try t := WinGetTitle("ahk_exe Discord.exe")
    if !RegExMatch(t, "^#(.+?)\s*\|", &m)
        return ""
    return DiscordSlug(m[1])
}
The leading # is the whole test

Discord titles a text channel "#<emoji>-aliw-staff-chat | ILTC - Discord". The # marks a TEXT channel.

A voice channel or the settings page titles itself without one — and those have to fall through to the OCR read rather than have their SERVER name matched as if it were a channel.

This is the source of a recurring confusion in this repo's own notes: the window title you get when someone is in a voice channel is the voice channel's, not the text channel you are reading.

Two CoordMode / DetectHiddenWindows flips, both necessary

"This script runs with DetectHiddenWindows ON (it needs it to PostMessage the MMA GUI). Left on, ahk_exe Discord.exe can resolve to one of Discord's hidden helper windows — blank title, nothing to capture."

"Client coords, so a maximized window's invisible border (its rect starts at −8,−8) does not shift the band out from under the header."

Both are saved and restored around the call. This is the standard shape for any function that changes a thread-global.

Matching the slug shape, not the first characters

DiscordSlug(txt) {
    if RegExMatch(txt, "([A-Za-z][A-Za-z0-9]*(?:-[A-Za-z0-9]+)+)", &m)
        return StrLower(m[1])
    return ""
}

Requiring the hyphen is what keeps prose from being read as a channel — "Set a channel topic", a banner, a server name. And Discord draws an emoji immediately before the name, which OCR turns into junk, so matching the shape rather than the start is what survives that.

Which segment is the model?

ModelFromChannel(chan) {
    segs := StrSplit(chan, "-")
    for known in KnownModelNamesFromCfg()
        for s in segs
            if (s != "" && StrLower(s) = StrLower(known))
                return s                      ; a known name wins outright
    for s in segs
        if (StrLen(s) >= 3)
            return s                          ; else the first non-debris segment
    return segs.Length ? segs[1] : ""
}

Not simply "the first segment": OCR can render the emoji as a stray character or two, so the slug can arrive as q-aliw-staff-chat. So a segment that matches a model MMA already knows wins, and only if none does do we fall back to the first segment long enough not to be OCR debris.

KnownModelNamesFromCfg() reads the model slots plus the [ModelAliases] table from the cfg — read, not hard-coded, so renaming a model in Settings does not quietly break the routing.

CONCEPT-ENCOUNTERED

Tagging data in-band, because the channel cannot carry metadata

A window message carries two integers. The clipboard carries text. There is nowhere to put "this mass is for model 2" except in the text itself.

So the sender prepends @model: aliw as a line, and the receiver strips it:

ExtractModelName(&raw) {
    lines := StrSplit(...)
    for i, ln in lines {
        t := Trim(ln)
        if t = ""
            continue
        if RegExMatch(t, "i)^@(?:mma-)?model\s*[:=]?\s*(.+)$", &m) {
            name := Trim(m[1])
            lines.RemoveAt(i)
            raw := ""                          ; rebuild WITHOUT that line
            for _, l in lines
                raw .= (raw = "" ? "" : "`n") l
            return name
        }
        return ""      ; first real line isn't a marker — stop looking
    }
    return ""
}

Note the return "" in the loop body: it only looks at the first non-blank line. A @model: further down is message text, not a marker.

The in-band signalling pattern always has this hazard — real content that looks like a marker — and the standard defence is the one used here: only recognise the marker in a position where content cannot appear.

The last link, and the one that fails silently

_guiWin := MMA_GuiWin()
if WinExist(_guiWin) {
    PostMessage MMA_MSG_AUTOPARSE, 0, 0, , _guiWin
    LOGI("seq.discord", "told the MMA window to auto-parse the clipboard")
} else {
    LOGE("seq.discord", "the copied text is on the clipboard, but the MMA window"
                      . " is not running — nothing will parse it",
                      "looked for window title " _guiWin)
}

"The text is on the clipboard, tagged and ready, and if the GUI is not running there is nothing to receive it. From Discord that looks exactly like the import having done nothing at all."

MMA_GuiWin() rather than MMA_SRC_GUI — chapter 3 covers why. Hard-coding the Win32 shell's path was correct while it was the only front end and silently wrong the moment WebView could be the running window.

The other import route

WEB_IMPORT_SENTINEL := "#MMA-IMPORT#"

WebImportFromClipboard(dataType) {
    if _webImporting || dataType != 1     ; 1 = clipboard now holds text
        return
    cb := A_Clipboard
    if SubStr(cb, 1, StrLen(WEB_IMPORT_SENTINEL)) != WEB_IMPORT_SENTINEL
        return
    _webImporting := true
    body := LTrim(SubStr(cb, StrLen(WEB_IMPORT_SENTINEL) + 1), "`r`n")
    A_Clipboard := body                   ; leave a clean copy
    ClipWait(0.5)
    try WinActivate("ahk_id " g.Hwnd)
    PostMessage(MMA_MSG_AUTOPARSE, 0, 0, , "ahk_id " g.Hwnd)
    _webImporting := false
}

Registered by OnClipboardChange. A web page's "Send to MMA" button copies a sentinel plus the mass text; MMA notices, strips the sentinel, and reuses the same parse path.

Two guards worth noting: dataType != 1 ignores non-text clipboard events, and _webImporting is a re-entrancy flag — writing the clean copy back to the clipboard re-fires this very handler, and without the flag it would recurse.

Routing at the receiving end

Covered in chapter 9. In summary:

SituationBehaviour
Name matches a slot, fast-parse onSwitch tab, parse, save silently. _lastImportModel is remembered.
No name at all, fast-parse on, a previous import existsRoute to the same model as last time.
Anything elsePromptSaveTarget(detected) — a dialog with a name combo and a model dropdown, plus a "remember this name" checkbox.

The prompt's name combo is pre-filled with KnownModelNames() and the detected name, so the common case is one Enter. And the "remember" checkbox goes through RememberModelName, which adopts the name when the slot has never been named and writes an alias otherwise — chapter 9 covers the bug that distinction fixed.
