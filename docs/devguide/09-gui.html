Chapter 9

The GUI

src/ui/ is 13,500 lines — a third of the codebase — and almost nothing includes it. Windows are the outermost layer, not the centre. This chapter covers the one file that matters to the core: main_core.ahk, the app behind the main window, with no window in it.

The seam

MMA has two front ends for the same window:

  • ui/main_window.ahk (1,497 lines) draws the panel out of Win32 controls.
  • ui/webview_main_window.ahk (981 lines) draws the same panel with Edge and CSS, loading ui/webview/main_window.html.

Everything that is not drawing lives in ui/main_core.ahk (1,800 lines), and both of them #Include it.

Why this file exists

It did not, and the two shells had grown their own copies of the same logic — thirty-four functions defined twice. They had already drifted:

  • ApplyFile differed by 56 lines.
  • PickMassSlot differed by 28.
  • The WebView's LoadFile called RefreshModelHeader() where the Win32 one did not — so loading a model you were not looking at left both buttons naming the previous one.

"That is the exact shape of the mass-# bug (2.0.3): what you SAW and what the keys SENT disagreed, because two copies of one truth are one copy plus a lie waiting to be found."

The rule

If a function does not touch a Gui control's POSITION, SIZE or CREATION, it belongs in main_core.ahk, not in a shell.

The contract

Nothing in main_core.ahk creates a control, and nothing in it knows what a control is. A shell must have assigned these before anything in core is called:

CONCEPT-ENCOUNTERED

Duck typing, and the smallest possible interface

Core needs objects with a .Value and, for captions, a .Text. That is the entire interface. The Win32 shell hands it real Gui controls, which already have both. The WebView shell hands it shims:

class WvCell {
    __New(startValue := "") {
        this._v := startValue
    }
    Value {
        get => this._v
        set {
            this._v := value
            WV_Touch()          ; mark the page dirty
        }
    }
    Text {
        get => this._v
        set => this.Value := value
    }
}

Fifteen lines, and it is what makes one copy of 1,800 lines of logic possible.

This is worth studying as a technique. The seam is minimal — two properties — so almost nothing can be shell-specific by accident. Contrast a "renderer interface" with twenty methods: every method is a place the two implementations can diverge.

Note also that WvCell exposes Value and Text over the same storage. A button's caption and an edit box's contents are both "the string this thing shows", and the Win32 controls happen to agree.

The one place the duck type leaks, and how it is caught

WV_Quiet(cell, v) {
    if (cell is WvCell)
        cell._v := v
    else
        cell.Value := v
}

"edCtrls holds two kinds of thing. The main panel's fourteen fields are shims; the Variants window's branch cells are REAL Gui Edit controls, because that window is still old AHK. A Gui control has no _v, and AHK will happily create one — so the assignment would succeed, the box would keep its old text, and nothing anywhere would say so."

That is a general AHK hazard worth remembering: assigning to an undeclared property on an object silently creates it. There is no compile error and no run-time error, just a value that goes nowhere.

CONCEPT-ENCOUNTERED

Coalescing writes onto a zero-delay timer

A single FillTabFromSlot writes forty-odd cells in a row. Forty round trips through ExecuteScript to draw one tab is the kind of thing that makes a WebView feel slower than the Win32 window it replaced.

SetTimer(fn, -1) schedules fn to run once, on the next message-pump tick. Calling it forty times in a burst still results in one run. That is the whole coalescing mechanism: one line.

This idiom — "mark dirty, redraw once on the next tick" — is the standard answer to any write-amplification problem where the writes are cheap and the flush is expensive.

WV_Sync then pushes the whole window state to the page, every time. No delta protocol. That is a deliberate trade: a delta protocol is a second model of the state that can disagree with the first, and the whole state is a few kilobytes of JSON.

Never open a modal inside a COM callback 
WV_OnMessage(sender, args) {
    ; `set` is handled inline: common case, every keystroke, cannot put a window up.
    ; Everything else is QUEUED onto a -1 timer instead of being run here.
}

"This function is called from inside a COM event, and half these commands open a modal — the unsaved-changes prompt, 'All fields are empty. Save anyway?', the Settings window. A modal pumps messages, so running one inside the callback invites the next web message to arrive while this one is still on the stack. Returning first costs nothing and takes the whole question away."

The same rule as "never block inside a hotkey handler" from chapter 8, arriving from a different direction.

The load / save / parse cycle

This is the part of the GUI that owns your data. Four functions, and every one of them has a comment about a bug that cost real masses.

LoadFile(fname) — library → boxes

LoadFile(fname) {
    modelNo := ModelNoOf(fname)
    LOGD("gui.load", "Load fired for " fname " → model " modelNo)
    doc  := MASS_Load()
    slot := MASS_MassNo(doc, modelNo)
    if (slot < 1 || slot > MASS_SLOTS)
        slot := 1
    FillTabFromSlot(modelNo, slot, doc)
    try tabs.Value := modelNo
    RefreshModelHeader()
    lblLoaded.Text := ModelNameForSlot(modelNo) " loaded (mass " slot ")"
    LOGI("gui.load", "loaded model " modelNo " (" fname ") mass slot " slot)
}

Which mass comes in is the model's own live slot, and the Mass # radio is set to match, so the box always says what you are looking at.

Two bugs recorded in this one function

1. A_Index in a nested loop. The original had Loop MASS_SLOTS { for field in MASS_Fields() { ck := "m" A_Index "_" field } } — and A_Index always refers to the innermost loop, so inside the for it counted fields (1..44), not slots. It silently built control keys like m17_fu1 that matched nothing, and for the few that did exist wrote one slot's value into another's box. Saving was always fine, which is why it would not come back.

2. The control keys are m<MODEL>_, not m<SLOT>_. They were slot-keyed when the tabs were the three masses. Leaving this loop indexing by slot while the tabs became models is precisely how three-masses-per-model editing was lost: loading a model wrote its masses 1–3 across the first three models' tabs.

3. RefreshModelHeader() nearly went missing in the merge. The tab is moved in code, which fires no tab-change event in either shell — so the labels naming the model Load and Save act on have to be told. The WebView copy called it; the Win32 copy did not.

FillTabFromSlot — the one place boxes are filled

FillTabFromSlot(modelNo, slot, doc := 0) {
    if !doc
        doc := MASS_Load()
    rec := MASS_Get(doc, modelNo, slot)
    for field in MASS_Fields()
        if edCtrls.Has("m" modelNo "_" field)
            edCtrls["m" modelNo "_" field].Value := rec.Has(field) ? rec[field] : ""
    if (modelNo >= 1 && modelNo <= massNoCurrent.Length)
        massNoCurrent[modelNo] := slot
    SetMassNoRadio(modelNo, slot)
    VarRefresh()
    CORE_Changed()
}

Every field is written, including the empty ones. That is the whole point of loading a slot you have not written yet: mass 2 of a model that only has a mass 1 must come up blank, not leave mass 1's text sitting in the boxes looking like it belongs to mass 2.

ApplyFile(fname, silent) — boxes → library

ApplyFile(fname, silent := false) {
    modelNo := ModelNoOf(fname)

    ; ── refuse a save that would blank this model ────────────────
    _pfx := "m" modelNo "_"
    allEmpty := true
    for k, c in edCtrls {
        if (SubStr(k, 1, StrLen(_pfx)) = _pfx && Trim(c.Value) != "") {
            allEmpty := false
            break
        }
    }
    if allEmpty {
        if silent {
            LOG_Bail("gui.save", "silent save of model " modelNo " SKIPPED — every"
                               . " field on screen is empty, and writing that would"
                               . " blank this model's masses on disk")
            return
        }
        if MsgBox("All fields are empty. Save anyway?", "Confirm Save", 0x24) != "Yes"
            return
    }

    ; ── read-modify-WRITE THE WHOLE LIBRARY ─────────────────────
    slot := MassNoForModel(modelNo)
    doc  := MASS_Load()
    rec := MASS_Blank()
    for field in MASS_Fields() {
        ck := "m" modelNo "_" field
        rec[field] := edCtrls.Has(ck) ? edCtrls[ck].Value : ""
    }
    MASS_Set(doc, modelNo, slot, rec)
    MASS_SetMassNo(doc, modelNo, slot)
    if !MASS_Save(doc)
        return
    engineUp := NotifyMassesChanged()
    ...
}

Three things happening here

1. The empty check is scoped to this model's prefix. It used to scan every control in the window, which was right when the window held one model; with a tab per model it would call a blank model "not empty" because a different model's tab has text — and the whole point of the check is to refuse a save that would blank this one.

2. Read-modify-write the whole library. The file holds all N models and the GUI only has this one on screen. Writing a document built from the edit boxes alone would blank the others.

3. MASS_SetMassNo right after MASS_Set. "What you just saved is what the keys should send. Without this you would save into mass 2 and go on sending mass 1, which is the 'hotkeys are broken' report."

And it tells you when the save is pointless

MsgBox("Saved model " modelNo " — but the mass engine is NOT running, so no "
     . "hotkey will send it.`n`nTick engine.ahk under Settings → startup "
     . "scripts, or run src\mass\engine.ahk.", "Saved, but nothing can send it", 0x30)

NotifyMassesChanged() broadcasts MMA_MSG_MASSES_CHANGED and returns whether the engine was there to hear it. "Saved model 2" while nothing on the machine can send model 2 is a lie by omission — the save worked, but the thing the user is about to go and press does not exist.

ParseCurrent() — paste box → boxes

ParseCurrent(*) {
    raw := StrReplace(StrReplace(edPaste.Value, "`r`n", "`n"), "`r", "`n")
    mNo := tabs.Value
    LOGI("gui.parse", "parsing " StrLen(raw) " chars of pasted text into model "
                    . mNo "'s fields"
                    . (Trim(raw) = "" ? "  — THE PASTE BOX IS EMPTY, so this will"
                                      . " clear the fields and fill nothing" : ""))
    pfx := "m" mNo "_"
    for k, c in edCtrls
        if SubStr(k, 1, StrLen(pfx)) = pfx
            c.Value := ""
    FillTab(StrSplit(raw, "`n"), mNo)
    VarRefresh()
    ... archive ...
    CORE_Changed()
}

StrLen(pfx), not 3. pfx is "m" mNo "_", so it is three characters only while mNo is one digit — at ten models "m10" was compared against "m10_", matched nothing, and Parse stopped clearing the old text out of the boxes before filling them. That fix came from the WebView copy and was folded in during the merge.

"Parsing into the WRONG TAB is the classic version of 'it did not work': the text lands in model 3's boxes while you are looking at model 1's, so the fields you can see stay empty and it reads as the parser failing outright." Hence the model number in the log line.

The archive, and the dialog that was removed

if FEAT("archive") && LOG_IniInt(CFG_FILE, "Settings", "ArchiveOnParse", 1)
                   && Trim(raw) != "" {
    if dup := ArchiveFindDuplicate(mName, raw) {
        ToolTip("Archive: already saved today")
        SetTimer(ClearArchiveTip, -1500)
    } else {
        ts := FormatTime(, "yyyy-MM-dd HH:mm:ss")
        FileAppend "[" ts "] [" mName "]`n" raw "`n===END===`n`n", ArchiveFile(), "UTF-8"
    }
}

"Archiving is silent in both directions now. It used to raise a Yes/No dialog on every duplicate — mid-parse, with the fields already filled, for the most ordinary thing you can do here: fix a line and press Parse again. The answer was 'No' every time, so the dialog was a keystroke charged for nothing."

Note the unnamed-slot guard: an unnamed model used to write [] as its label, "which no dup check could match". Small, and it made the whole dedupe silently useless for that model.

PickMassSlot — clicking a Mass # radio

PickMassSlot(modelNo, slot, *) {
    prev := massNoCurrent[modelNo]
    if (slot = prev) {
        FillTabFromSlot(modelNo, slot)      ; re-click = reload, a free undo
        return
    }
    if TabDiffersFromSlot(modelNo, prev) {
        if (MsgBox("Mass " prev " has unsaved changes.`n`nSwitch to mass " slot
                 . " and lose them?", "Unsaved changes", 0x24) != "Yes") {
            SetMassNoRadio(modelNo, prev)   ; put the radio BACK
            return
        }
    }
    doc := MASS_Load()
    FillTabFromSlot(modelNo, slot, doc)
    MASS_SetMassNo(doc, modelNo, slot)
    empty := (Trim(MASS_Get(doc, modelNo, slot)["mass"]) = "")
    if MASS_Save(doc)
        NotifyMassesChanged()
    LOGI("gui.massno", "model " modelNo " is now on mass " slot
                     . " — shown in its tab, and what the keys send"
                     . (empty ? ". That slot is EMPTY, so the mass keys will do"
                              . " nothing for this model until you fill it in" : ""))
}

Three design decisions in twenty lines:

Re-clicking the current slot reloads it — a free undo, at no cost.

It asks before discarding, and only when there is something to lose. TabDiffersFromSlot compares against the slot the tab is showing, not the live one, so the prompt is true only when there is genuinely unsaved text. It also logs which field differs and both values — because when it was wrong (it refused to leave a slot nobody had edited) the alternative was bisecting forty fields by hand.

One control, one meaning. "The radio is this model's mass, full stop: what you SEE, what a save writes, and what the hotkeys SEND." The old "-- Set massNo --" grid was a separate control that wrote the live slot; dropping half of that made the row look broken — a model sat on mass 3 because that was its live slot, and clicking mass 1 changed the boxes while every key went on sending 3.

CONCEPT-ENCOUNTERED

One control, one meaning

The 2.0.3 bug ("the mass # radio changed what you SAW but not what the keys sent") is the archetype. Whenever a control shows state and a separate control sets it, they will disagree — and the disagreement is invisible, because both look correct on their own.

The fix is never "keep them in sync". It is to make them the same control.

Import routing

AutoParseFromClipboard(wParam, lParam, msg, hwnd) {
    raw      := A_Clipboard
    detected := ExtractModelName(&raw)      ; strips a leading @model line
    edPaste.Value := raw
    slot := detected != "" ? MatchModelName(detected) : 0

    if (fastParseAutosave && slot) {
        tabs.Value := slot
        ParseCurrent()
        ApplyFile(_mFiles[slot], true)
        _lastImportModel := slot
    } else if (fastParseAutosave && detected = "" && _lastImportModel) {
        tabs.Value := _lastImportModel
        ParseCurrent()
        ApplyFile(_mFiles[_lastImportModel], true)
    } else {
        PromptSaveTarget(detected)
    }
}

tabs.Value first, every time. ParseCurrent fills the tab that is in front and ApplyFile saves the model it is given — the same number, or the import lands in one model's boxes and is written to another's record.

Fast mode auto-saves only when the model is known: a matched name, or the model the last import was routed to. Otherwise it asks. Never silently dump into mass 1.

"Remember this name for the model"

One checkbox on the import prompt, and it means two different facts:

RememberModelName(name, slot) {
    ; …ADOPT the name when the slot has never been named,
    ; …otherwise write an ALIAS.
}

Writing only the alias is right for a model MMA already knows, and wrong for a slot that has never been named — that slot then has no display name, so nothing shows it and the user opens Settings and types the same name a second time. That was the reported bug.

ModelNameForSlot, and the ternary that lied

ModelNameForSlot(slot)

This replaced slot = 1 ? … : slot = 2 ? … : model3Name, which answered for slot 4, 5 and 40 with model 3's name — confidently and wrongly. Out of range now says so.

CONCEPT-ENCOUNTERED

A chained ternary has no "else" — it has a last branch

Every a ? x : b ? y : z ends in a value that catches everything else, including inputs that are errors. It reads like an enumeration and behaves like a default. This pattern is worth grepping for whenever a bound has changed.

Why these are behind a call and not at the top level

They used to be top-level statements, "which made WHERE a shell #Included this file part of its behaviour: the OnMessage lines sat mid-file in the Win32 shell and the HK_Binds sat at its very end, so any shell that included this anywhere else got a subtly different startup."

A call says plainly "arm the shared behaviour now", and both shells make it at the end of their own setup. Nothing in here is safe to run twice — OnClipboardChange would fire the import handler twice per copy — so it must be called exactly once per process.

CORE_SettingsChangedFromMsg is worth noting for what it fixes: the Win32 Settings is a Gui inside this process and calls UpdateModelButtons() directly; the WebView one is its own script and cannot. "Without this handler a rename or a theme change made there landed in the cfg and nowhere on screen until a restart, which reads exactly like the setting did not save."

Two smaller things worth reading

CORE_OpenActivity() — a button that fires a hotkey

The activity chart has always existed and has only ever had one door: the gui.activity key. That is a door you have to already know about, and the log said it had never been opened once — act.boot every session, act.chart never.

So a button was added, in both shells — but it does not run activity_window.ahk itself. The tracker owns the minute in progress and flushes it before opening the chart; without that the chart comes up showing everything except the minute you just pressed the button about.

The button therefore fires gui.activity through the registry and the tracker answers — exactly as the Actions menu runs a key that lives in another process. One implementation, and the button and the key cannot drift.

CheckCollisions() — a linter for your own hotstrings

if RegExMatch(ln, "^:[^:]*:([^:`r`n]+)::", &m)
    trigger := StrLower(Trim(m[1]))
else if RegExMatch(ln, "^([^:\s]+)::", &m)
    trigger := StrLower(m[1])

Scans utils.ahk, content/general.ahk and every account file for hotstring and hotkey definitions, and warns when the same trigger appears in two files. It is a plain text scan of source — crude, and exactly right for the job, because those files are hand-written and there is no other authority.
