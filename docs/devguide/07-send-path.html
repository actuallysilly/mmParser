CONCEPT-ENCOUNTERED

Key overloading — several ids, one action

fu1short, mFu1, altFu1 and fu1 are four ids for one action. That is deliberate: one action can carry a keyboard key, a mouse button and a Scimitar side button at once without any of them knowing about the others.

Add an id to hotkeys.ahk, add a line here, done. No branching anywhere, no "which kind of key is this" test.

Some of these are historical. altFu1 was once "pick an alternative for follow-up 1", back when that was a separate key. It is now simply a second binding for DoFu1, kept only so an existing Ctrl+F1 binding does not go dead — because the plain key now stages every alt and every branch, so there is nothing left for a "pick alt" key to do.

Two ways in, and they never overlap

MassBindModel(n) {
    for slot, fn in MassSlotHandlers() {
        id := "mass." n "." slot
        if HK_META.Has(id)
            HK_Bind(id, _ModelFire(n, fn))
    }
    _MassApplyMouseControl("mass." n)
}

    for slot, fn in MassSlotHandlers() {
        id := "mass.active." slot
        if HK_META.Has(id)
            HK_Bind(id, _ActiveFire(fn, slot))
    }

Why this matters historically. There used to be three processes — 1_mass.ahk, 2_mass.ahk, 3_mass.ahk — and all three bound the same physical keys. Five separate mechanisms existed purely to arbitrate between them: a 350 ms timer per process re-reading the detector status to switch other models' keys off, a re-check inside every handler, a list of which ids were shared, and an exemption in the Hotkeys window's conflict report so it would not flag three copies of one key as a clash.

One process needs none of it. All five are gone. In v1, with the detector on and model 2 in front, model 1's F1 went dead — that is what this design fixed.

Mouse control, applied after binding

_MassApplyMouseControl(section) {
    if mouseControl
        return
    for slot in MassSlotHandlers() {
        if (SubStr(slot, 1, 1) != "m" || SubStr(slot, 1, 4) = "mass")
            continue
        id := section "." slot
        if !HK_META.Has(id)
            continue
        if !_IsMouseKey(HK_Key(id))
            continue
        HK_SetState(id, "Off")
    }
}

Done after binding rather than by skipping the bind, so flipping the setting back on only needs a reload, not a rebind.

Two guards worth noticing. SubStr(slot, 1, 4) = "mass" excludes the mass slot, which starts with "m" but is not a mouse key. And more subtly:

"The slot name says overload, not mouse. Nothing stops a keyboard key going in one — mPpv/mPpvFus hold F4/F5 — and a setting labelled 'Mouse-button follow-ups' must not reach across and darken those. Test the KEY, which is the thing the setting is actually about."

_IsMouseKey(key) {
    key := RegExReplace(Trim(key), "^[\^!+#<>*~$]+")     ; strip modifiers
    return RegExMatch(key, "i)^(?:L|R|M|X)Button[12]?$|^XButton[12]$"
                         . "|^Wheel(?:Up|Down|Left|Right)$") > 0
}

Wheel is included: WheelUp on a follow-up is exactly the kind of accident "mouse control off" is meant to prevent.

Step 1 — _HK_Fire

Covered in detail in chapter 4. In one sentence: three anti-fumble guards, then set _HK_SENDING, call HK_SendBegin() (which arms the click wall), run the handler in a try, and clear everything in a finally.

One detail that only makes sense now:

finally {
    if (isSend) {
        _HK_LAST_SEND := A_TickCount
        HK_SendEnd()          ; hooks run BEFORE the flag clears
        _HK_SENDING := false
    }
}

"The hooks run BEFORE the flag clears, so the whole guarded window — including a click the wall plays back — is one unbroken 'still sending'. Clearing first would open a several-millisecond gap in which a real keypress could land between the last Enter and the playback, which is the fumble, just narrower."

Step 2 — which model is firing

The numbered path: _ModelFire

_ModelFire(modelNo, fn) {
    return (*) => (_SetCurModel(modelNo), fn())
}
_SetCurModel(n) {
    global MASS_CUR_MODEL := n
}

Two lines. This is what lets mass.1.fu1 (F1) and mass.2.fu1 (F9) be two live keys in one process, with no gating and no timer: the key you press IS the model selector.

MASS_CUR_MODEL is declared in core/utils.ahk, not in runtime.ahk, because sndFu reads it there and utils.ahk is also included by scripts that never load the mass engine (content/general.ahk, the account files). An unset global would throw the moment one of them touched it.

The shared path: _RunOnActiveModel

This is the interesting one. Read the order of its gates carefully — each one exists because of a specific failure.

_RunOnActiveModel(fn, slot := "") {

    ; ── 1. switched off in Settings ▸ Models ──────────────────
    if !SharedKeysOn() {
        LOG_Bail("mass.active", "…'Use a single hotkey for all masses' is switched"
                              . " off… the numbered per-model keys still work.")
        return
    }

    ; ── 2. LOCKED: one model, no question and no pixels ───────
    lock := LockedModelNo()
    if lock {
        _SetCurModel(lock)
        fn()
        return
    }

    ; ── 3. "I pick" mode: ask, don't assume ───────────────────
    if (ModelMatchMode() = "manual") {
        group := PickGroupForSlot(slot)
        if group {
            MassPickThenFu(group)
            return
        }
    }

    ; ── 4. resolve from the screen ────────────────────────────
    st := ActiveModelStatus()
    if !st.no {
        LOG_Bail("mass.active", "…MMA does not know which model is on screen (state: "
                              . st.state "). Nothing sent — that is deliberate,"
                              . " since guessing would send to the wrong fan.")
        return
    }
    _SetCurModel(st.no)
    fn()
}

Gate 1 — checked at fire time, not bind time

"Unbinding would need a restart of the engine to take effect either way round, and the whole point of the switch is for the shift where the detector has started lying: you turn it off, the shared keys stop guessing, and the numbered keys — which never come through here — carry on working from the same keypress."

Gate 2 — the lock comes first, before everything

Because that is what "locked" means: nothing else gets a vote. Not the mode, not the detector, not the picker. And the badge on screen naming the model is the condition on which this branch is allowed to exist at all, since it sends to a model nothing on screen identifies. Chapter 8 covers lock mode properly.

Gate 3 — why manual mode asks

"Manual mode never reads the screen — ActiveModelStatus always answers 'ok' with whatever model you last selected, however long ago that was. For a follow-up key that is the worst possible shape of confident: it sends, to a model nothing on screen names."

Which slots ask is PickGroupForSlot's call — the follow-ups always, the PPV pair behind its own feature switch, the mass key and next-follow-up never (a window in front of every shared key would be a window in front of everything).

Gate 4 — "no answer" means do nothing

That is the correct choice — guessing sends one model's message to another model's fan — but it is also the single most confusing thing MMA does, because the key is bound, the feature is on, and nothing happens. ActiveModelStatus has already logged why it has no answer; this adds the consequence, so the two lines sit together and the chain is readable end to end.

Step 3 — _DoFuGroup, the decision point

_DoFuGroup(group, editable, openTab) {
    ; each extra is BOTH a user setting AND a feature
    editable := editable && FEAT("editableFu")
    openTab  := openTab  && FEAT("openTab")
    sendBoth := doubleMM && FEAT("doubleMM")

    LOG_Kv("mass.fu", Map("group",    group,
                          "model",    MASS_CUR_MODEL,
                          "massNo",   MASS_MassNo(MASS_DOC, MASS_CUR_MODEL),
                          "branch",   ActiveBranchNo(),
                          "editable", editable ? "y" : "n",
                          "openTab",  openTab ? "y" : "n",
                          "doubleMM", sendBoth ? "y" : "n"))

    MASS_RememberSent(MASS_CUR_MODEL, MASS_MassNo(MASS_DOC, MASS_CUR_MODEL),
                      "fu" group)

    if AltIntercept(CurMass(), group, editable, ActiveBranchNo())
        return

    m := CurMass()

        return
    }

        sndFu(group, _FuParts(CurMassSlot(1), group)*)
        sndFu(group, _FuParts(CurMassSlot(2), group)*)
    } else {
        sndFu(group, _FuParts(m, group)*)
    }

        clickReturn(openInNewTabButton)
}

The LOG_Kv line is the most useful line in the file

Seven values, on one line, before any of them is acted on. Which model, which mass slot, which branch, and the three modifiers. When somebody says "it sent the wrong thing" or "it sent nothing", these are the four things you would ask for first.

MASS_RememberSent is called on the press, not on a successful send

"…because a follow-up that sent nothing (you never wrote it) is precisely the one you are about to go and write."

The note feeds the "Add Hotkey ▸ Replace follow-up" capture window, whose three dropdowns open on the follow-up you last aimed at.

_FuParts, and the group-3 fallback

_FuParts(m, group) {
    parts := [m.%"fu" group%, m.%"fu" group "_5"%, m.%"fu" group "_7"%]
    if (group != 3)
        return parts
    for p in parts
        if Trim(p) != ""
            return parts
    return DefaultFu3Parts()
}

Group 3 alone has a fallback: a mass with no f3 at all sends the DefaultFu3 text from Settings instead of nothing.

Why here and not in sndFu: SndFuEditable takes the same parts and has no idea which group it is holding. One place covers the plain send, the editable paste, and both halves of a double-MM — so a second model with no f3 still gets the default.

DefaultFu3Parts() {
    if !FEAT("defaultFu3")
        return ["", "", ""]
    return MASS_SplitParts(IniRead(MMA_CFG, "Settings", "DefaultFu3", ""))
}

Read per press rather than cached, so editing it in Settings takes effect without restarting the engine. And it goes through MASS_SplitParts because the ini stores line breaks as ``n — the same escape the branch fields use, so the record format's own reader already knows how to handle it.

Step 4 — AltIntercept and TAB staging

This is the biggest single subsystem in utils.ahk, and its history is worth knowing before its code.

The one-key rule

AltIntercept(m, group, editable := false, activeBranch := 0) {
    if !FEAT("altFollowups") {
        LOG_Bail("alt.intercept", "feature 'altFollowups' is off — follow-up "
                                . group " sends its main wording, no picker")
        return false
    }
    variants := AltVariants(m, group)
    if (variants.Length <= 1) {
        LOG_Bail("alt.intercept", "follow-up " group " has " variants.Length
                                . " variant(s) — nothing to choose between, so it"
                                . " sends directly with no picker")
        return false
    }
    ...
    AltStageBegin(group, variants, editable, AltStartIndex(variants, activeBranch))
    return true
}

Returns true = "I took over the send." Returns false = fall through to the plain send.

There is no ctrl-variant to press and no "prompt using ctrl+hotkey" setting any more. If this follow-up can be answered more than one way, the key stages the choices and TAB walks them. If it cannot, the key sends, exactly as it always did.

Note the second LOG_Bail. "The alt picker did not come up" is the commonest confused report about this feature — with one variant there is nothing to pick between, so it correctly sends straight away, which is indistinguishable from the feature being broken unless something says so.

AltVariants — one list of ways to answer

AltVariants(m, group) {
    out := []
    base := []
    for _, sfx in ["", "_5", "_7"] {
        key := "fu" group sfx
        if m.HasOwnProp(key) && Trim(m.%key%) != ""
            base.Push(Trim(m.%key%))
    }
    if base.Length
        out.Push({ parts: base, label: "main", branch: 0 })

    for bi, b in BranchList(m) {
        if !b.fu[group].Length
            continue                ; f1-only branches are NORMAL
        out.Push({ parts: b.fu[group], label: b.name, branch: bi })
    }
    return out
}

Each variant is {parts, label, branch}: the messages to send, what the list calls it, and which branch it commits you to (0 = trunk).

A branch with nothing in this group is skipped rather than shown empty — branches are commonly f1-only, and an empty row you can TAB onto and send is a way to send silence.

Where the preview goes — and why that is the whole bug

The failure that shaped this design

The preview used to go into the chat box. That read beautifully — the variants in the font and width they would actually send at, no window taking focus off the chat. And it had one failure that costs a real message to a real person:

Enter → clear the box (Ctrl+A, Delete) → paste the chosen variant → Enter

The clear is not reliable. Infloww's composer is a web editor, and Ctrl+A in one of those does not always mean "select what is in this box" — it can be swallowed outright, or select the page instead. When it misses, Delete removes nothing, the preview is still there, and the chosen variant is pasted onto the end of it. Then Enter sends the lot: every variant, the markers, the labels, as one message to the fan.

That is the "it sent the whole sequence" report. No amount of settling delay fixes it, because the failure is not a race — it is the composer refusing the keystroke.

So the preview goes in a small always-on-top window that never takes focus, and the chat box is never written to and never cleared. The variants cannot be sent because they were never in the thing that sends.

The chat-box mode is still there, one checkbox away (Settings ▸ Sending, "Don't use a GUI for alt FUs"), because a picker that does not draw on your machine is worse than one that occasionally over-sends.

The staging state machine

AltStageBegin(group, variants, editable := false, startAt := 1) {
    _altVariants := variants
    _altStaged   := (startAt >= 1 && startAt <= variants.Length) ? startAt : 1
    _altGroup    := group
    _altEditable := editable
    _altWin      := WinExist("A")        ; BEFORE the window exists — the CHAT window
    _altInBox    := !AltStageUseGui()
    AltPaintStage()
    if !_altHotkeysOn {
        HotIf AltStageActive
        Hotkey "*Tab",    AltStageNext,   "On"
        Hotkey "*+Tab",   AltStagePrev,   "On"
        Hotkey "*Enter",  AltStageCommit, "On"
        Hotkey "*Escape", AltStageCancel, "On"
        HotIf
        _altHotkeysOn := true
    }
    SetTimer(AltStageTimeout, -ALT_STAGE_TIMEOUT_MS)   ; 45 s, one-shot
    SetTimer(AltStageWatch, ALT_STAGE_WATCH_MS)        ; 250 ms, repeating
}
CONCEPT-ENCOUNTERED

Hijacking universal keys safely

Tab, Enter and Escape are the three keys you cannot afford to break. While a choice is staged they are claimed, and three independent mechanisms make sure they come back:

  1. A context. HotIf AltStageActive restricts them to the window staging began in and to the staged state. Without it, a stray Enter hook would swallow Enter in every application on the machine.
  2. A timeout. 45 seconds, one-shot. A forgotten staging gives the keys back on its own — and it logs a WARN, because a user who walked away mid-pick and came back to "Enter does not work in my chat" is looking at exactly this.
  3. A watchdog. Every 250 ms: if the chat window is gone, end the staging (there is nothing left to send into). If it is merely not active, hide the picker and keep the staging — you alt-tabbed; come back and it is where you left it.

Note the order in AltStageEnd: hotkeys released first, then the window closed. "A picker still on screen with Tab and Enter handed back is a window that ignores you."

AltStageActive(*) {
    if !_altVariants.Length
        return false
    if (_altWin && WinActive("ahk_id " _altWin))
        return true
    return _altGui && WinActive("ahk_id " _altGui.Hwnd)
}

The (*) is required, not stylistic — HotIf calls its criterion with the hotkey name, and a zero-parameter function is rejected with "Invalid callback function".

The picker being in the criterion is a safety net, not a feature: the window is WS_EX_NOACTIVATE and should never be active, but if anything ever does activate it, without that line Escape stops working and the only way out of a window with no title bar is the timeout.

The commit

AltStageCommit(*) {
    v    := _altVariants[_altStaged]
    grp  := _altGroup
    edit := _altEditable
    LOGI("alt.stage", "committed variant " _altStaged " of " _altVariants.Length
                   . " — '" v.label "'"
                   . (v.branch ? "  (this commits the conversation to branch "
                               . v.branch ", so f2/f3 will open on it)" : "") ...)
    if _altInBox {
        Send "^a"
        Sleep 20
        Send "{Delete}"
    }
    AltStageEnd()
    if ALT_ON_PICK
        try ALT_ON_PICK.Call(v.branch)
    HK_SendBegin()
    try
        SendAltVariant(grp, v.parts, edit)
    finally
        HK_SendEnd()
}

Four things happen here that are each worth a sentence:

Only chat-box mode clears. The unreliable step runs on exactly the mode that cannot do without it, and never on the one that can.

The branch is recorded BEFORE sending. So if the send throws, the next follow-up still knows where the conversation went.

It is a callback, not a direct call. Remembering a branch needs the mass document and the active model, which live in runtime.ahk — and utils.ahk is also included by account scripts that never load the engine. Calling _BranchKey() from here would throw in those.

The send edges are raised by hand. This send does not come through _HK_Fire — Enter is a hotkey AltStageBegin registered directly — so nothing in hotkeys.ahk knows a message is about to go out. Missing it here would leave the one send path that involves a deliberate pause as the only unguarded one.

Escape does not clear the box

AltStageCancel(*) {
    LOGI("alt.stage", "cancelled with Escape — nothing sent"
                   . (_altInBox ? ", chat box cleared"
                                : "; the chat box was never touched"))
    if _altInBox { Send "^a"; Sleep 20; Send "{Delete}" }
    AltStageEnd()
}

In window mode there is nothing to put back — the chat box was never written to — so clearing it would delete whatever the user had typed there, which Escape has no business doing.

Where the marker starts

AltStartIndex(variants, activeBranch) {
    if !activeBranch
        return 1
    for i, v in variants
        if (v.branch = activeBranch)
            return i
    return 1
}

Once you have picked a branch at f1, f2 opens on that branch — so walking a branch is Enter, Enter, Enter rather than TAB-hunting for the same name three times. TAB still reaches everything, so it is a starting point and never a lock. Falls back to 1 when that branch has nothing in this group, which is the normal case for an f1-only branch reaching f2.

Remembering the branch

ActiveBranchNo() {
    k := _BranchKey()
    if !_activeBranch.Has(k)
        return 0
    n := _activeBranch[k]
    return (n >= 1 && n <= BranchList(CurMass()).Length) ? n : 0
}

_BranchKey() {
    return MASS_CUR_MODEL "." MASS_MassNo(MASS_DOC, MASS_CUR_MODEL)
}

The key includes the model, not just the slot: with several models in one process, "mass 1" alone would let model 2's chosen branch overwrite model 1's.

And the range check guards against a mass edited since the pick — the branch may no longer exist, and indexing past the end of BranchList would throw inside a hotkey handler.

Step 5 — sndFu

sndFu(group, parts*) {
    nonEmpty := []
    for p in parts
        if Trim(p) != ""
            nonEmpty.Push(p)

    if !nonEmpty.Length {
        LOG_Bail("send.fu", "model " MASS_CUR_MODEL " follow-up " group " is EMPTY"
                          . " in the selected mass — nothing to send. (Sparse masses"
                          . " are normal; check the mass in the GUI if you expected text.)")
        return
    }

    fuSingle := IniRead(MMA_CFG, "Settings",
                        "FuSingle_" MASS_CUR_MODEL "_" group, "0") = "1"

    if !fuSingle {
        for p in nonEmpty
            snd(p)
        return
    }
    combined := ""
    for p in nonEmpty
        combined .= (combined != "" ? "`n" : "") p
    A_Clipboard := ""
    A_Clipboard := combined
    if !ClipWait(1)
        LOGE("send.fu", "…about to paste the PREVIOUS clipboard and press Enter", ...)
    Send("^v")
    Send("{Enter}")
    Sleep(waitTime)
}

The empty-parts bail is the most reported "the key did nothing". Masses are legitimately sparse — f1-only and f1+f3 with a gap are both normal — so this is correct behaviour and not a fault. It is still the answer to the question, so it names which model and which follow-up was empty.

FuSingle joins the parts into one message instead of three. The key is FuSingle_<model>_<group> — and the comment warns that the model number must be the one whose key was pressed, because read from the wrong one IniRead just returns its default and the setting appears to do nothing with nothing saying why.

Step 6 — Snd, the one function that actually sends

Snd(arg) {
    if (arg = "") {
        LOG_Bail("send.snd", "empty message — nothing sent")
        return
    }
    A_Clipboard := ""
    A_Clipboard := arg
    if !ClipWait(1) {
        LOGE("send.snd", "the clipboard never accepted the message — Ctrl+V is"
                       . " about to paste WHATEVER WAS ON THE CLIPBOARD BEFORE"
                       . " and press Enter",
                       "wanted to send: " SubStr(arg, 1, 120))
    }
    LOGI("send.snd", "sending " StrLen(arg) " chars: " SubStr(arg, 1, 90))
    Send("^v")
    Send("{Enter}")
    Sleep(waitTime)
}

Ten lines. Everything else in MMA is a decision about which message; this is the send.

Why this is instrumented so heavily

If the clipboard does not take the text — another app owns it, a clipboard manager is holding it, the text is enormous — ClipWait returns false and the very next line presses Ctrl+V anyway.

That does not send nothing. It sends whatever was on the clipboard before, into a real fan's chat, and then presses Enter. There is no way to see that from the outside except by reading the sent message.

It is a FAIL rather than a warning for that reason: it is the one failure in the file with a consequence you cannot take back.

waitTime is 400 ms by default (1500 for WaitTimeLong), declared at the top of utils.ahk. That pause between parts is what makes a three-part follow-up take over a second — and therefore what makes the anti-fumble guards and the click wall necessary.

The editable variant

SndFuEditable(parts*) {
    ... join non-empty parts with "`n" ...
    A_Clipboard := ""
    A_Clipboard := combined
    ClipWait(1)
    Send "^v"                ; NO Enter
}

Pastes the whole group as one block and does not press Enter, so you can edit before it goes out. This is what the Editable and Wallet-check toggles switch to.

The click wall — the mouse half of the guard

src/screen/click_wall.ahk, installed by engine.ahk as HK_OnSend(CW_Arm, CW_Release).

A follow-up is three messages with a waitTime pause between each, so one keypress owns the chat box for over a second. Click the next conversation inside that second and the parts still in flight land in the chat you just moved to. The fan you were talking to gets half a follow-up, and a stranger gets the other half.

None of the hotkey guards can see it coming, because a click on the conversation list is not a hotkey — it is the browser doing exactly what it was told.

CONCEPT-ENCOUNTERED

Choosing a mechanism by how it fails, not how it works

"An invisible wall" describes a transparent always-on-top window over the list, and that is the more literal build: clicks land on the window, so there is no criterion to evaluate and nothing can slip past while the script is busy.

It was not built that way because of how it fails:

"A window is state that outlives the code that raised it. If the engine dies mid-send — a crash, a reload at the wrong moment, a throw nothing catches — the wall is still up, still invisible, and still eating every click on the conversation list, with no window on screen to explain why and no hotkey left alive to take it down. That is a machine somebody has to reboot to fix, having never once seen the cause."

A hotkey cannot do that. It belongs to the process; when the process goes, the claim goes with it. The cost is that HotIf has to evaluate at click time and could in principle time out under a wedged script — which loses one wall, the same click that gets through today, every single time.

Losing the guard occasionally beats a desk that cannot be clicked. Apply this question to any mechanism you add: what state does it leave behind if the process dies at the worst moment?

And it verifies before playing the click back

Infloww sorts the conversation list by most recent message — and the send that is holding your click is what makes a conversation most recent. So the list can reorder underneath a held click, and a point that meant "Jess, row 4" when you pressed it can mean "Marie, row 4" a second later.

Playing that back is the exact failure the file exists to prevent, arriving by the front door. So the swallow keeps a small bitmap of what was under the pointer, the playback re-grabs it and compares, and different pixels mean the rows moved — a moved row is not clicked. It says so and leaves the click to you.

next_fu.ahk — one key for f1 → f2 → f3

310 lines, and the most interesting design decision in the mass folder.

Why it reads the screen instead of remembering

"The obvious implementation is for MMA to remember what it sent. It cannot, not usefully: 'which follow-up is next' is per FAN, and MMA has no fan identity — it would need to OCR the chat header to get one, which is the same cost as this and gives an answer that is still wrong after a restart, after you send from your phone, or the first time you open a chat you were mid-way through."

"The conversation already holds the answer. The follow-up text is known — it is in masses.json, MMA wrote it — so finding it is a substring search, not recognition."

Reading it back means: per chat for free, per model for free, correct after a restart, and correct in a chat MMA never sent in.

The matching

NFU_Norm(s) {
    return RegExReplace(StrLower(s), "[^a-z0-9]", "")
}

Everything that survives OCR reliably: letters and digits, lower-cased. Spaces go too — OCR engines disagree about them constantly, dropping them outright or inserting them inside words at line breaks, so any needle containing one is a coin flip. Punctuation and emoji go for the same reason. What is left still identifies a message: two different follow-ups do not share twenty-four consecutive letters by accident.

NFU_Needles(part, cfg) {
    n := NFU_Norm(part)
    if (StrLen(n) < cfg.minNeedle)      ; 12 — below this, "hey" matches everything
        return []
    L := cfg.needleLen                  ; 24
    if (StrLen(n) <= L)
        return [n]
    mid  := ((StrLen(n) - L) // 2) + 1
    last := StrLen(n) - L + 1
    out  := [SubStr(n, 1, L)]
    if (mid > 1)   out.Push(SubStr(n, mid, L))
    if (last > mid) out.Push(SubStr(n, last, L))
    return out
}

Three needles from one message, at the start, middle and end. One would be enough if OCR were perfect. It is not, and a single mangled character inside a 24-character window silently turns "already sent" into "not sent" — which sends the fan the same follow-up twice. Three windows spread across the message means a slip has to land in all three.

InStr with a negative start

at := InStr(hay, needle, true, -1)

Searches backwards from the end, finding the last occurrence. A long thread can hold the same follow-up from a previous round, and what matters is the most recent one.

Position, not group number

NFU_LastGroup(m, hay, cfg) {
    hits := [], best := 0, bestAt := 0
    Loop 3 {
        at := NFU_GroupAt(m, A_Index, hay, cfg)
        hits.Push(at)
        if (at > bestAt)
            best := A_Index, bestAt := at
    }
    return {group: best, at: bestAt, hits: hits}
}

What is wanted is the last one sent, and the pane reads top to bottom, so furthest down is most recent. Taking the highest group number instead would get this wrong the moment you deliberately re-send an earlier follow-up — the thing this key exists to let you do.

The three refusals

SituationAction
Nothing found, mass visibleSend f1. The sequence genuinely starts here.
Nothing found, no mass eitherSend nothing.
Last follow-up already foundSend nothing.
OCR read nothing at allSend nothing, and say why loudly.

The second one is the subtle one. "No follow-up found" has two very different causes that look identical to a substring search: the sequence has not started, or we cannot see it — scrolled up, or a chat the mass never went to. Sending f1 in the second case either repeats a follow-up that is in the thread just out of view, or opens with "did you see what I sent?" to someone who was sent nothing.

The mass is the evidence that tells them apart, so f1 waits for it (NFU_MassPresence).

"Next" means the next one that exists

NFU_NextWithContent(m, after) {
    g := after
    while (++g <= 3)
        for part in _FuParts(m, g)
            if (Trim(part) != "")
                return g
    return 0
}

Not group + 1. A mass is not required to carry all three follow-ups. Counting blindly broke both ends: on an f1-only mass, press two resolved to f2, and sndFu returns silently when every part is empty — so the key did nothing at all while the toast said "sending f2". A key that lies about having sent is worse than one that refuses, because you believe it and move on.

Note that it calls _FuParts, not the three stored fields. Those are the same thing for groups 1 and 2 and not for group 3, where the DefaultFu3 fallback means the message that lands in the conversation is the default — and matching the stored fields, which are blank, meant the walker could never find its own f3, and would send the default again to a fan who had already had it.

Live settings, without a restart

Eight settings are read once at engine load and then kept current by messages:

mouseControl   := LOG_IniInt(MMA_CFG, "Settings", "MouseControl",   1, "mass.boot")
openTabFu2     := LOG_IniInt(MMA_CFG, "Settings", "OpenTabFu2",     0, "mass.boot")
...
walletCheckFu3 := LOG_IniInt(MMA_CFG, "Settings", "WalletCheckFu3", 0, "mass.boot")

OnMessage(MMA_MSG_EDITABLE_FU1, SetEditableFuMsg)
OnMessage(MMA_MSG_EDITABLE_FU2, SetEditableFuMsg)
OnMessage(MMA_MSG_EDITABLE_FU3, SetEditableFuMsg)
Why every one is LOG_IniInt

These eight lines run at the top level of the mass engine. A throw here is not a wrong setting — it is an engine that does not start: every follow-up key, every PPV key, every branch and every __mm trigger in MMA silently dead.

And Integer() throws on anything non-numeric, so all it takes is one hand-edited MouseControl=yes in a file MMA itself invites you to edit.

They are then dumped at boot with LOG_Kv, and that is deliberate too: eight values that decide what every follow-up key does, read once, then kept live by messages — so a stale one is invisible and permanent for the life of the process. Writing them down at boot is what makes "editable was on the whole time" a thing you can see rather than deduce.

The __mm triggers

:*X:__mm::MassSendOrPick()

Ask, then paste. One model configured and there is nothing to ask, so it pastes that one; past that it opens a picker window whose buttons show the first line of each model's live mass.

The preview is the point, not decoration. It is also the only place in MMA that shows an empty mass slot before you paste it — the "__mm does nothing" complaint is always a live massNo pointing at a slot nobody filled in, and here that slot reads "(empty)" instead of failing after the keypress.

Why the numbered form is __1mm and not __mm1

__mm is declared :*X:, and * means "fire the moment the trigger is typed, no ending character". So while __mm was live it expanded on the second m and the 1 in __mm1 was never reached.

The two could only ever be mutually exclusive — which is what a whole mechanism called NumberedSendActive existed to arrange: __mm1 was live precisely when __mm was dead.

Putting the number in front dissolves that. __1mm shares no prefix with __mm, both are live at once, and neither has to be gated on the other. It also does not run out at nine: __mm11 could never have fired (the __mm1 before it would have), while __11mm is just another trigger — which is what lets these follow MASS_MODELS up to twelve.

CONCEPT-ENCOUNTERED

Dissolving a problem instead of arbitrating it

Two things could not coexist, so a mechanism was built to decide which one was live. The mechanism was correct, and it was a workaround for the trigger names, dressed as a policy about detector state.

Renaming removed the conflict outright and deleted the mechanism. Look for this shape: when you find arbitration code, ask whether the two things need to conflict at all.
