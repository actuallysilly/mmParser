Chapter 3

The spine: paths.ahk and log.ahk

Two files that every other file includes. One decides where everything is; the other decides whether you will ever find out what went wrong. Together they are about a thousand lines and they set the standard the rest of the codebase is written to.

Part one — src/core/paths.ahk

276 lines. Included, directly or transitively, by 47 files — more than any other file in the repo. Its job sounds trivial: hold some path constants. Its actual job is to prevent an entire category of silent failure.

The bug this file exists to kill

CONCEPT-ENCOUNTERED

A_ScriptDir versus A_LineFile

A_ScriptDir is the folder of the main script — the one you double-clicked or that Run launched. It is not the folder of the file the code is written in.

While every entry point in MMA lived in the repo root, those were the same folder, so 37 uses of A_ScriptDir "\something" happened to work by coincidence.

The moment a script runs from a subfolder — which is now every script — the coincidence is gone. And the failure is silent:

v := IniRead(A_ScriptDir "\mass_gui.cfg", "Settings", "Key", "default")

The file does not exist. IniRead returns the default. The setting quietly reverts, and nothing says why.

A_LineFile is the file this line of code is written in. It is immune to which script is the main one, which makes it the only correct anchor.

; Strip the last "\segment" off a path. Defined before first use: AHK parses every
; function at load time, so calling this from the top-level initialisers below is
; safe regardless of which script #Included us.
MMA_ParentDir(p) {
    cut := InStr(p, "\", , -1)
    return cut ? SubStr(p, 1, cut - 1) : p
}

; This file is  <root>\src\core\paths.ahk  → three levels up is <root>.
global MMA_ROOT := MMA_ParentDir(MMA_ParentDir(MMA_ParentDir(A_LineFile)))

That is the entire mechanism. Three MMA_ParentDir calls climb from …\src\core\paths.ahk to …\MMA. Every other path in the repo is derived from MMA_ROOT, so moving this file means editing one line and nothing else.

Note the comment on MMA_ParentDir: it is defined before it is used because AHK parses function definitions at load time, so a top-level statement can call a function declared later. But this file may be included by anything, in any order, so it puts the definition first anyway. That is a defensive habit worth copying.

The source-as-path group deserves attention

Three things in MMA reference source files as paths rather than #Includeing them, and all three break silently when files move:

  • recorder.ahk writes new code into sequences.ahk and hotkeys.ahk.
  • main_window.ahk scrapes utils.ahk as text to read its waitTime value.
  • sequences.ahk builds a WinTitle from the main window's path, because an AHK script's window title is its full path.

Their constants sit together at the bottom of the file with a header saying exactly this. If you move a file, that block is the first thing to check.

Three functions worth reading closely

MMA_ScriptPath(name) — resolving a bare filename

The config stores bare filenames: StartupScripts=engine.ahk,ALIW.ahk,general.ahk. That was unambiguous while every script sat in one folder; those three now live in three different ones. Rather than change the config format and break everyone's settings, this function searches a folder list:

for dir in [MMA_ACC_DIR, MMA_CONTENT,
            MMA_SRC "\mass", MMA_SRC "\chat", MMA_SRC "\sequences",
            MMA_SRC "\screen", MMA_SRC "\ui", MMA_SRC] {
    p := dir "\" name
    if FileExist(p)
        return p
}
The failure this function had

A folder missing from that list fails the worst possible way: ResolveScriptPath returns "", LaunchStartupScripts skips the entry, and the script simply never starts. No error, no dialog, nothing in the log. That is how engine.ahk silently stopped running after it moved to src\mass\ — and "engine not running" means every mass hotkey in MMA is dead.

The fix was not just adding the folder. It was adding the LOGW at the bottom that names the file and says, in words, that anything launching it will do nothing, silently. That is the pattern: make the silence audible.

MMA_ShellFor(which) — one question, asked once

MMA has three windows that come in both WebView and Win32 flavours. Rather than three launchers each reading their own key their own way, there is one function:

MMA_ShellFor(which) {
    if (which = "settings")   { key := "SettingsShell",   wv := MMA_SRC_SETTINGS_WV }
    else if (which = "hotkeys"){ key := "HotkeysShell",    wv := MMA_SRC_HOTKEYS_WV  }
    else                       { key := "MainWindowShell", wv := MMA_SRC_WEBVIEW     }
    v := StrLower(Trim(IniRead(MMA_CFG, "Settings", key, "webview")))
    return (v = "webview" && FileExist(wv)) ? "webview" : "legacy"
}

Two design points in five lines. First, the default lives in the read, not in a written key — so an install that has never touched the radio has no key at all and takes the new default, which is the entire mechanism by which WebView became the front end. Second, it falls back when the file is missing rather than failing: this is a preference, and a preference must never be able to leave you with no window at all.

Note also: IniRead and nothing else. No LOG_IniInt, no logging. paths.ahk is included by scripts that include nothing else, so it cannot call into log.ahk from a function that might run before the logger exists.

MMA_GuiWin() — addressing a window that might be either shell

MMA_GuiWin() {
    prev := A_DetectHiddenWindows
    DetectHiddenWindows true
    try {
        for _, path in [MMA_ShellPath(), MMA_SRC_GUI, MMA_SRC_WEBVIEW] {
            title := path " ahk_class AutoHotkey"
            if WinExist(title)
                return title
        }
        return MMA_ShellPath() " ahk_class AutoHotkey"
    }
    finally
        DetectHiddenWindows prev
}

Asks the preference first, then tries the other shell, so it is right whichever is up even if the setting changed without a restart. If neither is running it still returns a title, so the caller's "not running" branch and its log line can say something meaningful.

The bug this replaced: two files hard-coded MMA_SRC_GUI, which was correct while main_window.ahk was the only front end and silently wrong the moment WebView could be the window MMA started. The Discord import would report "MMA is not open" while MMA was plainly open.

The last line

#Include "log.ahk"

At the end, deliberately. log.ahk's own load-time code writes a boot line, and it needs MMA_LOGFILE and MMA_DEBUGLOGS to exist first.

And it is here at all because this is the one file every entry point already includes. Putting the logger include here means every process in the tree — including the ones nobody remembers exist — gets a boot line, an exit line and an uncaught-error hook with no wiring of its own and no way to drift out of step.

Part two — src/core/log.ahk

728 lines for a logger is a lot. Read its header and it stops being a lot, because it is not really a logging library — it is a theory of why this application fails, made executable.

The observation the whole file is built on

Quoting the header, because it is the clearest statement of the problem in the repo:

"MMA is not one program. It is up to eight processes that talk to each other through ini files and PostMessage. Nothing in that arrangement produces a stack trace when it goes wrong. It produces NOTHING, which is the actual complaint: it silently failed to do something on my friend's machine."

"Every failure this repo has fixed has the same shape: a folder missing from a list so a script never runs; an IniRead with a default so a setting silently reverts; a key absent from hotkeys.ini so an action is unbound; a feature switched off so its hotkey never registers; the engine dropped out of the startup list so every mass key went dead."

"Not one of those throws. Every one of them is a branch that returned early, and the only way to see a branch that returned early is to have written it down on the way past."

CONCEPT-ENCOUNTERED

Silent failure, and instrumenting the negative path

Most logging you have seen records what happened. The insight here is that in a system like this, the interesting event is what did not happen, and why.

So MMA has a log level for it. LOG_Bail(tag, why) means: this returned early on purpose, and here is the condition that made it.

A feature that is off, a key that is unbound, a mass slot that is empty, a window that is not in front — all four are correct behaviour, all four look identical to the user (nothing happened), and all four are what "why did it silently do nothing?" is actually asking about.

Take this pattern with you. It applies to any system where an early return is a legitimate outcome — which is most of them.

The seven levels

CallLevelMeans
LOGI(tag, msg)INFOSomething happened that you would want in a timeline.
LOGV(tag, msg)VERBSomething happened, and there are thousands of them. Only written when max logging is on.
LOGW(tag, msg)WARNWrong, but survivable, and nobody is going to notice.
LOGE(tag, msg, detail)FAILIt did not work. The only level that can raise a dialog, and the only one written even when logging is switched off.
LOG_Bail(tag, why)BAILIt deliberately did nothing, and here is why.
LOG_Ok(tag, msg)DONEA thing that can fail finished. Pairs with the FAIL above it.
LOGD(tag, msg)DEVLA breadcrumb: this handler was entered.

Why LOGD is a separate level from LOGI

This is the subtlest and most useful idea in the file. Every other level describes an outcome. LOGD describes an arrival — "control reached here" — because that is a different question and it is the first one you actually ask:

the code ran and decided to do nothing   →  there is a BAIL line
the code never ran at all                →  there is no line at all

Without an arrival marker those two are indistinguishable, and you cannot tell which half of the app to go and look at. So the three functions a user means when they say "I pressed f2 and nothing happened" each open with one:

DoFu2() {
    global editableFu2, openTabFu2
    LOGD("mass.fu2", "DoFu2 entered")
    _DoFuGroup(2, editableFu2, openTabFu2)
}

If there is no devlog: DoFu2 entered line, the problem is upstream of that file entirely — the key never bound, the feature is off, the engine is not running, the press was debounced — and the hk.* lines above say which. If there is one, the cause is below it.

LOGD writes at the normal level, not behind max logging, "because a breadcrumb nobody can see by default is not a breadcrumb."

LOG_Heartbeat — the timer version

LOG_Heartbeat(tag, msg, everyMs := 60000)

The background services poll every 500 ms. A devlog per tick would be 7,000 lines an hour each. But "is the detector still alive?" is a real question with no other answer: it has no window, no tray icon and no output, so a dead one and an idle one look identical. A heartbeat every minute costs 60 lines an hour — and its absence from a stretch of the log is what tells you when the service died.

Why LOGI and not LOG

Log() is an AutoHotkey built-in — the base-10 logarithm. A user-defined LOG() shadows it, so every file that includes the logger works perfectly; every file that does not silently binds to the built-in instead, and LOG("tag", "msg") fails at load with "Too many parameters passed to function". The failure lands in a file that never mentioned the logger, blaming a function nobody wrote, and it only appears once some unrelated include order changes.

Naming the info level LOGI removes the collision outright.

The three switches

In mass_gui.cfg under [Debug], owned by Settings ▸ Debug:

KeyDefaultEffect
LoggingonWrite to debuglogs\mma.log at all.
PopupsoffA FAIL also raises a dialog carrying the last 20 log lines.
MaxLoggingoffAlso write the VERB firehose.

Logging defaults on because "a log nobody switched on is a log that is empty on the morning you need it." Popups is the debug-on-someone-else's-machine switch: off, a failure is a line in a file they would have to find, open and send you; on, it is a dialog in front of them they can screenshot. Same information, and only one of those two actually arrives.

The environment override

MMA_DEBUG=max      ; logging + verbose + popups
MMA_DEBUG=popups   ; logging + popups
MMA_DEBUG=off      ; nothing

Beats all three cfg keys, read once per process. This exists for the machine you cannot open Settings on, and for a failure during startup before anything has read the cfg. This is the single most useful thing in this chapter for you personally: set MMA_DEBUG=max, launch MMA, do the broken thing, read the log.

The rules the file obeys, and why each one matters

  1. A logger must never crash the thing it is logging for. Every path is inside a try, including the ones that look incapable of throwing.
  2. A logger must never lose the last line before a crash. Nothing is buffered — the tail of the file is what you are reading it for.
  3. The switches are cached for 1500 ms. Reading three ini keys per event would put a file read in the send path. A toggle taking a second and a half to apply costs nothing; an IniRead per keystroke is "MMA feels laggy".
CONCEPT-ENCOUNTERED

Cache with a TTL

The pattern appears three times in the core and is worth recognising:

global LOG_SETTINGS_TTL := 1500
global _LOG_T := 0

_LOG_Settings() {
    now := A_TickCount
    if (_LOG_T && now - _LOG_T < LOG_SETTINGS_TTL)
        return                     ; still fresh
    _LOG_T := now
    try { ... re-read the ini ... }
}

Store a timestamp, compare against A_TickCount, refresh when stale. The TTL is chosen against a human timescale: 1500 ms for a settings toggle, 250 ms for the positional model scan — "far below the time it takes a human to click a tab and press a key, so nothing observable is ever stale."

Note the try with the comment: an unreadable cfg leaves the previous values in place. A logger that switches itself off because it could not read its own settings is the exact silent failure this file exists to stop.

The line format

2026-08-28 14:03:11.482  INFO  engine.ahk           18432   mass.fu             group=2  model=1  massNo=1  branch=0  editable=n

Timestamp, level, script name, PID, tag, message. Fixed-width columns, padded by hand rather than through Format, because "the columns are the whole point of the format — you read this file by scanning down the tag column — and a helper that cannot throw is worth four lines."

Every message is flattened to one line (_LOG_Flat replaces newlines with ¶), because a message carrying a newline would split into two records and break every grep in the file's own documentation.

Tags are dotted scopes: mass.fu2, hk.bind, proc.engine, model.resolve, send.snd. Keep them short, keep them stable — it is the column you grep.

Eight processes, one file

_LOG_Append(line) {
    loop 3 {
        try {
            FileAppend(line "`n", MMA_LOGFILE, "UTF-8")
            return true
        }
        Sleep 8
    }
    return false
}

FileAppend opens, writes and closes, so a collision between processes is a sharing violation rather than corruption — it throws, and the retry catches the overwhelming majority. A line lost after three attempts is preferable to a logger that blocks the send path.

Rotation is checked every 250 writes rather than every write, because FileGetSize is a filesystem call and this is on the send path. Eight processes race to rotate; the loser's FileMove throws and is swallowed, which is the correct outcome.

The helpers that make instrumenting one line

These are the functions you will actually call. Learn them; they are how you write code in this repo.

LOG_IniInt(file, section, key, default, tag)

An ini value as a number, or the default when it is not one. Never throws. Use this instead of Integer(IniRead(...)), always.

Why this exists

Integer() throws on anything non-numeric. Where those reads sit at a script's top level, that is not a degraded setting — it is a script that does not load:

  • mass/runtime.ahk reads nine of them → the engine dies → every mass hotkey in MMA is dead, silently.
  • core/hotkeys.ahk reads one → every script that binds a key dies.
  • screen/model_detector.ahk reads ten → the detector dies, and it has no window, so there is nothing at all to notice.

All it takes is one hand-edited MouseControl=yes in a file MMA itself invites you to edit.

The rest

HelperUse
LOG_Int(v, default, what)The same guard for a value that did not come from an ini — a ListView cell, a regex capture, a GUI field.
LOG_IniNum(...)For genuinely fractional settings. IsInteger("0.30") is false, so using LOG_IniInt on a threshold would "work" and silently snap every value to its fallback.
LOG_IniRead(...)An IniRead that says at VERB level when it fell back to the default. This is the single most common silent failure in the tree.
LOG_Try(tag, what, fn, &ok)Run something that might throw; turn the throw into a FAIL line instead of a dialog nobody reads or a bare try that swallows it.
LOG_Err(e)An Error object as one readable string. Every property access individually guarded, because not everything thrown is an Error.
LOG_Kv(tag, map, level)Dump a block of related values as one line — what a script resolved at boot, what a scan measured.
LOG_Marker(text)A findable line. The Debug tab's "Mark log" button writes one, so a user can bracket a reproduction.
LOG_On() / LOG_Max()Test before building an expensive message — AHK evaluates arguments before the call, so LOGV(t, Expensive()) pays for Expensive() either way.

The two files, deliberately

LOGE writes to both mma.log and error_log.txt:

  • mma.log is the timeline — everything, from every process, interleaved. It answers "what was happening when it broke".
  • error_log.txt is the list — failures only, short enough to open and read top to bottom. It answers "what broke".

Those are different questions and they want different files. LOGE also writes even when Logging is switched off, because "a failure is never noise, and a user who turned logging off to keep the file small still wants the file to contain the reason MMA stopped working."

The popup budget

Two limits, both per process:

  • The same tag + message pops once, ever.
  • No more than 15 dialogs in total.

Because a failure inside a timer is not one failure — it is one every 500 ms, and 200 modal dialogs is not a debugging aid, it is a machine you have to reboot. Everything suppressed is still in the file, and the suppression itself is logged.

The ring buffer

The last 40 lines this process wrote are held in memory, so a failure dialog can show what led up to it. The reasoning: "OCR returned nothing" is a fact you cannot act on; the same message under the twelve lines that preceded it usually names the cause.

How to read a log

Set MMA_DEBUG=max, reproduce, then open debuglogs\mma.log. A successful follow-up press looks roughly like this (columns trimmed):

DEVL  hk.fire      (nothing — hk.fire logs at INFO)
INFO  hk.fire      mass.1.fu1 → running  (send)
DEVL  mass.fu1     devlog: DoFu1 entered
VERB  feat         editableFu on  ([Settings] EditableFuAny)
INFO  mass.fu      group=1  model=1  massNo=1  branch=0  editable=n  openTab=n  doubleMM=n
BAIL  alt.intercept  follow-up 1 has 1 variant(s) — nothing to choose between,
                     so it sends directly with no picker
INFO  send.fu      model 1 follow-up 1: 2 part(s), sent as separate messages
INFO  send.snd     sending 118 chars: Want me to strip away the facade of…
INFO  send.snd     sending 64 chars: and then strip for real x?
VERB  hk.fire      mass.1.fu1 finished in 912ms

Read it top to bottom and you have the entire decision chain. Now the diagnostic questions become mechanical:

SymptomWhat to look for
Key does nothingIs there a hk.fire … → running line? No → the key is not bound, or a guard dropped it (there will be a BAIL hk.fire saying which of the three).
Key fires, nothing sendsLook for the BAIL after the DEVL … entered. It names the reason: empty slot, feature off, no model resolved.
Wrong modelmass.fu logs model= and massNo=. Compare with model.resolve above it.
Wrong textmass.load at engine start prints, per model, which slot is live and which slots have text.
Setting appears to do nothingGrep cfg at VERB — every defaulted read is written down.
A service diedIts LOG_Heartbeat line stops. The gap is the time of death.
A save did not applyhk.broadcast — did it reach anybody?

The takeaway for your own code

When you add a function to this repo, ask three questions:

  1. Can this return early? If yes, every early return gets a LOG_Bail naming the condition — including the cfg key you would have to change.
  2. Can this be reached without running? If it is a handler, open it with a LOGD.
  3. Does it read a number from a file? Then LOG_IniInt, never Integer(IniRead(...)).

That is most of what separates code that fits this codebase from code that will produce the next silent bug.
