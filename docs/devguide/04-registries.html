Chapter 4

The four registries

Everything declarative in MMA lives in exactly one file. This is the most useful thing to know about the codebase, and each registry replaced a specific set of hand-kept lists that had drifted apart silently.

RegistryFileDeclares
Featurescore/modes.ahkFEAT_Def(id, cfgKey, label, default, section) — every optional feature, once.
Hotkeyscore/hotkeys.ahkHK_Section / HK_Def(id, label, when, owner) — every key, its context, its owner.
Messagescore/messages.ahkEvery 0x80xx window message.
Servicescore/processes.ahkSVC_Def(id, kind, path, tag, noun, extra) — every background service.

(paths.ahk from the last chapter is arguably a fifth. ARCHITECTURE.md counts it as one.)

CONCEPT-ENCOUNTERED

The registry pattern, and what it actually buys

A registry is: one table, declared once, that everything else walks — rather than the same list written out by hand in each place that needs it.

The benefit is not "less typing". It is that a hand-kept list drifts silently. Nothing tells you when two lists that should match no longer do. In this repo the drift was real and it was invisible:

  • Three services were missing from the boot list, so they did not start until the first watchdog tick five seconds later — and never at all in Easy mode.
  • Two services were missing from the Features chain, so unticking either wrote the config key and left the process running. Untick "Activity tracker" and it kept counting your keystrokes until you restarted MMA, with the checkbox saying it was off.

The test for whether you have built a real registry: can a declared thing be missing from a list? If the answer is no — because there are no lists — you have one.

Registry 1 — Features (core/modes.ahk)

What a feature is

FEAT_Def(id, cfgKey, label, default, section)
idThe short name used in code: if FEAT("altFollowups")
cfgKeyIts key in mass_gui.cfg [Settings]. Existing keys are reused as-is so nobody's settings are lost.
labelWhat the Settings window shows.
default"1" or "0" — the value when the key is absent.
sectionGrouping in the Features tab: Sending, Library, Tools, Background.

It fills three globals:

global FEAT_META  := Map()   ; id -> the record
global FEAT_ORDER := []      ; declaration order, for the Settings window
global FEAT_SECTIONS := []   ; section names in first-seen order

The Features tab draws itself from these. There is no list of checkboxes anywhere — adding a FEAT_Def line makes a checkbox appear.

Easy mode, and why it switches off rather than hides

FEAT(id) {
    if !FEAT_META.Has(id)
        return true                    ; undeclared = not a gated feature
    if MODE_IsEasy()
        return false                   ; Easy switches off the whole registry
    f := FEAT_META[id]
    return Trim(IniRead(MODE_CFG, "Settings", f.cfgKey, f.default)) = "1"
}

So FEAT() is the feature's own checkbox AND Advanced mode. Two consequences fall out of that one line:

  • A user can switch a single feature off inside Advanced, and Easy switches off the lot without touching their choices. Flip back to Advanced and every checkbox is exactly where they left it.
  • Easy does not hide features — it disables them. Advanced hotkeys never register, background children never start, advanced behaviours are bypassed in code. The header states why: "a hidden feature still interferes. The model detector silently gating a model's send keys off is exactly the class of surprise Easy mode exists to remove."

FEAT_Raw(id) is the checkbox alone, ignoring the mode — the Settings window needs it so boxes still show real choices while Easy greys them out.

The single-writer rule

FEAT_SetRaw(id, on) {
    ...
    was := Trim(IniRead(MODE_CFG, "Settings", f.cfgKey, f.default))
    if (was != now)
        LOGI("feat.set", id " " ... "   ([Settings] " f.cfgKey ")")
    IniWrite(now, MODE_CFG, "Settings", f.cfgKey)
}

Instrumented here rather than in the Features panel, on purpose: this is the single writer of every feature key, so one line catches every toggle from everywhere, forever, and cannot be forgotten by a future second caller.

Note that only changes are logged. Saving the Features tab rewrites all ~24 keys whether or not you touched them, and 24 identical lines per save would make the one that matters unfindable. That is a small detail with a big effect on whether a log is usable.

FEAT_HOTKEY_MAP — one gate instead of a guard everywhere

global FEAT_HOTKEY_MAP := Map(
    "altFu",              "altFollowups",
    "br",                 "altFollowups",
    "nextFu",             "nextFu",
    "mFu",                "mouseControl",
    "mPpv",               "mouseControl",
    "gui.actions",        "actionsMenu",
    "marks.",             "tabMarks",
    "recorder.",          "recorder",
    "automation.",        "automation",
    "cap.",               "capitalizer")

This ties hotkey-id prefixes to features, so HK_Bind refuses to register a key whose feature is off. One central gate, instead of a guard in every script.

Matching is longest prefix first, so mass.1.altFu1 finds altFu while plain mass.1.fu1 matches nothing and stays unguarded — correct, because plain follow-ups are not an optional feature.

The bug in this matcher, worth studying

FEAT_ForHotkey strips the model out of a mass id before matching:

if RegExMatch(id, "^mass\.(?:\d+|active)\.(.+)$", &m)
    slot := m[1]

That |active was added after a real failure. The original pattern was \d+ only, so mass.active.altFu1 and mass.active.mFu1 did not match, and fell through to being matched on their full id — where no prefix in the map can ever match, since they all start "mass.".

Result: turning off alt follow-ups or mouse control silenced the numbered keys and left the shared ones live. A feature switch that only half worked, in the direction that sends messages.

The one feature that is deliberately not declared

Read the comment block for sequences. It had a FEAT_Def, and that made it the fourth switch able to kill the Discord import on its own — after the startup-scripts checkbox and the Hotkeys tab, both of which had already done it. Easy mode made it a fourth: it killed the import with no checkbox to look at.

Leaving it undeclared is what makes it always-on, because FEAT() answers true for any id not in the registry. The old cfg key is simply ignored from there on.

Design lesson. "Everything should be configurable" is not free. Every switch is a way for the thing to be off when someone did not intend it, and switches multiply: four independent ways to disable one feature means four places to check and four ways to be surprised. If something is core, give it no switch at all.

Registry 2 — Hotkeys (core/hotkeys.ahk)

1003 lines, and the first thing its header says is: THIS FILE CONTAINS NO KEYS.

The separation

WhereWhat lives there
hotkeys.ahkThe declaration: what actions exist, what they are called, what context they may fire in, which script owns them.
userdata/hotkeys.iniThe binding: which physical key each action is on.
The owning scriptThe behaviour: HK_Bind("nav.unread", Unread).

A script attaches behaviour by id and never names a key:

HK_Bind("nav.unread", Unread)

To change a key: edit the ini, or use the Hotkeys GUI. Never touch code.
To add one: HK_Def(...) here + a line in hotkeys.default.ini + one HK_Bind call.

The declaration

HK_Section("nav", "Navigation")
HK_Def("nav.unread",  "Mark unread / drag back", , "engine.ahk")
HK_Def("nav.nextChat","Next chat down",          , "engine.ahk")

HK_Section("seq", "Sequences")
HK_Def("seq.copyDiscordMsg", "Copy Discord message → parse", "discord", "sequences.ahk")

Four fields: id, label, when (a registered context name, blank = anywhere), owner (for the Hotkeys GUI's conflict report). The double comma is an omitted when.

The id is section.key and it must match hotkeys.ini exactly:

[nav]
unread   = !-
nextChat = Down
The HK_Split exception

Ids split at the last dot — except [hotstring] ids, which split at the first. Those ids end in a hotstring trigger, and a trigger is text the user chose: ..intro, ..ppv4f2. A fifth of the message library starts with two dots.

Splitting those at the last dot gave section hotstring...intro minus its tail — a section that does not exist — so the key was written in one place and read from another and never fired. The first attempt at fixing this refused to bind any trigger containing a dot, which is "a rule about MMA's id format dressed up as a rule about your triggers", and it turned away 23 of them.

HK_Key(id) — the ini is the authority

HK_Key(id) {
    s := HK_Split(id)
    v := IniRead(HK_INI, s.section, s.key, HK_UNSET)
    if (v == HK_UNSET) {
        HK_Log("[" s.section "] " s.key " missing from hotkeys.ini — '" id "' left unbound")
        return ""
    }
    return Trim(v)
}

Three states, not two:

  • Absent from the ini → unbound, and logged as a warning (something is wrong).
  • Present but blank → deliberately disabled, no warning.
  • Present with a value → bound.

That distinction is why HK_UNSET is a sentinel string beginning with Chr(1) and is compared with ==. It is also why HK_MergeDefaults can safely add new keys on update without resurrecting a key you cleared on purpose.

HK_Bind — every gate, in order

HK_Bind(id, fn) {
    if !HK_META.Has(id) {
        HK_Log("HK_Bind('" id "') — id not declared in hotkeys.ahk; ignored")
        return
    }
    if !FEAT_HotkeyAllowed(id) {
        LOG_Bail("hk.bind", id " NOT REGISTERED — feature '" FEAT_ForHotkey(id)
                          . "' is off (or MMA is in Easy mode). Settings ▸ Features.")
        return
    }
    m := HK_META[id]
    if (m.when != "" && !HK_CTX.Has(m.when)) {
        HK_Log("... context '" m.when "' not registered; refusing to bind globally")
        return
    }
    _HK_BOUND[id] := {fn: fn, key: ""}
    _HK_Apply(id, HK_Key(id))
}

Read the third gate carefully. Binding a context-limited key with no registered context would make it global — exactly the bug this registry exists to kill (see the #HotIf trap in chapter 1). It refuses instead.

And note that the feature gate logs. It is still silent to the user — a key absent because a feature is off is not a fault — but "that key does nothing on his machine" and "that feature is off on his machine" are the same sentence, and this is the line that says so. It names the feature, so the answer is actionable.

_HK_Apply — where HotIf and Hotkey meet

_HK_Apply(id, key) {
    m := HK_META[id]
    b := _HK_BOUND[id]
    if (m.when != "")
        HotIf(HK_CTX[m.when])          ; scope the registration
    if (b.key != "")
        try Hotkey(b.key, "Off")       ; release the old key
    if (key != "") {
        try {
            Hotkey(key, _HK_Wrap(id, b.fn))
            LOGI("hk.bind", id " ← " key ...)
        } catch as e {
            HK_Log("'" key "' is not a valid key for " id " — " e.Message)
            key := ""
        }
    } else {
        LOG_Bail("hk.bind", id " has NO KEY — blank or missing in hotkeys.ini,"
                          . " so nothing can trigger it")
    }
    HotIf()                            ; ALWAYS clear it
    b.key := key
}

The HotIf() with no argument at the end is mandatory. Leave it set and every subsequent Hotkey() call anywhere in the script inherits that context.

Identity matters to HotIf. HK_CTX stores the criterion function object, and it must be the same object each time — AHK groups hotkeys by criterion identity. That is why contexts are registered once with HK_Context(name, fn) and looked up, rather than written inline.

_HK_Fire — the anti-fumble gate

Every hotkey in MMA is wrapped in this before it is registered. It exists because AHK hotkey threads are interruptible (chapter 1), and a follow-up takes about a second to send.

_HK_Fire(id, fn) {
    now := A_TickCount
    isSend := _HK_IsSend(id)

    if (HK_WINDOW_MS) {
        if (_HK_SENDING) {
            LOG_Bail("hk.fire", id " DROPPED — another send is still in flight."
                              . " Anti-fumble guard 1 of 3.")
            return
        }
        if (_HK_LAST.Has(id) && now - _HK_LAST[id] < HK_WINDOW_MS) {
            LOG_Bail("hk.fire", id " DROPPED — same key repeated after only "
                              . (now - _HK_LAST[id]) "ms … guard 2 of 3.")
            return
        }
        if (isSend && _HK_LAST_SEND && now - _HK_LAST_SEND < HK_WINDOW_MS) {
            LOG_Bail("hk.fire", id " DROPPED — a different send went out "
                              . (now - _HK_LAST_SEND) "ms ago … guard 3 of 3.")
            return
        }
    }

    _HK_LAST[id] := now
    if (isSend) {
        _HK_LAST_SEND := now
        _HK_SENDING := true
        HK_SendBegin()
    }
    LOGI("hk.fire", id " → running" (isSend ? "  (send)" : ""))
    try
        fn()
    catch as e {
        LOGE("hk.fire", id " threw while running", LOG_Err(e))
        throw
    }
    finally {
        _HK_LAST[id] := A_TickCount
        if (isSend) {
            _HK_LAST_SEND := A_TickCount
            HK_SendEnd()          ; hooks run BEFORE the flag clears
            _HK_SENDING := false
        }
        LOGV("hk.fire", id " finished in " (A_TickCount - now) "ms")
    }
}
CONCEPT-ENCOUNTERED

Debouncing, and three different kinds of it

Guard 1 — in-flight. If any send handler is running, drop this press outright. Without it, F2 pressed during F1's one-second send runs DoFu2 spliced into DoFu1 — half a follow-up in each of two chats.

Guard 2 — same-key repeat. Swallow an immediate repeat of this id: key chatter, or a press that queued during the last run. Measured from both start and end, which is why _HK_LAST[id] is written twice.

Guard 3 — cross-send cooldown. After any send, a different send within the window is dropped, so an accidental F1-then-F2 cannot both go out even once F1 finished.

Set DoubleFireWindowMs = 0 in hotkeys.ini [meta] to disable all three.

Two details worth internalising:

Why "send" is defined the way it is

_HK_IsSend(id) {
    return SubStr(id, 1, 5) = "mass." && SubStr(id, 1, 12) != "mass.select."
}

Navigation and utility keys are not sends, so fast chat-hopping is never eaten. And mass.select.* is explicitly excluded: it sends nothing, it only records which model the shared keys mean. Left in, a select would set the cross-send clock and swallow the follow-up you pressed it in order to send — the switch-then-send sequence is the one pair of presses that must never be debounced against each other.

Why every branch is logged

All three guards are invisible and intentional: the key was registered, the handler exists, and nothing happened. That is indistinguishable from a broken hotkey from the outside. So each drop says which guard ate it and by how many milliseconds it missed — a number that also tells you whether the window is simply set too high for how this person types.

The send hooks — dependency inversion in eight lines

global HK_SEND_HOOKS := []

HK_OnSend(begin, end) {
    HK_SEND_HOOKS.Push({begin: begin, end: end})
}

The three guards only ever see hotkeys. A mouse click on the conversation list mid-send is the same fumble with the same cost, and not one of them can see it coming. So the two edges are published, and engine.ahk installs the click wall on them:

HK_OnSend(CW_Arm, CW_Release)
CONCEPT-ENCOUNTERED

Callback registry — why not just call the function?

Because hotkeys.ahk is included by every process MMA runs — the GUI, each account script, every background service — and click_wall.ahk is loaded by exactly one of them. Naming CW_Arm in hotkeys.ahk would be a load-time "nonexistent function" in all the others.

A registry inverts the dependency: the low-level file publishes an edge, and the high-level file that knows about both subscribes. The same pattern appears twice more in MMA:

  • global ALT_ON_PICK := "" in utils.ahk — mass/runtime.ahk installs the real one; account scripts that never load the engine leave it blank and the commit simply skips it.
  • SVC_Def(..., {onStop: SVC_ClearDetectorStatus}) — a function reference stored in a data table.

Hooks are wrapped in try: a hook that throws must not take the send down with it. The message is the job; the hook is a courtesy.

HK_Broadcast — reaching every process

HK_Broadcast(msg, wparam := 0, exceptHwnd := 0) {
    DetectHiddenWindows true
    for hwnd in WinGetList("ahk_class AutoHotkey") {
        if (hwnd = exceptHwnd)
            continue
        seen++
        try {
            if (InStr(WinGetTitle(hwnd), HK_DIR "\") = 1) {
                PostMessage(msg, wparam, 0, , "ahk_id " hwnd)
                sent++
            }
        }
    }
    ...
}

Enumerated, not a hard-coded list. HK_DIR is the repo root — and the comment at the top of the file explains that this is not tidiness: if HK_DIR were this file's own folder (src\core\), the title test would match nothing, because no script lives there. Every rebind, suspend and remote fire would silently stop crossing process boundaries.

exceptHwnd exists for the Actions menu: it suspends the other scripts while it is open, but must keep its own keys alive to close.

Keeping a user's ini across updates

HK_MergeDefaults()

The updater skips hotkeys.ini, so an update cannot overwrite anyone's keys. That alone would freeze the file: a key added in a later release would be absent, and HK_Key treats absent as unbound — the action would never work.

So new defaults are merged in additively: a key missing from hotkeys.ini is copied from hotkeys.default.ini; a key already present is left alone, always. A blank value counts as present, so a key you cleared on purpose does not come back to life.

CONCEPT-ENCOUNTERED

Additive migration

The general shape: ship defaults in a separate file, merge only what is missing, never overwrite. It works for any user-owned config that a release needs to extend.

Compare with the one-time migration in MMA.ahk (lifting the shell default) and AltStageMigrateSep() in utils.ahk. That second one is worth reading: it replaces a bad default value only if it is still the untouched original. A value someone deliberately set is left alone. "Silently overwriting a customised setting is its own kind of bug."

The dynamic tail

At the very bottom, after every static HK_Def, the file declares one id per bound hotstring — read from the ini, sorted, appended last.

The ordering is load-bearing. The Actions menu fires an action by broadcasting its index in HK_ORDER, so every process must agree on what index N is. Static declarations guarantee that because they are the same source read by every process. These are not static: a script started before you bound a hotstring has a shorter HK_ORDER.

Appending them after every static id keeps indices 1..static identical in every process however long it has been running, and a stale process handed an index in the dynamic tail finds it out of range and ignores it. Sorted, for the same reason — every process must build the tail in the same order, and ini enumeration order is file line order, which changes the moment a line is rewritten.

Registry 3 — Messages (core/messages.ahk)

The smallest registry, and the one whose "before" state is most instructive.

The ten numbers were declared as bare literals in four different files — 0x8001–0x8005 in runtime.ahk, 0x8006 in engine.ahk, 0x8010 in sequences.ahk, 0x8020–0x8022 in hotkeys.ahk. Four files each owning a slice of one number space, and no file listing it.

The senders were worse. main_window.ahk posted the raw numbers, including:

HK_Broadcast(0x8002 + f, val)     ; arithmetic on a magic number

which only works because 0x8003–0x8005 happen to sit directly above 0x8002. And at the receiving end, msg - 0x8002. Both correct, and both encoding the block's layout at a call site — so moving those three numbers would have broken a send and a receive in two different files, silently, with the wrong follow-up going out.

The fix is a pair of named functions:

MMA_MSG_EditableFu(n) {
    return MMA_MSG_EDITABLE_FU1 + (n - 1)
}

MMA_MSG_EditableFuNo(msg) {
    if (msg < MMA_MSG_EDITABLE_FU1 || msg > MMA_MSG_EDITABLE_FU3)
        return 0
    return msg - MMA_MSG_EDITABLE_FU1 + 1
}

The inverse returns 0 rather than a wrong number, because it runs in an OnMessage handler where a bad index would quietly set the wrong toggle.

The rule: declare it here, in the right block, and use the name at both ends. Never a literal — a literal is how 0x8002 came to mean two things depending on which file you read.

Registry 4 — Services (core/processes.ahk)

The clearest before/after in the repo. There were eleven near-identical Launch*/Stop*/*Running triples — 409 lines — differing in four tokens. Then four separate hand-written lists decided when each one ran: the boot list, the Features tab's if/else chain, the watchdog, and the Tools window's own list.

The declaration

SVC_Def(id, kind, path, tag, noun, extra := "")
idThe FEATURE id from modes.ahk. Not a new name — the label, the cfg key and the on/off switch all still come from FEAT_META. A service is a feature that happens to be a process.
kind"ahk" (found and closed by window title) or "python" (found and closed by named event).
pathThe .ahk file, or the .vbs that starts the Python without a console window.
tagThe log tag.
nounWhat to call it in a log line: "the stats overlay".
extraOptional, only where a service genuinely differs: event, needText, needKey, onStop.
 
SVC_Def("modelDetector", "ahk", MMA_SRC "\screen\model_detector.ahk",
        "proc.detector", "the model detector",
        {onStop: SVC_ClearDetectorStatus})

SVC_Def("automation", "python", MMA_SRC "\services\automation\automation_listen.vbs",
        "proc.automation", "the automation listener",
        {event: "Global\MMA.automation.listener.stop",
         needKey: "automation.unsendLast",
         needText: "The automation listener needs Python…"})

onStop is a named function, never a lambda — "this table is meant to be read." That is a deliberate style choice: a data table stops being readable data the moment you inline logic into it.

The verbs

FunctionDoes
SVC_Running(id)Window title for AHK, event handle for Python. Sets DetectHiddenWindows itself, so a caller who forgot cannot get a false "everything is down".
SVC_Launch(id, announce)Gates in order: feature off → already running → Python missing → file missing. Each gate has its own log line.
SVC_Stop(id)ProcessClose or SetEvent. Then onStop, whether or not it was up — the status files it clears are on disk, and a service that died on its own leaves exactly the stale reading this removes.
SVC_Sync(id)Make the world match the switch: launch if on, stop if off.
SVC_SyncAll()Walk SVC_ORDER. This is what fixed the Features tab bug — its hand-written chain covered seven of nine services.
SVC_LaunchEnabled()Start what is on, leave everything else alone. Boot and the watchdog want this, not SyncAll: neither is a moment where the user changed a switch.
SVC_RunningCount()One pass with DetectHiddenWindows held on. Drives the "Tools (2)" button label.
SVC_StopPython()For KillAllScripts, which closes AutoHotkey windows and these do not have one.
SVC_Label(id)From FEAT_META, never retyped — a service renamed in modes.ahk is renamed everywhere.
Why SVC_StopPython exists as a loop

It was four named Stop* calls, one per service — exactly the list a fifth Python service would have been forgotten from. And being forgotten there means it survives "close all" and goes on running after MMA is gone.

Adding a service, in full

  1. A FEAT_Def line in core/modes.ahk.
  2. An SVC_Def line in core/processes.ahk.
  3. The file itself.

That is the whole change. Boot, the Features tab, the Tools window, the Tools button's count and the watchdog all walk SVC_ORDER. tools/test/services_test.ahk exists specifically to stop a fifth list growing back.

Guarding against future TOCTOU

One more pattern that shows up throughout processes.ahk and is worth naming:

CONCEPT-ENCOUNTERED

TOCTOU — time of check to time of use

if WinExist(path " ahk_class AutoHotkey") {
    try {
        pid := WinGetPID(path " ahk_class AutoHotkey")   ; ← may already be gone
        ProcessClose pid
    } catch as e {
        LOGW("proc.toggle", fname " vanished while we were closing it")
    }
}

The script can exit between the check and the use, and then WinGetPID throws "Target window not found". Unguarded, clicking the toggle at the moment a script happens to be dying raised an error dialog and left the button's label lying about the state.

The same problem, worse, in KillAllScripts: WinGetList returns a snapshot, and closing scripts is exactly when its entries go stale. The guard is per window inside the loop, not around the loop — because a throw that escapes the loop means "close all running scripts too?" on exit silently left every script after the vanished one still running.

The general rule: any check on external state is stale by the time you act on it. Guard the action, not the check.
