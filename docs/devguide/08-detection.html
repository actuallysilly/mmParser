Chapter 8

Detection — which model is on screen

The shared [mass.active] keys need an answer to one question: which of your models am I looking at? Three files answer it — a pure pixel scanner, a background service, and a resolver — and the most instructive thing about all three is how often they refuse to answer.

Why this is hard, and what happens when it is wrong

Infloww shows your models as a horizontal strip of tabs. The lit one is the model you are working. That is the whole signal.

The failure mode is specific and expensive: when detection is wrong, it is confidently wrong. A scan that groups two tabs into one run reports "tab 1 of 1" forever, and every shared key then sends model 1's messages no matter which model you are looking at. That is not hypothetical — it is what detector_status.ini said while active_model.ahk was being written, and the comment says so.

The design rule that follows from that, and it is stated a dozen times across these files: 0 means "I cannot see", never "tab 1". A key that does nothing costs a keypress. A key that guesses costs a real message to a real person.

Part one — screen/pill_scan.ahk: pure functions

296 lines. Nothing here reads an ini, writes a file, or starts a timer. That is not a stylistic preference:

"model_detector.ahk (the background service), core/active_model.ahk (the hotkey path) and tools/detector_probe.ahk (the calibrator) ALL include this and have to agree down to the pixel. A calibrator that reads the strip with its own copy of the scan is one you cannot trust — you would tune numbers that satisfy the tool and leave the service wrong."

CONCEPT-ENCOUNTERED

Separating the measurement from the service

The general shape: pure scanners with no side effects, and services built on them. MMA splits src/screen/ in two along exactly this line — pill_scan, rail_scan, reply_scan are pure; model_detector, fansly_detector, reply_box, stats_overlay are services.

The payoff is not testability in the abstract — it is that a service and its calibration UI cannot disagree about geometry. Any time you have a "tuning tool" and a "production path" reading the same thing, they must share the reading code or the tool is lying.

The performance discovery that made this file exist

Measured, not estimated

Everything used to call PixelGetColor per pixel. On this machine that is ~30 milliseconds each:

sampling 3 tab slots (~150 px)    4,632 ms
one sweep of the 330×50 band     10,828 ms

The background detector polls every 500 ms and did a full sweep each time — so it was roughly 20× slower than its own poll interval. Permanently behind, never once returning a current reading.

"That is the real reason auto-detection never worked, and it is why every explanation before it (wrong colours, wrong geometry, tab counting) fitted the symptoms without fixing anything: the data those theories were tested against was stale by seconds."

PixelGetColor goes through GDI GetPixel on the screen device context, which on a composited desktop can round-trip the GPU per call. One BitBlt of the whole band into a memory bitmap costs about the same as a single GetPixel, and every pixel after that is a memory read.

Grab once, then read from the buffer.

PILL_Grab — the capture

PILL_Grab(x, y, w, h) {
    hdcScreen := DllCall("GetDC", "ptr", 0, "ptr")          ; 0 = the whole screen
    hdcMem := DllCall("CreateCompatibleDC", "ptr", hdcScreen, "ptr")
    bi := Buffer(40, 0)                                     ; BITMAPINFOHEADER
    NumPut("uint", 40, bi, 0)          ; biSize
    NumPut("int",   w, bi, 4)          ; biWidth
    NumPut("int",  -h, bi, 8)          ; biHeight, NEGATIVE = top-down
    NumPut("ushort", 1, bi, 12)        ; biPlanes
    NumPut("ushort", 32, bi, 14)       ; biBitCount
    NumPut("uint", 0, bi, 16)          ; BI_RGB
    hbm := DllCall("CreateDIBSection", ..., "ptr*", &pBits, ...)
    old := DllCall("SelectObject", "ptr", hdcMem, "ptr", hbm, "ptr")
    ok := DllCall("gdi32\BitBlt", "ptr", hdcMem, "int", 0, "int", 0,
                  "int", w, "int", h, "ptr", hdcScreen,
                  "int", x, "int", y, "uint", 0x00CC0020)   ; SRCCOPY
    if ok {
        data := Buffer(w * h * 4)
        DllCall("RtlMoveMemory", "ptr", data, "ptr", pBits, "uptr", w * h * 4)
        img := {data: data, w: w, h: h, x: x, y: y}
    }
    ; …every handle released, in reverse order…
    return img
}
CONCEPT-ENCOUNTERED

GDI, device contexts, and DIBs

Device context (DC) — a Windows handle representing a drawing surface. GetDC(0) gives you the screen; CreateCompatibleDC gives you an off-screen one in memory.

DIB section — a device-independent bitmap whose raw pixel bytes you can address directly. CreateDIBSection hands back both a bitmap handle and a pointer to those bytes.

BitBlt — a block transfer. Copy a rectangle from one DC to another. SRCCOPY (0x00CC0020) means straight copy.

Every handle must be released. SelectObject back to the original, DeleteObject the bitmap, DeleteDC the memory DC, ReleaseDC the screen DC. This function polls twice a second forever; a leak here is a machine that runs out of GDI handles in an afternoon.

Two flags worth knowing:

Negative height makes the DIB top-down, so row 0 is the top row and the index arithmetic in PILL_Px is the obvious one. Bottom-up DIBs (the default) are the classic source of vertically mirrored reads.

CAPTUREBLT is deliberately NOT set. It pulls in layered windows — tooltips and overlays — and MMA's own toast can sit over the strip at exactly the moment a select key is pressed.

PILL_Px — one pixel, in screen coordinates

PILL_Px(img, sx, sy) {
    ix := sx - img.x, iy := sy - img.y
    if (ix < 0 || iy < 0 || ix >= img.w || iy >= img.h)
        return -1
    return NumGet(img.data, (iy * img.w + ix) * 4, "uint") & 0xFFFFFF
}

A DIB row is B,G,R,A. A little-endian NumGet of a uint therefore yields A<<24 | R<<16 | G<<8 | B, so masking off the alpha gives 0xRRGGBB directly — the same format PixelGetColor returns, which is what lets the calibrated [Detector] colours stay exactly as they were.

Addressed in screen coordinates so callers never have to think about the capture's origin. -1 when outside.

PILL_CountIn — the whole of positional detection

PILL_CountIn(img, x1, x2, y1, y2, rgb, tol, xstep, ystep) {
    n := 0
    x := x1
    while (x <= x2) {
        y := y1
        while (y <= y2) {
            c := PILL_Px(img, x, y)
            if (c >= 0 && PILL_ColorDist(c, rgb) <= tol)
                n++
            y += ystep
        }
        x += xstep
    }
    return n
}

"This is the whole of positional detection. Tab positions are FIXED, so there is nothing to search for: look at where tab 2 is and ask whether it is lit."

PILL_ColorDist is per-channel max distance, not Euclidean — cheaper, and a tolerance expressed in "how far off can any one channel be" is easier to reason about when you are hand-tuning a value in an ini.

PILL_PickLit — the decision, split out so it is testable

PILL_PickLit(counts, minCount) {
    best := 0, bestN := 0, secondN := 0
    for i, n in counts {
        if (n < 0)
            continue
        if (n > bestN)
            secondN := bestN, best := i, bestN := n
        else if (n > secondN)
            secondN := n
    }
    if (!best || bestN < minCount)
        return 0
    if (secondN * 2 > bestN)
        return 0
    return best
}

Split from the sampling "so the DECISION is testable without a screen — every wrong-model bug here has been in the decision, and none were reachable by a test that needed the live Infloww strip in front of it."

Two refusals, and both matter more than picking a winner:

  • Nothing reaches minCount → no tab is lit, or the colour/region is wrong.
  • The runner-up is more than half the winner → two slots both look lit, which is not what one active tab looks like. It IS what a wrong TabPitch looks like, with one pill straddling two slots.

PILL_Scan — the sweep, and the bug it encodes

Used by the OCR path (which needs a rectangle to read a name out of) and by the probe. The hotkey path never calls it — it already knows where the tabs are.

Why there are two separate column lists

The active and inactive colours used to share one list — a column counted if it held either — and the runs, including the rectangle handed to OCR, came from that.

That works only while the inactive colour really is the inactive pill and nothing else. On Infloww it is not: #0d0d0d is the inactive tab and the empty strip either side of the tabs, measured in 82 of 83 columns.

So every column qualified, no gap ever appeared, and the single run spanned everything. OCR returned "AW Bellarama" — two model names as one string — and the tab count came back 1.

That one string then got auto-claimed into a model's map and permanently gated its keys off. Two symptoms, one root cause, and neither pointed at the colour list.

Part two — screen/model_detector.ahk: the service

254 lines. No hotkeys, no window, no output except an ini file. Started and stopped by the "Auto-detect active model" switch.

The hybrid: cheap scan every poll, expensive OCR only on change

Poll() {
    if (WinMatch != "" && !WinActive(WinMatch)) {
        LOG_Heartbeat("detector.idle", "alive, but '" WinMatch "' is not in front…")
        WriteActive(""), WritePos(0, 0), WriteX(-1)
        _lastCentre := -99999, _lastName := ""
        return
    }
    LOG_Heartbeat("detector.poll", "alive and scanning; last name read: …")

    img := PILL_Grab(RegionX, RegionY, RegionW + 1, RegionH + 1)
    r := PILL_Scan(img, …)
    if (r.count < MinGrey) {
        WriteActive(""), WritePos(0, 0), WriteX(-1)     ; no pill → gating off
        _lastCentre := -99999, _lastName := ""
        return
    }

    ; OCR only when the pill has MOVED (a tab switch) or we have no name yet
    if (_lastName = "" || Abs(r.avgX - _lastCentre) > MoveTol) {
        name := OcrPill(r.minX, RegionY, r.maxX - r.minX, RegionH, OcrScale)
        if (name != "") {
            LOGI("detector", "OCR read '" name "'  pill x " r.minX "-" r.maxX
                           . "  tab " r.index " of " r.total)
            _lastName := name, _lastCentre := r.avgX
        } else {
            LOGW("detector", "found the lit pill at x " r.minX "-" r.maxX " but OCR"
                           . " read nothing from it. Name mode has no answer;"
                           . " positional mode is unaffected and still works.")
        }
    }
    if (_lastName != "")
        WriteActive(_lastName)
    WritePos(r.index, r.total)
    WriteX(r.avgX)
}

The window gate is not optional

"This MUST default to the Infloww window, not to "" — the scan looks at a fixed screen rectangle, not at a window, so with no gate it happily OCRs whatever else is sitting at those coordinates. That is not hypothetical: with WinMatch empty it read VS Code's menu bar and wrote 'File Edit Selection View Go R' as the active model, which then got auto-claimed into a slot and permanently gated that model's keys off."

Everything is written through a dedupe

WriteActive(name) {
    if (name = _written)
        return                      ; ← the early return that keeps the log usable
    LOGI("detector", "active model name: '" … "' → '" … "'")
    _written := name
    try IniWrite(name, STATUS, "detector", "active_model")
}

This runs every 500 ms. Without the early return the log would fill with one identical line twice a second. What is left is a clean record of every tab switch MMA believed in — which is exactly what you want when reconstructing "it sent the wrong model's message at 14:03".

Positional data is free; the name is not

WritePos and WriteX run every poll because they fall straight out of the scan and need no OCR. So positional mode keeps working even when OCR reads nothing at all. That distinction is why the OCR-failure branch says so explicitly.

Top-level initialisation order

A real crash, worth remembering

All of these must be assigned before the first Poll(), not merely somewhere in the file. Top-level statements run in order and function bodies are skipped, so an initialiser sitting further down — next to the function that uses it, which reads better — has simply not run yet when Poll() fires.

That is what "_wPos has not been assigned a value" was: the very first poll, reading a variable initialised 130 lines later.

Part three — core/active_model.ahk: the resolver

783 lines, and the one file in the core with the most refusals per line. It answers "which model?" for the send path, and it is reached from a hotkey context expression — which AHK re-evaluates on every keystroke.

This is a typing-hot-path file

Every consequence in this file follows from that:

  • _IniInt must never throw, or one hand-typed CurrentModel=one is an error dialog per character typed into a fan's chat.
  • The positional scan is cached for 250 ms, or a paragraph is a few hundred pixel scans.
  • It is read-only. It never writes an ini and never opens a dialog. The GUI owns the asking (PromptUnmappedModel), on a timer, in a process that has a window.

Positional mode, in two steps that are deliberately separate

"Two steps, deliberately separate, because only ONE of them is a measurement:

1. Which tab is in front — from the screen. Pure colour, no OCR.
2. Which model that tab is — from Settings. You said so; nothing is read.

Step 2 is not something a detector should ever try to work out. Tab 1 is Aliw because you put it there, and no pixel on screen carries that fact. Every round of this that went wrong went wrong by trying to infer it."

And step 1 is arithmetic, not a search:

TabIndexFromX(x, cfg) {
    if (x < 0)                      return 0
    if (cfg.pitch < 1 || x < cfg.origin) return 0
    return ((x - cfg.origin) // cfg.pitch) + 1
}

"The entire positional detection, in one line of arithmetic. Everything that came before it — grouping runs, counting tabs, matching centroids against taught coordinates within a derived tolerance — was an elaborate attempt to discover something that was never unknown: where tab 2 is."

CONCEPT-ENCOUNTERED

Ask what you actually need to measure

Counting tabs requires seeing the tabs you are not on — and on a theme that draws inactive tabs as bare background, they cannot be seen at all. That is why every "count the tabs" approach failed.

A position requires only the tab you are on, and that one is always visible by definition. Reframing the question from "how many tabs and which index" to "where is the lit one" made an unsolvable measurement into a division.

This is the highest-leverage debugging move in any pixel-reading code: list what you are inferring, and check whether any of it was already known.

ActiveModelStatus() — the answer, plus why

return {no: …, name: …, state: …}
stateMeansWhat a caller can do
"ok"Exactly one slot owns the name; .no is it.Send.
"none"Detector off, or Infloww not in front.Nothing. Manual keys are the answer.
"unknown"A plausible single name that maps to no slot.Worth asking about — e.g. Infloww says "Bellarama" and nothing claims it.
"ambiguous"The text matches more than one slot.Never ask. The answer would put a string containing both models' names into one model's map.

The gate order inside it is itself a design statement:

1. manual mode        ; reads no pixels on ANY platform — must win everywhere
2. Fansly             ; routed by which WINDOW is in front, not by a setting
3. positional         ; if that is the mode
4. name               ; the default

Fansly sits after manual deliberately: "you said model 2" must keep meaning model 2 wherever you are. And routing is by which window is in front, not by a setting, "because a setting is a thing that can be wrong."

_SlotOwnsName — three ways to claim a name

  1. [ActiveMap] File<n> — an explicit, comma-separated list. One model wears more than one name: MMA calls it Rama, Infloww's tab says Bellarama, Discord's channel says something else again.
  2. [ModelAliases] — the alias table the Discord import already uses. It existed and this never read it, which is why an alias of rama=2 did nothing here.
  3. [Settings] Model<n> — the display name, as a substring. Requiring equality meant a name you would call a match was not one.
More than one match returns 0

If the detected text contains two models' names there is no way to tell which tab is in front, and the cost of guessing is one model's mass sent to the other's fan.

And note why matching is by substring, which is not the obvious reason: it matters for the ambiguity check as much as for matching. "AW Bellarama" (two tabs read as one) has to count as evidence for slot 1 as well as slot 2 — or exactly one slot matches, the caller sees no ambiguity, and it confidently returns the wrong model.

The auto-claim that had to be removed

IsAskableModelName(name) {
    name := Trim(name)
    if (name = "" || StrLen(name) > 24)
        return false
    return !RegExMatch(name, "\s")        ; no whitespace = one plausible name
}

This replaced a silent auto-claim that gave any unrecognised string to the first empty slot. That is how "File Edit Selection View Go R" became a model's identity and permanently gated its keys off.

A wrong slot claim is silent and sticky; a question is neither. And the names genuinely do not match across Discord, Infloww and MMA, so there is no rule that could get this right without being told.

Lock mode

The picker window is the right answer to "which model am I on?" and the wrong answer to the way the work is actually done: you answer every message for one model, then move to the next. Over a shift that is a window per keypress asking a question whose answer has not changed in twenty minutes — and a window you dismiss by reflex is a window that is not protecting you from anything.

A lock gives the answer once. While one is set:

  • Every [mass.active] key sends that model — no window, no pixels read.
  • The badge sits on screen naming it, because a mode that silently re-aims every shared key has to be visible from the chat you are sending into, not from MMA's window behind it.
  • An "active model = N" key moves the lock instead of being ignored by it — which is exactly "done with this one, on to the next". Refusing would mean unlock, select, lock again: three keys for one thought.
  • Unlocking gives the picker back, unchanged.
CONCEPT-ENCOUNTERED

The visible-state requirement

From the header of ui/lock_badge.ahk, and repeated in runtime.ahk: the badge is not decoration bolted on the side — it is the condition on which the lock branch is allowed to exist at all, since it sends to a model nothing on screen identifies.

Generalise: any mode that changes what an action does, invisibly, needs an indicator that is present for exactly as long as the mode is. If you cannot make it visible, reconsider the mode.

ToggleMassLock(*) {
    if MassIsLocked() { … unlock, beep 600 Hz, toast … ; return }

    st := ActiveModelStatus()
    if !st.no {
        SoundBeep(300, 250)
        _MassToast("Cannot lock — MMA does not know which model is on screen…")
        LOG_Bail("model.lock", "lock key pressed with no resolvable model … nothing"
                             . " locked, because locking to a guess is the one thing"
                             . " this feature must not do")
        return
    }
    LockToModel(st.no)
}

It locks to whichever model is already resolved, rather than asking. In "I pick" mode that is the model you last selected — the one whose messages you are in the middle of — and with a detector running it is the tab in front. Either way the press means "keep sending to this one", which needs no second question.

A resolve that comes back with nothing is refused, not filled in from the remembered model. "MMA does not know which model is on screen" and "lock every shared key to model 1" are very different sentences, and only one of them is what the key promises.

And the refusal is audible: 300 Hz for 250 ms. You pressed a key expecting a lock, so silence would read as "locked" and every send after it would be a surprise.

Teaching by pointing

TeachPosition(n) {

Pressing "active model = 2" while model 2's tab is in front records "whatever tab index that is, is model 2". The same fact the Settings dropdowns hold, entered the way you actually know it: nobody knows their tab is index 2; everybody knows the tab they are looking at is Rama.

Three things this function does that are worth stealing

It reads the pixels HERE, at the moment of the press. It used to go through detector_status.ini, which the service refreshes every 500 ms and only while Infloww is focused — so "click the tab, press the key" acted on a reading from before the click, and both models got taught the same x. There is no reason to route a measurement you can take directly through a file.

It shows its working. The per-tab pixel counts are the diagnosis: all zeros means nothing lit (wrong colour or region); two big numbers means one pill straddling two slots (wrong TabPitch). Without them, "it did not work" is unactionable.

Every outcome is audible. 880 Hz short for success, 300 Hz long for failure. "A tooltip you have to notice is not feedback when your eyes are on the chat you are about to send into."

_OrderSummary() prints the whole mapping after every press and flags duplicates — two tabs mapped to the same model is a real mistake and one you would otherwise only find by sending to the wrong fan.

The Fansly twin, and the ordering that matters

if TeachFanslyRow(n)
    return
if IsManualPlatform(n) { … }
if (mode = "position") { TeachPosition(n); return }

TeachFanslyRow returns true when it handled the press — meaning Fansly was in front, whatever the outcome. SelectModel uses that to stop, because a press aimed at the rail must never fall through to the Infloww teacher underneath it, which "would file a Fansly model under whatever Infloww tab happened to be lit behind the window and quietly reroute that tab's sends."

And it is checked before the per-model platform setting, "because which window is in front is a fact, and the per-model platform setting is a claim."

The picker window — mass/model_picker.ahk

One window, two questions, both of the form "which model?".

Question 1 — the shared follow-up keys in "I pick" mode

PickGroupForSlot(slot) {
    if RegExMatch(slot, "i)^(?:m|alt)?fu([123])(?:short)?$", &m)
        return Integer(m[1])
    if FEAT("ppvPicker") {
        if RegExMatch(slot, "i)^m?ppv$")     return "ppv"
        if RegExMatch(slot, "i)^m?ppvFus$")  return "ppvFus"
    }
    return 0
}

Derived from the slot name rather than a second list of handlers — because fu2, fu2short, mFu2 and altFu2 are four ids for one action, and a hand-kept list of them is the thing that goes stale the next time a slot is added.

mass and nextFu return 0 deliberately. A window in front of every shared key would be a window in front of everything; __mm has its own asking route, and nextFu is already looking at the screen you would be answering about.

Question 2 — __mm, in any mode

MassSendOrPick(*) {
    count := _PickModelCount()
    if (count <= 1) {
        _SetCurModel(1)
        DoMass()
        return
    }
    _PickOpen("mass")
}

One model and there is nothing to ask. The count comes from the same _PickModelCount the button grid is built from, so "the window would have had one button" and "no window at all" cannot disagree.

Which buttons preview, and why not all of them

_PickHasPreview(group) {
    return (group = "mass") || (group = "ppv") || (group = "ppvFus")
}

"The follow-up groups do not preview. Their text depends on alts, branches and the editable toggle, so whatever a button showed could differ from what the send actually resolves to — a preview that is usually right is worse than none. mass and ppv both paste one fixed field, so theirs cannot drift."

Two things the window has to get right

Focus. The window takes the foreground, and the follow-up is typed into whatever holds it — so sending while the picker is up would type into the picker. The window that was in front is saved on open and re-activated before a single character is sent.

The hotkey thread. mass.active.* starts with "mass.", so _HK_IsSend counts it as a send and _HK_Fire holds the in-flight flag for as long as the handler runs. Waiting for your choice inside that handler would deaden every other key until you answered. So the handler shows the window and returns; the send happens later, from the choice, outside the hotkey thread.

CONCEPT-ENCOUNTERED

Never block inside a hotkey handler

Anything that waits for a human — a dialog, a picker, a confirmation — must not do so inside the handler, because the handler holds locks (here, the anti-fumble flag) and blocks the whole pseudo-thread. The pattern is: show the UI, return, and continue from the UI's own callback.

The same reasoning appears in AltStageBegin, which registers TAB/Enter hotkeys and returns rather than looping.
