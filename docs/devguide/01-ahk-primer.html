What AutoHotkey is

AutoHotkey is a Windows scripting language whose defining feature is that it can register global hotkeys and synthesise keystrokes and mouse input. That is the whole reason MMA is written in it. A follow-up key has to work while Chrome is focused, without Chrome cooperating, and then type into Chrome as though you had typed it. No ordinary application can do that; AHK does it in one line.

What you get with that power is a language that is, frankly, eccentric. It was designed for five-line macros and grew into a general-purpose language. Some of its rules exist for backwards compatibility with a macro syntax from 2003. You will meet several of them.

CONCEPT-ENCOUNTERED

AutoHotkey v1 versus v2

These are different languages that share a name. v1 code does not run on v2 and vice versa. Most AutoHotkey answers you find on the internet, in forums, and in older Stack Overflow posts are v1, and they will not work here.

Tells that you are reading v1 (and should close the tab):

  • Assignment with = instead of :=, e.g. x = 5
  • Percent signs around variables in commands: MsgBox %name%
  • Commands with comma arguments and no parentheses: StringSplit, out, str, |
  • Labels ending in a colon used as targets for Gosub
  • SetFormat, StringReplace, IfWinActive

Every file in MMA opens with #Requires AutoHotkey v2.0, which makes AHK refuse to run the file at all under v1. That line is not decoration — it is the guard that stops a v1 interpreter from silently misreading v2 code as something else entirely.

Where to look things up: the official v2 docs at autohotkey.com/docs/v2/. Nowhere else, until you can tell the versions apart on sight.

Scripts, processes, and the auto-execute section

CONCEPT-ENCOUNTERED

A script is a process

When you run engine.ahk, Windows starts a copy of AutoHotkey64.exe with that file as its argument. That is a real OS process with its own memory, its own variables, and its own message queue. Two AHK scripts running at once share nothing — not globals, not functions, not state. If they need to cooperate they must go through the filesystem or through Windows itself.

This is the single most important thing to internalise about MMA. The GUI and the engine are two processes. When you save a mass in the GUI, the engine does not "see" it. The GUI writes a file and then tells the engine, via a Windows message, that the file changed.

CONCEPT-ENCOUNTERED

The auto-execute section

An AHK script has no main(). When it starts, the interpreter runs statements from the top of the file downward — skipping over function definitions, hotkey definitions and class definitions, which are only declarations — until it hits one of:

  • a return at the top level,
  • the first hotkey or hotstring definition, or
  • the end of the file.

Everything that actually ran is called the auto-execute section. After it finishes, the script sits idle waiting for hotkeys, timers, and messages.

The consequence that bites: top-level code written below the first :: hotstring never runs. There is a real example in src/mass/runtime.ahk, and it carries a long comment explaining exactly this:

; Up HERE, far from the __mm hotstring it belongs beside, for a reason worth the
; distance: top-level code stops running at the first hotstring definition in the
; script, and __mm is one. Down there this loop would parse cleanly, read
; correctly, and never execute.
_MassRegisterNumbered()

The call sits at the top of the file, hundreds of lines away from the thing it relates to, because the alternative is code that looks perfect in a diff and does nothing.

CONCEPT-ENCOUNTERED

Persistence — when does a script exit?

A v2 script exits when the auto-execute section finishes and nothing is keeping it alive. Things that keep it alive: a registered hotkey or hotstring, a running SetTimer, a visible GUI, or the explicit directive Persistent.

What does not keep it alive: an OnMessage handler, or a GUI you created but never showed. This has bitten this repo. A background service that only listened for messages would start, register its handler, reach the end of the file, and quietly exit — leaving no error and no process. Every MMA service therefore has a timer or a hotkey.

Directives and #Include

Lines starting with # are directives: instructions to the interpreter, processed at load time, not statements that run. The ones you will meet:

DirectiveMeaning
#Requires AutoHotkey v2.0Refuse to run under any other version. On every MMA file.
#SingleInstance ForceIf this script is already running, kill the old copy and take over. On every entry point, so a double-launch cannot produce two engines fighting over the same keys.
#Include "path"Paste that file's contents in here, at load time.
#HotIf exprEvery :: hotkey written below this line only fires when expr is true. See the warning further down.
#WarnTurn on load-time and run-time warnings about suspicious code.
CONCEPT-ENCOUNTERED

#Include is textual, and idempotent

#Include "store.ahk" literally inlines that file at that point, before anything runs. There are no modules, no namespaces, no exports. Everything a file defines becomes visible to everything else in the same script.

AHK loads any given file only once, no matter how many times it is named. That is what makes the include graph in MMA safe: paths.ahk includes log.ahk, and log.ahk includes paths.ahk right back. That circle is harmless — whichever is reached first wins and the other include is a no-op. The comment at the bottom of paths.ahk says exactly this, because it looks like a bug and is not.

The practical rule this repo follows: a file that names a function includes the file that defines it. Not "the file that includes me will have done it." That costs nothing (the second include is free) and it means a file can never break because someone reordered includes somewhere else.

Include paths are relative to the file containing the directive, so #Include "../core/paths.ahk" in src/mass/store.ahk resolves to src/core/paths.ahk.

Trap

Because there are no namespaces, every function name in a script is global and can collide. MMA's answer is prefixes: HK_ for hotkeys, MASS_ for the store, FEAT_ for features, PILL_ for the pixel scan, SVC_ for services, MMA_ for paths. The convention is stated in ARCHITECTURE.md §8: a folder's name is the global prefix its functions use. So HSI_Build lives in src/hotstrings/index.ahk, and you can find any function from its name with no search.

Variables, assignment, and scope

CONCEPT-ENCOUNTERED

:= versus =

:= is assignment. = is comparison (case-insensitive equality). == is case-sensitive comparison.

x := 5              ; assign
if (x = 5)          ; compare — true
if (name = "Bob")   ; true for "bob", "BOB", "Bob"
if (name == "Bob")  ; true only for exactly "Bob"

You will see == in this repo specifically where a sentinel value is being tested, because a sentinel must match exactly:

global HK_UNSET := Chr(1) "«unset»"
v := IniRead(HK_INI, section, key, HK_UNSET)
if (v == HK_UNSET)  ; the key is genuinely absent from the file

The sentinel is a string starting with character 1 precisely because no real hotkey could ever equal it — which lets "absent from the ini" be distinguished from "present but blank", and blank means deliberately disabled.

CONCEPT-ENCOUNTERED

String concatenation is a dot, or a space

msg := "model " . n . " follow-up " . group
msg := "model " n " follow-up " group     ; identical — the dot is optional

Both forms appear in MMA. When a string spans lines, the continuation is a leading . on the next line:

LOGW("mass.load", "masses.json does not exist — starting with an EMPTY"
                . " library. Normal on a first run; on an existing install"
                . " it means every mass is missing.")

Note the leading space inside each fragment. Nothing joins them for you.

CONCEPT-ENCOUNTERED

Scope: locals by default, and the global keyword

Inside a function, every name is local unless you say otherwise. A function cannot even read a global without declaring it. This is the opposite of AHK v1 and it catches everyone.

global MASS_MODELS := 3

BadCount() {
    Loop MASS_MODELS       ; THROWS: reads an unset LOCAL named MASS_MODELS
        ...
}

GoodCount() {
    global MASS_MODELS     ; now it means the real one
    Loop MASS_MODELS
        ...
}

The comment above ActiveModelNo() in core/active_model.ahk spells out why this is worse than it sounds there: that function is reached from a hotkey context expression, which AHK re-evaluates on every keystroke. So the throw is not one error dialog — it is one error dialog per character typed into a fan's chat.

There is also a bulk form, global on its own line, which makes the entire function operate in global scope:

ParseCurrent(*) {
    global                 ; every name in here is global
    raw := StrReplace(edPaste.Value, ...)
    ...
}

MMA uses this in the GUI files, where a function genuinely needs a dozen globals (edCtrls, tabs, edPaste…). It is convenient and it is dangerous: a typo creates a global instead of failing. Prefer naming what you need.

CONCEPT-ENCOUNTERED

static — a local that survives between calls

PythonAvailable() {
    static cached := ""
    if cached != ""
        return cached = "1"
    ... expensive scan of PATH ...
    cached := found ? "1" : "0"
    return found
}

The initialiser runs once, the first time the function is reached. This is MMA's standard memoisation idiom. AltStageMigrateSep() uses static done := false to make a one-time migration genuinely one-time per process.

Arrays, Maps, and objects

Three container types that look similar and are not interchangeable. Getting these confused is the most common source of "it says it has no such key" errors.

CONCEPT-ENCOUNTERED

Array — ordered, 1-based

a := ["fu1", "fu2", "fu3"]
a.Push("ppv")
a.Length          ; 4
a[1]              ; "fu1"  — ONE-based, not zero
a.RemoveAt(1)
for i, v in a     ; i = index, v = value
for v in a        ; just the values

AHK v2 arrays have no Sort. This repo hand-writes an insertion sort where it needs one — see HK_HotstringTriggers() in core/hotkeys.ahk, with a comment saying so.

CONCEPT-ENCOUNTERED

Map — a real dictionary, with arbitrary keys

m := Map()
m["fu1"] := "text"
m := Map("fu1", "text", "fu2", "more")   ; key, value, key, value…
m.Has("fu1")      ; true — ALWAYS check before reading
m["nope"]         ; THROWS if absent. It does not return blank.
m.Delete("fu1")
for k, v in m     ; iteration order is insertion order

A Map throws on a missing key. That is why MASS_Blank() in store.ahk exists: it builds a record with every field present and empty, so that every reader downstream can drop its .Has() guards. Guaranteeing shape at the boundary is cheaper than guarding at every use.

It is also why HK_SECTION_LABEL being missing an entry raised "key not found" in the Hotkeys window — a real bug, recorded in hotkeys.ahk's comments.

CONCEPT-ENCOUNTERED

Object — properties by name, with dot access

o := {no: 2, name: "Rama", state: "ok"}
o.no                     ; 2
o.HasOwnProp("name")     ; true
o.state := "ambiguous"   ; assign

An object literal {} is not a Map. Keys must be valid identifiers, and you access them with a dot. MMA uses objects for small structured returns — the pattern is everywhere:

return {no: hits[1], name: active, state: "ok"}
return {index: PILL_PickLit(counts, cfg.min), counts: counts}
return {text: text, rest: rest}
return {name: Trim(m[1]), body: Trim(m[2])}

This is a deliberate style: a function that must answer "which model, and why" returns both in one object rather than an out-parameter or a magic value. ActiveModelStatus() is the clearest example — .no is the answer and .state is the reason, and callers that can act on the reason do.

CONCEPT-ENCOUNTERED

Dynamic property access: obj.%name%

When the property name is in a variable, wrap it in percent signs:

key := "fu" group "_5"        ; e.g. "fu2_5"
if m.HasOwnProp(key)
    part := m.%key%           ; the property NAMED by key

This is used constantly in the send path, because a follow-up group is a number and the fields are named after it. _FuParts in runtime.ahk is three lines of it:

_FuParts(m, group) {
    parts := [m.%"fu" group%, m.%"fu" group "_5"%, m.%"fu" group "_7"%]
    ...
}

The same syntax works on the left of an assignment: o.%k% := v, which is how MASS_AsObject converts a Map to an object one key at a time.

Trap

base is a reserved property name. Writing {base: someValue} does not create a property called "base" — it attempts to set the object's prototype, and throws. In this repo that once produced a script that exited with code 0 and no message at all. If you need a field called "base", rename it — which is why the mass record has ppv_base and not base.

Functions

Name(required, optional := "default") {
    return required optional
}
CONCEPT-ENCOUNTERED

Variadic parameters: parts*

A trailing * in a definition collects all remaining arguments into an array:

sndFu(group, parts*) {
    for p in parts
        ...
}

The same * on a call site does the reverse — it spreads an array into separate arguments:

sndFu(group, _FuParts(m, group)*)   ; array of 3 → three arguments

That one line in _DoFuGroup is doing real work: _FuParts returns an array of three strings, and the * unpacks it so sndFu receives them as its variadic parts.

CONCEPT-ENCOUNTERED

ByRef parameters: &name

An & in the definition means the caller's variable itself is passed, so the function can write to it. The caller must also write &:

ExtractModelName(&raw) {
    ...
    raw := ""              ; modifies the CALLER's variable
    ...
    return name
}

detected := ExtractModelName(&raw)   ; raw comes back stripped

You meet this constantly with RegExMatch, which writes its match object into a ByRef output:

if RegExMatch(t, "i)^!?mm[a]?[\s:]+\s*(.*)", &m)
    text := Trim(m[1])     ; m[0] = whole match, m[1] = first group

An optional ByRef is written &ok? — the trailing question mark is the v2 spelling. &ok := unset is not valid syntax. LOG_Try uses this so callers can branch on success without every caller being forced to.

CONCEPT-ENCOUNTERED

Fat arrows — one-expression functions

MODE_IsEasy() => (MODE_Current() = "easy")

LOG_On()     => (_LOG_Settings(), _LOG_ON)

The second one uses the comma operator: evaluate the first expression for its side effect, then return the second. It reads as "refresh the cached settings, then answer with the flag."

Fat arrows also make anonymous functions:

SetTimer(() => ToolTip(), -1400)          ; clear the tooltip in 1.4s
HK_Context("chrome", (*) => WinActive("ahk_exe chrome.exe"))

(*) means "accept any arguments and ignore them". It appears everywhere in MMA because AHK passes arguments you did not ask for: a hotkey callback receives the hotkey's own name, a GUI event handler receives the control and info. A function that does not accept them raises "Invalid callback function" or a parameter-count error.

That is why so many MMA handlers are declared DoSomething(*) — including ToggleMassLock(*), AltStageNext(*) and ParseCurrent(*). It is not laziness; it is the required signature.

Closures and the loop-variable trap

This one has cost this repo real bugs, more than once, and it is subtle enough that tools/test/mass_bind_test.ahk exists specifically to pin it down.

CONCEPT-ENCOUNTERED

A closure captures the variable, not its value

When a fat-arrow function refers to a variable from the enclosing function, it captures the variable itself. If that variable changes later, the closure sees the new value.

; WRONG — every key selects model 3
Loop 3 {
    n := A_Index
    HK_Bind("mass.select.m" n, (*) => SelectModel(n))
}

There is one function body, so there is one n. All three lambdas share it. By the time any key is pressed, the loop has finished and n is 3.

Two correct fixes, both used in MMA:

; 1. .Bind() — copies the VALUE at bind time
HK_Bind(id, SelectModel.Bind(A_Index))

; 2. a factory function — a parameter is a fresh binding per call
_ModelFire(modelNo, fn) {
    return (*) => (_SetCurModel(modelNo), fn())
}
HK_Bind(id, _ModelFire(n, fn))

The factory works because each call to _ModelFire creates a new modelNo. The lambda closes over that one.

_MassRegisterNumbered() in runtime.ahk uses the factory form and says why in a comment: without it, all twelve __1mm…__12mm triggers would mean model 12.

Trap

A closure cannot read a for-loop's own loop variables at all. In for k, v in map, a lambda inside the body cannot see k or v. Copy them to plain locals first. AHK's /validate syntax check does not catch this; you find out at run time.

CONCEPT-ENCOUNTERED

.Bind() — partial application

SelectModel.Bind(2)        ; a function that calls SelectModel(2)
SVC_RunVbs.Bind(s.path)    ; a function that calls SVC_RunVbs(path)

The bound arguments are evaluated now and stored. Any arguments passed later are appended after them. This is the safest way to build a callback in a loop.

Hotkeys and hotstrings

CONCEPT-ENCOUNTERED

Hotkeys — two syntaxes

Static, at the top level of a file:

F1::DoFu1()          ; one-liner

^!o::                ; block form
{
    ToggleStats()
}

Dynamic, at run time — which is what MMA uses exclusively:

Hotkey("F1", DoFu1)           ; register
Hotkey("F1", "Off")           ; disable, keep the binding
Hotkey("F1", "On")            ; re-enable

MMA never writes a key in code. Every key lives in userdata/hotkeys.ini and is registered by HK_Bind(id, fn), which looks the key up. Chapter 4 covers why.

Modifier prefixes: ^ Ctrl, ! Alt, + Shift, # Win. So ^!F9 is Ctrl+Alt+F9. Other prefixes: * means "fire regardless of extra modifiers", ~ means "also let the key through to the app", $ forces the keyboard hook.

F13–F24 are real keys that no keyboard has — which is why MMA maps a Corsair Scimitar's twelve side buttons to them in src/core/coords.ahk. They can never conflict with anything else.

Trap

*Tab also fires on Shift+Tab, because the wildcard ignores extra modifiers. To handle them separately you must bind *+Tab as well — an exact modifier match beats a wildcard one. The TAB-staging picker in utils.ahk binds both, with a comment saying exactly this.

CONCEPT-ENCOUNTERED

Hotstrings — text that expands as you type

::btw::by the way          ; type "btw" + space → "by the way"
:*X:__mm::MassSendOrPick() ; MMA's actual mass trigger

The letters between the colons are options:

  • * — fire the instant the trigger is typed, with no ending character.
  • X — the replacement is code to execute, not text.
  • ? — fire even inside another word.
  • C — case sensitive.

Dynamic registration exists too, and MMA uses it for the numbered triggers:

Hotstring(":*X:__" A_Index "mm", _MassNumberedFire(A_Index))

The * option has a consequence worth knowing. Because __mm fires the moment the second m is typed, a trigger named __mm1 could never fire — __mm would have already expanded. That is why MMA's per-model triggers put the number in front (__1mm), and it is why a whole arbitration mechanism (NumberedSendActive) could be deleted: the two triggers no longer overlap, so nothing has to decide between them.

Contexts: #HotIf versus HotIf()

CONCEPT-ENCOUNTERED

The two are not the same thing, and mixing them fails silently

#HotIf is a directive. It applies to :: hotkeys written literally below it in the source, at load time. It has no effect whatsoever on keys registered with the Hotkey() function.

HotIf(criterion) is a function. It sets the context for Hotkey() calls that follow it at run time, until you call HotIf() with no argument to clear it.

HotIf(HK_CTX[m.when])          ; from now on, keys are context-limited
Hotkey(key, _HK_Wrap(id, fn))
HotIf()                        ; back to global

This has bitten this repo. The Discord import in sequences/sequences.ahk was wrapped in a #HotIf directive while being bound with Hotkey(). The directive did nothing, so the key was registered globally and fired in every application. The comment in that file records it. The context now comes from the hotkey registry, which applies it the correct way.

A criterion must accept arguments — HotIf calls it with the hotkey's name — so every context in MMA is declared (*) => ...:

HK_Context("chrome",  (*) => WinActive("ahk_exe chrome.exe"))
HK_Context("discord", (*) => WinActive("ahk_exe Discord.exe"))

The performance consequence is real. A context expression is re-evaluated every time the key might fire, which for a key like Tab means on every keystroke. Anything a criterion calls is therefore on the typing hot path. That is why _PositionalStatus() caches for 250 ms, why _IniInt must never throw, and why FEAT() logs at VERB and never higher.

Threads, timers, and interruption

CONCEPT-ENCOUNTERED

AHK "threads" are pseudo-threads, and they interrupt each other

When a hotkey fires, AHK starts a new thread — not an OS thread, but a nested execution context. Crucially, a running thread can be interrupted by another hotkey. If DoFu1 is halfway through sending three messages with pauses between them and you press F2, DoFu2 starts running inside that pause.

The result is two follow-ups interleaved into one chat. This is the exact mess that the three anti-fumble guards in _HK_Fire exist to prevent — see chapter 7.

Because they are pseudo-threads sharing one OS thread, a DPI awareness context set at the top of a script is still in force inside every hotkey and every timer callback. That is why DPI_ScriptWide() works as a single top-level statement in model_detector.ahk.

CONCEPT-ENCOUNTERED

SetTimer, and the meaning of a negative period

SetTimer(Poll, 500)        ; every 500 ms, forever
SetTimer(Poll, 0)          ; stop it
SetTimer(ClearTip, -1400)  ; ONCE, after 1400 ms

A negative period means "run once after this delay". MMA uses it for every tooltip auto-clear and for the staging timeout. Re-calling SetTimer with a negative period on a pending timer resets the countdown, which is how a debounce is written.

Sending text, and the clipboard

CONCEPT-ENCOUNTERED

Send — synthesising keystrokes

Send("^v")           ; Ctrl+V
Send("{Enter}")      ; a named key
Send("hello")        ; literal text, typed character by character
SendText("hello")    ; literal, no modifier interpretation at all

Braces name special keys; ^!+# are modifiers, exactly as in a hotkey. SetKeyDelay(-1, -1) at the top of utils.ahk makes sends as fast as possible.

CONCEPT-ENCOUNTERED

The clipboard, and why every use is guarded

A_Clipboard is a built-in variable that is the Windows clipboard. Assigning to it copies; reading it pastes-in-reverse. MMA sends messages by putting them on the clipboard and pressing Ctrl+V, because that is far faster and far more reliable than typing 200 characters into a web app.

A_Clipboard := ""          ; clear first, so ClipWait tests THIS write
A_Clipboard := arg
if !ClipWait(1)            ; wait up to 1s for the clipboard to actually hold it
    LOGE(...)
Send("^v")
Send("{Enter}")

ClipWait(seconds) returns false on timeout. The failure mode if you ignore it is the worst in the codebase and the comment on Snd() says so plainly: if the clipboard did not take the text, Ctrl+V pastes whatever was on the clipboard before into a real fan's chat, and then presses Enter. There is no way to notice except by reading the message that went out.

Clearing to "" first is not decoration either. Without it, ClipWait would see the previous content and return true immediately.

Windows: titles, classes, and hidden windows

CONCEPT-ENCOUNTERED

WinTitle — how AHK addresses a window

Most window functions take a "WinTitle", which can be a title substring or one of several prefixed forms:

FormMeans
"Infloww Messages"a window whose title contains this
"ahk_exe chrome.exe"matched by executable
"ahk_class AutoHotkey"matched by window class
"ahk_id " hwndone specific window handle
"A"the currently active window
combinedpath " ahk_class AutoHotkey" — both must match

WinExist(t) returns the hwnd or 0. WinActive(t) returns non-zero if that window is in front.

CONCEPT-ENCOUNTERED

A script's main window is titled with its full path

Every AHK script has a hidden main window, and Windows titles it with the script's full file path. That single fact is load-bearing throughout MMA:

  • HK_Broadcast finds "our" scripts by testing whether a window's title starts with the repo root.
  • processes.ahk closes a service by looking up path " ahk_class AutoHotkey" and calling ProcessClose on its PID.
  • sequences.ahk posts the auto-parse message to a title built from the main window's path.

It is also why MMA.ahk uses Run instead of #Include to start the GUI — its own comment explains that including would run the GUI under the title "MMA.ahk" and all three of those mechanisms would quietly stop matching.

These windows are hidden, so you must turn on DetectHiddenWindows true before WinExist can find them. Every MMA function that looks for a script saves the previous setting, sets it, and restores it — because leaving it on changes the behaviour of unrelated code.

Window messages — how processes talk

CONCEPT-ENCOUNTERED

PostMessage and OnMessage

Windows lets any process send a numbered message to any window. The receiver registers a handler for that number.

; receiver
ReloadMasses(*) {
    global MASS_DOC := MASS_Load()
}
OnMessage(MMA_MSG_MASSES_CHANGED, ReloadMasses)

; sender, in another process entirely
PostMessage(MMA_MSG_MASSES_CHANGED, 0, 0, , "ahk_id " hwnd)

A message carries a number and two integer payloads (wParam, lParam). It cannot carry a string. That constraint shapes MMA's entire IPC design: the message is only ever a nudge, and the actual data travels through a file. "The GUI saved masses.json" is a message with no payload; the engine responds by re-reading the file.

Numbers must be in the user range, above 0x8000. MMA declares all ten in core/messages.ahk and uses the name at both ends, because a literal is how 0x8002 once came to mean two different things in two different files.

A handler receives four arguments: (wParam, lParam, msg, hwnd). Handlers that ignore them are declared (*). msg is the message number, which is what lets one handler serve three contiguous messages — see SetEditableFuMsg.

Trap

PostMessage's fourth parameter is Control, not the target window. Passing 0 there throws "Target window not found". Omit it — leave the slot empty, as PostMessage(msg, wparam, 0, , "ahk_id " hwnd) does.

INI files as a database

CONCEPT-ENCOUNTERED

IniRead / IniWrite, and the silent-default problem

v := IniRead(file, "Section", "Key", "default")
IniWrite(value, file, "Section", "Key")
IniRead(file, "Section")        ; whole section as "key=value" lines
IniRead(file)                   ; all section NAMES, newline separated

MMA stores essentially all of its configuration this way, in userdata/mass_gui.cfg and userdata/hotkeys.ini. Settings are read per use, not cached, which is what lets a change in the GUI apply to the engine's next keypress with no restart.

The failure mode that shapes half this codebase: IniRead with a default cannot fail. A wrong path, a missing section, a typo in the key name — all return the default, silently. A setting appears to do nothing and nothing says why. The header of paths.ahk is entirely about this, and LOG_IniRead exists so that a defaulted read is at least written down at verbose level.

A second failure mode, worse:

n := Integer(IniRead(cfg, "Settings", "ModelCount", 3))   ; ← latent crash

Integer() throws on anything non-numeric. One hand-typed ModelCount=three in a file MMA itself invites you to edit does not mis-configure the app — if that line is at a script's top level, the script does not load. In runtime.ahk that means every mass hotkey in MMA is dead, silently. The repo's answer is LOG_IniInt, which degrades to the default and says so.

Two more ini quirks that have caused bugs here:

  • Windows strips leading and trailing whitespace from values, so a separator of " | " comes back as "|". MMA encodes spaces as \s in the staging separators for exactly this reason.
  • A trailing ; comment on a value line is not stripped — it becomes part of the value. hotkeys.default.ini says so in its header.
  • An = inside a key is impossible: IniWrite of a key a=b emits a=b=value, which reads back as key "a". That is why the hotstring-key UI refuses a trigger containing = at the point of writing.

Errors

CONCEPT-ENCOUNTERED

try / catch / finally / throw

try {
    risky()
} catch as e {
    LOGE("tag", "it failed", LOG_Err(e))
} finally {
    cleanup()          ; runs whether or not it threw
}

try FileDelete(tmp)    ; single-statement form, no braces

catch as e binds the error object. It has .Message, .What, .File, .Line, .Extra — LOG_Err(e) in log.ahk flattens all of them into one readable string, each access individually guarded because not every thrown value is an Error object.

finally is used in MMA wherever a global setting is temporarily changed, so it is restored even on a throw:

prev := A_DetectHiddenWindows
DetectHiddenWindows true
try {
    ...
}
finally
    DetectHiddenWindows prev

The bare try with no catch swallows everything. That is deliberate in exactly one place — the logger — where the rule is stated as: a logger must never crash the thing it is logging for. Everywhere else, a bare try should make you suspicious.

Trap

< and > are numeric operators. Comparing two non-numeric strings with them throws "Expected a Number but got a String". Use StrCompare(a, b) for ordering strings. This is not caught by /validate; you find out at run time. A character-by-character filter loop in next_fu.ahk was written this way originally, and it did not filter letters — it crashed on the first one.

Trap

A_Index always refers to the innermost loop. In

Loop MASS_SLOTS {
    for field in MASS_Fields()
        ck := "m" A_Index "_" field    ; ← counts FIELDS (1..44), not slots
}

the inner for has taken over A_Index. MMA's fix, recorded in a comment in LoadFile, is to copy it first: slot := A_Index before the inner loop. The bug this produced was silent — it built control keys like m17_fu1 that matched nothing.

DllCall — talking to Windows directly

CONCEPT-ENCOUNTERED

Calling the Win32 API from a script

hdc := DllCall("GetDC", "ptr", 0, "ptr")

The pattern is: function name, then alternating type, value pairs, then a final type which is the return type. Types you will see in MMA: "ptr", "int", "uint", "ushort", "str", "ptr*" (an out-pointer).

MMA uses DllCall in three places, all core:

  • pill_scan.ahk — GetDC, CreateCompatibleDC, CreateDIBSection, BitBlt, RtlMoveMemory: capture a rectangle of screen into memory so pixels can be read a thousand times faster. Chapter 8 explains why that mattered so much.
  • processes.ahk — OpenEventW / SetEvent: a Python service has no AHK window, so it signs its presence with a named kernel event. Opening it answers "is it running?"; setting it means "please exit".
  • dpi.ahk — SetThreadDpiAwarenessContext: make coordinate maths agree with a mixed-DPI desk.

Buffer(size) allocates raw memory; NumPut and NumGet write and read typed values into it at byte offsets. That is how the bitmap header in PILL_Grab is built.

Coordinates and DPI

CONCEPT-ENCOUNTERED

CoordMode — relative to what?

CoordMode("Pixel", "Screen")   ; pixel functions use screen coordinates
CoordMode("Pixel", "Client")   ; …relative to the active window's client area
CoordMode("Mouse", "Screen")

The default is "Window", which is almost never what you want. MMA's detectors use "Screen" because they scan fixed rectangles; the Discord import uses "Client" because the header band's position depends on the window, not the desktop — and because a maximised window's rect starts at −8,−8, which would shift a screen-relative band right off the header.

CoordMode is global to the thread, so functions that change it save and restore the previous value. DiscordChannelName() is a clean example.

CONCEPT-ENCOUNTERED

DPI awareness

AutoHotkey ships a system-DPI-aware manifest. On a desk where every monitor shares the primary's scaling, that is indistinguishable from being fully aware. Put a second monitor on a different scale and Windows starts handing the process invented numbers for window rects, cursor position, and the origin a BitBlt reads from.

The measurements are in src/core/dpi.ahk: a box asked for at (−1200, 400) 400×200 on a 150 % second monitor landed at (−1008, 545) 480×240. Off by exactly 1.2× in both size and position.

The reason this is nastier than "20 % off" is that inside the process every wrong number is consistent. The mouse, the overlay and the capture rectangle all agree with each other and disagree only with the screen. Every reading looks plausible.

Two entry points, and choosing wrong is the only way to break something:

  • DPI_ScriptWide() — for a script whose whole job is pixels, called once at the top. Not for anything that builds a normal GUI.
  • DpiScope() / DPI_Enter() + DPI_Leave() — thread-scoped and reversible, for a library included into a process that does have a GUI.

Checking your work without running it

AutoHotkey can parse a file and report syntax errors without executing it:

AutoHotkey64.exe /validate "path\to\file.ahk"

Two traps, both recorded in this project's notes:

  • AHK is a GUI-subsystem executable, so it detaches immediately from a console. From PowerShell you must use Start-Process -Wait to get the exit code.
  • Under Git Bash on Windows, MSYS rewrites /validate into a path. Set MSYS_NO_PATHCONV=1.

/validate is a parser, not a linter. It will not catch: a closure reading a loop variable, a string comparison with <, a Map key that does not exist, or a variable and a function whose names differ only by case — which is the next one.

Trap

A variable and a function cannot share a name, even across case. AHK identifiers are case-insensitive, so a global _LOG_FORCED and a function _LOG_Forced() are the same name. The script fails to load — and it fails silently, exiting with code 0 and printing nothing. That exact collision is why log.ahk has a global called _LOG_FORCE_CACHE with a comment explaining that it may not be called _LOG_FORCED.
